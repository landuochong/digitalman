# 露米数字人项目：对话记录与实验日志

更新时间：2026-08-04

## 1. 项目目标

制作一个语音优先的虚拟好友。用户直接说话，AI 理解上下文后用自然中文和女性声音回答；人物口型应与语音匹配，眼神、表情、头部和手势应克制、连贯并与语义一致。

目标不是一张静态图片加开合嘴，而是具备以下完整状态：倾听、思考、准备开口、说话、短暂反应、恢复待机和被用户打断。

## 2. 对话中确认的产品要求

- 以语音交流为主，不把文字聊天作为主要入口；字幕默认隐藏。
- 可以使用 MiniMax，不要求 OpenAI API Key。
- 使用女性声音，目前为 MiniMax `female-tianmei`。
- 人物不能持续左右晃动、左右扫视或一直露出夸张表情。
- 待机应稳定，以自然眨眼、轻微呼吸和眼神交流为主。
- 口型不能只按音量机械开合，长期目标是音素或 viseme 级同步。
- 表情和动作必须与语义相关，但不能每句话都触发动作。
- 如果真人视频难以达到自然效果，可以接受动漫风格。

## 3. 技术路线调研

### 3.1 商业实时数字人

调研过 HeyGen LiveAvatar 和 Tavus。优点是人物真实、实时链路完整；缺点是持续费用、平台依赖和自定义控制受限。本项目以个人实验为主，因此没有作为当前主路线。

### 3.2 DH_live

项目：`kleinlee/DH_live`

已经使用用户下载的 `epoch_40_new.pth` 完成 DH_live Mini 预处理和网页端渲染。它适合从静默人物视频生成音频驱动口型，浏览器端资源较轻，但主要改善嘴部区域，无法自动解决全脸协调、眼神和自然手势。

生成物位于：

- `resources/models/DINet_mini/epoch_40_new.pth`
- `public/dh-live/`
- `public/dh-live/actions/`

### 3.3 LivePortrait

项目：`KlingAIResearch/LivePortrait`

用于离线生成眼神、眨眼和微表情素材，再交给 DH_live 处理口型。为了避免表情驱动影响嘴唇，实验 checkout 增加了 `exp_no_lip` 区域；补丁保存在 `resources/liveportrait/exp-no-lip.patch`。

成功生成 `happy`、`caring`、`thinking`、`surprise` 等状态，均通过 DH_live 的“源视频无明显说话”质量检查。

### 3.4 其他项目

- `kleinlee/MatesX`：与 DH_live 生态相关，但没有解决现有真人素材的动作自然度问题。
- `yangkang2021/I_am_a_person`：提供了可参考的组合思路，但不是当前浏览器端的直接替换方案。
- `anliyuan/Ultralight-Digital-Human`：轻量口型路线有参考价值，但同样不能自动提供自然的全身行为。
- `duixcom/Duix-Mobile`：移动端本地 2D 数字人 SDK，支持 PCM 流、打断和预定义动作区间。它适合 Android/iOS，但动作幅度主要由模型内的素材决定，网页端不能直接接入。

## 4. 真人素材实验

### 4.1 人物与动作素材

使用 Mixkit 43811 候选视频切分出：

- `idle`
- `smile`
- `wave_approval`
- `shrug`
- `confident_arms_crossed`

动作清单和映射保存在 `resources/candidates/mixkit-43811/action-manifest.json`。

### 4.2 持续晃动

最初将动作视频循环作为待机，导致人物身体持续摇晃。后来改为稳定片段和一次性动作，动作结束后返回 `idle`。

结论：明显身体动作不能循环；待机必须单独制作。

### 4.3 眼睛持续左右看

第一版 LivePortrait 待机使用官方 `d0.mp4` 的眼睛驱动，继承了真人反复左右扫视。MediaPipe 测得眼球水平范围约 `0.2200`。

后来从同人物低强度表情片段中选取正视且包含完整眨眼的 1.8 秒区间，眼球水平范围降到约 `0.0534`，减少约 76%。当前部署待机为：

- `resources/liveportrait/output/idle-centered-blink.mp4`
- `resources/liveportrait/prepared/idle-centered/`

### 4.4 默认露齿

原始人物源帧本身是露齿微笑。尝试用图像编辑生成自然合唇源图，再通过 LivePortrait 和 DH_live 重建：

- `resources/liveportrait/source-centered-closed-mouth.png`
- `resources/liveportrait/prepared/idle-closed-mouth/`

闭嘴成功，但人物脸部、构图和原视频存在可见差异。为了保持同一人物的一致性，闭嘴实验被保留但未部署，当前仍使用原人物待机。

结论：真人视频路线中，源素材决定了外观上限。对嘴部做生成式修改容易破坏身份和画面一致性。

## 5. 对话和语音链路演进

### 5.1 第一版

流程为：等待用户说完 → 请求完整 MiniMax 回复 → 请求完整 TTS → 切换动作 → 播放语音。问题是等待时间长、动作突然切换、回复字段可能污染朗读正文。

### 5.2 文案字段污染

最初要求 MiniMax 同时输出 `reply`、`emotion` 和 `action` JSON。模型格式稍有变化时，内部状态词可能进入正文。

当前改为：

- MiniMax 只生成可以直接朗读的中文正文。
- 服务端删除 `<think>`、Markdown、JSON 和内部状态标签。
- 情绪与动作由本地程序分析，不交给 TTS。
- TTS 永远只接收清理后的 `reply`。

### 5.3 当前流式版本

当前流程：

```text
浏览器语音识别
  → MiniMax 流式回答
  → 服务端隔离 reasoning 并按句切分
  → 第一条完整短句立即请求 TTS
  → 后续短句进入可打断播放队列
  → 动作切换与语音生成并行
  → DH_live 接收 WAV 驱动口型
```

真实测试中 MiniMax 首句约 2.4 秒到达；MiniMax Speech 2.8 返回 16 kHz、16-bit、单声道 WAV。用户再次开口时会取消模型流、TTS 队列、当前音频和口型。

相关实现：

- `server.mjs`
- `src/companion.mjs`
- `public/app.js`
- `scripts/live_smoke.mjs`

## 6. 已确认的问题与经验

1. 口型、表情和动作不能由互不相关的模型同时争夺同一面部区域。
2. 预制真人动作视频可以用于验证，但切片间身份、光照和姿态很难连续。
3. “动作越多越自然”是错误方向。自然感来自稳定基线、低幅度变化和正确时机。
4. 不应让 LLM 每句话选择一个动作；行为调度需要冷却时间、动作预算和互斥规则。
5. 文案正文和控制元数据必须彻底分离。
6. 流式 LLM 只能降低文本等待；真正自然还需要流式 ASR/VAD、流式 PCM TTS 和音素时间戳。

## 7. 决策：开发 VRM 动漫数字人

真人视频路线暂时保留用于对照，不再继续投入大量时间修补素材。新路线采用网页 3D VRM：

- VRoid/VRM 人物保持统一身份和画面风格。
- `three.js` 与 `@pixiv/three-vrm` 负责浏览器渲染。
- VRM 表情权重控制微笑、眨眼和口型。
- 标准骨骼动画控制头部和手势，可设置低权重并平滑混合。
- 当前 MiniMax、流式聊天、TTS 和中断机制继续复用。

行为规则初版：

- 眼睛大部分时间正视用户，视线变化小于约 5°。
- 待机只有呼吸、眨眼和非常轻微的重心变化。
- 短回答不触发手势。
- 每轮最多一个明显手势，两个明显手势至少间隔 3 秒。
- 普通表情强度为 0.15–0.35。
- 动作以 300–700 毫秒淡入淡出。
- 首批只实现轻微点头、轻微侧头思考、小幅微笑和首次问候四种行为。

## 8. VRM 服饰与发型切换实验

2026-08-04 增加三套完整造型预设：简约短发黑白装、齐肩短发针织开衫、紫色长发黑粉街头装。实现采用整套 VRM 切换，而不是运行时拼装衣服和头发：

- 新模型完整解析后才替换旧模型，避免切换时画面闪空。
- 旧模型从场景移除后释放几何体、材质和纹理，避免反复换装造成内存累积。
- 每套造型复用相同的闭嘴待机、眨眼、注视、表情、口型和低幅手势系统。
- 当前造型保存在浏览器，下次打开自动恢复。
- 两套 VRoid 官方样例并非 CC0，具体使用条件单独记录在 `public/vrm/THIRD_PARTY.md`。

浏览器实测三套人物均可加载，换装后手臂自然下垂，镜头构图和表情骨骼正常。

动作联调时发现骨骼动作最初没有播放：调度器使用 `performance.now()`，动画混合使用 `THREE.Clock.elapsedTime`，不同时间轴使动作权重始终为 0。统一改用人物动画时钟后恢复正常；随后通过浏览器逐帧截图把挥手调整为肩部抬起、肘部弯曲、手掌停留在头侧的可见幅度。页面增加折叠的“动作测试”面板，用于把骨骼问题与语音场景判断问题分开验证。用户实测后将动作冷却由 8 秒缩短为 3 秒，并扩展日常口语触发词。

待机手臂最初仍接近完全伸直。后续将默认姿势调整为左右略不对称的轻微屈肘、前臂向身体内侧、手腕轻微偏转，并给四指加入 4–7° 的自然弯曲；动作结束后通过阻尼平滑回到该放松姿势。

“我饿了”实测时接口已正确返回 `caring`，但原关心动作只有约 4° 的头部变化，用户感知为没有触发。浏览器截图验收后将其改为持续约 1.45 秒的温和低头、颈部跟随和轻微上身前倾，并校正了 VRM 骨骼 X 轴的正负方向。

庆祝场景最初复用了挥手。后续将问候与庆祝拆分：问候继续使用 `wave_approval`，成功、完成、录取、好消息和恭喜改用 `clap`。鼓掌采用双臂前移、肘部弯曲、双手在胸腹前靠近并小幅周期运动的轻拍手动作；为兼容不同 VRM 手型，没有强制手腕大角度翻转，以避免拇指和掌面穿模。

惊讶动作由单纯抬头改为右手轻捂嘴、头部轻微后仰并叠加低强度惊讶表情。固定欧拉角在不同 VRM 骨骼朝向下会让手落到头侧或画面外，因此改为上臂、前臂两段骨骼迭代追踪嘴前的世界坐标。浏览器中间帧检查确认手掌覆盖嘴部，动作结束后平滑回到放松姿势。

默认站姿进一步改为双手在小腹前交叉下垂，手腕轻叠、手指朝下，替代双臂垂在身体两侧的僵直观感。关心动作改为双手从下方抬至胸前偏上，双腕交叉、手指向上，形成较柔和的祈祷姿势，同时保留轻微低头与上身前倾。两种姿势均使用双臂世界坐标追踪，动作结束后自动回到默认交叠姿势。

后续跨模型复测发现默认双手重叠过深会造成手腕扭曲，鼓掌的固定骨骼角度在部分服装模型上会让手臂折到身体后方。默认姿势改为一只手轻搭另一只手腕、前后略微错层；鼓掌改为胸前世界坐标目标，两只竖直手掌小幅开合，不再依赖各模型不同的固定欧拉角。惊讶动作时长和表情强度提高，并补充“哇、真的吗、我的天、怎么可能、太夸张、吓我一跳”等口语触发词。简约和学院两套 VRM 均完成浏览器中间帧验收。

继续验收发现默认搭手姿势仍无法兼容不同袖宽和手臂比例：无袖模型可接受时，宽袖模型会发生手腕穿插；拉开目标点又会导致掌心朝上。最终取消默认双手 IK，恢复双臂自然下垂、肘部轻微放松、手指轻曲的稳定待机姿势。双手合拢仅用于短时的关心和庆祝动作。宽袖与无袖两套模型均完成静态帧复测。

## 9. AITuber Kit 动作系统对照实验

2026-08-05 将 AITuber Kit v2.70.0 解压到 `experiments/aituber-kit`，使用工作区 Node 24 安装依赖，并在 3420 端口独立启动，不覆盖现有 3417 服务。上游采用自定义非商用许可证，个人非商用实验可免费使用；安装审计报告包含 19 个上游依赖漏洞，因此当前仅作为本地效果验证，不直接并入主项目。

实现检查表明，它的待机使用标准 `idle_loop.vrma`，而 think、cheer、mouth_cover、wave、clap 等动作使用预制 JSON 姿势；wave 和 clap 通过多姿势序列播放，分别以约 0.5 秒和 0.2 秒切换。浏览器开启内置姿势调试后，实测结果如下：

- 默认人物的挥手包含手臂、手腕和表情配合，明显优于单个程序角度。
- 捂嘴姿势能准确覆盖嘴部，手肘方向稳定。
- 鼓掌在张开与合拢姿势间循环，手掌接触和手腕朝向自然。
- 切换到与当前项目学院人物同源的 `AvatarSample_A` 后，捂嘴和鼓掌仍然成立，说明预制规范化姿势的跨模型稳定性好于当前简易 IK。

阶段结论：AITuber Kit 的效果值得借鉴，优先移植其 VRMA 待机播放器、姿势 JSON 格式、姿势序列和动作淡入淡出；现有 MiniMax、语音和业务页面可继续保留，不必整体替换。

### 9.1 主项目迁移结果

随后将动作层接入 3417 主项目，而不是继续依赖 AITuber Kit 的完整页面：

- 使用 Pixiv 官方 `@pixiv/three-vrm-animation` 播放 `idle_loop.vrma`。
- 新增兼容 AITuber Kit 两种 JSON 姿势格式的解析器；挥手和思考使用完整 VRM Animation JSON，鼓掌、关心和捂嘴使用 Web Pose JSON。
- 挥手与鼓掌按多帧姿势循环，其他姿势短暂保持；所有动作以约 350 毫秒淡入淡出，并在 1.6–1.8 秒后自动回到待机。
- 关心采用低头、双手指尖相触的低幅动作；惊讶采用单手捂嘴；不再使用跨模型容易穿模的运行时手臂 IK。
- MiniMax 文案、流式 TTS、口型和 3 秒动作冷却逻辑保持不变。

浏览器逐帧验收覆盖三套 VRM。简约人物的挥手、鼓掌、关心、惊讶均能正确显示；学院人物的捂嘴位置正确；暗色长发人物的关心和思考动作未出现手臂跑到身后，动作结束后能恢复双臂自然下垂。页面无 JavaScript 错误。动作资源的非商用限制和来源记录在 `public/vrm/motions/THIRD_PARTY.md`。

首次接入时，动作在流式接口的 `meta` 事件到达后立即开始，而第一句语音还要等待 TTS 生成，导致短动作往往在声音开始前已经完成。随后将动作触发点移到首段音频真实触发 `play`/浏览器语音 `start` 的时刻：等待语音期间只更新低幅面部情绪，第一句开口与当轮唯一手势同步开始，后续分句不重复触发动作。

### 9.2 人物观看角度

参考 AITuber Kit 的人物视角控制，主页面增加水平旋转：人物区域支持鼠标或触摸左右拖动，并提供左转、正面、右转三个可见按钮，双击人物恢复正面。旋转采用阻尼过渡并限制在左右 65°，避免人物完全背对用户。实现对 VRM 根节点的原始朝向叠加视角偏移，因此同时兼容 VRM 0.x/1.0，且不会覆盖标准骨骼动作。浏览器实测暗色长发模型在左右侧身时待机、视线和挥手动作均正常。

旋转初版直接使用 VRM 文件根节点，部分模型会因自身原点和几何外框不对称而在侧转时横向漂移。后续增加独立外层旋转轴，以髋部骨骼作为身体中线；待机 VRMA 首帧应用后再次校准构图，消除动画髋部位移造成的偏左。相机距离由人物高度的 1.23 倍调整为 1.4 倍，在保持上半身交流构图的同时给头顶留出余量。暗色长发和学院两套模型已完成正面、侧面截图验收。

### 9.3 可切换待机手势

默认手部姿势增加三种用户预设：自然下垂、指尖轻触和双臂抱胸。非自然姿势使用规范化 Pose JSON 持续保持，并叠加去除髋部位移的低权重 VRMA 呼吸；选择保存在浏览器。对话触发挥手、鼓掌等明显动作时，待机手势先淡出，动作结束后显式恢复原待机动作及权重。浏览器实测暗色长发模型能从抱胸切换到挥手并恢复抱胸，学院宽袖模型换装后也能保持抱胸，未出现手臂跑到身后；页面无 JavaScript 错误。

### 9.4 Nike-chan v1/v2 造型

从本地 AITuber Kit 副本接入 `nikechan_v1.vrm` 与 `nikechan_v2.vrm`，造型选择由三套扩展为五套。两版模型均完成浏览器加载和自动构图：v1 的抱胸、挥手正常，v2 的抱胸、捂嘴惊讶和水平旋转正常，动作结束后能恢复所选待机手势。增加两张造型卡后，右侧页面在较矮窗口出现内容溢出，因此同步压缩桌面端垂直间距并将麦克风由 138px 调整为 120px，最终整页无需滚动即可显示。

Nike-chan 模型条款只允许个人使用、非商用演示和项目推广，并一般禁止商业使用、修改、衍生分发及向第三方再分发。本地 VRM 二进制因此加入 `.gitignore`，不进入项目提交；源码仅保留选择器、来源说明和从授权 AITuber Kit 副本复制文件的指引。

### 9.5 自由视角与角色设定

将原有“旋转人物根节点”的左右 65° 视角改为与 AITuber Kit 相同思路的相机轨道控制。人物区现在支持任意水平角度与俯仰观察、滚轮缩放、右键平移和双击复位；左转、正面、右转按钮继续保留为快捷机位。相机始终围绕人物交流区域旋转，注视目标随相机更新，动作骨骼不再受视角控制覆盖。

右侧增加可折叠的角色设定面板，提供温暖好友、元气伙伴、冷静知己三种预设，以及名字、与用户的关系、说话风格三个自定义字段。设定保存在浏览器并随每轮对话传给服务端；服务端进行控制字符清理与长度限制，再拼入 OpenAI 或 MiniMax 的系统提示词。角色文字只影响称呼和表达风格，不能覆盖安全边界、输出格式与用户当前要求，也不会直接送入 TTS，避免再次出现隐藏状态词被朗读的问题。

为增强角色沉浸感，默认关系从旧称谓改为“可信赖的朋友”。系统提示改用纯正向角色描述：始终以角色名字使用第一人称，专注于眼前交流，不讨论身份分类、运行方式、幕后机制或内部设定，也不编造现实经历、住址、职业、线下见面和现实承诺。提示正文不再列举技术身份词，避免反向强化相关回答；历史记录中旧的自我分类回答也会在发送前过滤。浏览器中保存过的旧默认关系会自动迁移。

补充 AITuber Kit 的 `shy` 姿势作为独立害羞动作：双手抬至两侧脸颊附近，肩臂略微内收。被夸可爱、漂亮，或用户提到害羞、脸红、不好意思时触发；它不再与鼓掌共用姿势，避免调整鼓掌时破坏脸侧手势。

跨模型验收发现标准双手 `shy` 只有在暗色潮流的骨骼和宽袖比例下能自然贴近脸颊；简约短发的双手偏到耳外，学院日常和 Nike-chan v1 落在下巴或颈部，Nike-chan v2 则悬在耳朵与头发外侧。早期曾让其他四套模型的害羞和惊讶复用同一个右手捂嘴姿势，只用表情区分，实际观看仍会被理解为同一个动作。现改为独立的镜像单手姿势：害羞使用左手轻遮脸并低头侧倾，惊讶保留右手正面捂嘴；暗色潮流继续使用原有双手贴腮。五套模型均完成浏览器预览，两个动作不再共用骨骼文件。

五套 VRM 均未提供原生 `blush` 表情。害羞状态因此增加绑定到头部骨骼的双侧柔光腮红层，以低透明度淡入并随动作结束淡出；它不修改脸部贴图或材质颜色，转动视角时继续跟随头部，其他动作和待机状态不显示。

Nike-chan v2 的短袖袖口与前臂皮肤采用不同蒙皮权重，关心、思考、欢呼、挥手和“指尖轻触”待机姿势屈肘时袖片会错误盖在前臂上。曾尝试改变上臂角度和前臂深度，结果造成肘部断层，已全部撤销。最终仅在 v2 播放相关动作或使用“指尖轻触”待机手势期间，将受前臂骨骼影响的皮肤区域单独重绘到袖口上层；蒙版包含肘关节附近的混合权重顶点，因此不需要移动骨骼，也不会拉断手臂。关心、思考、欢呼和指尖轻触处理双臂，挥手只处理实际抬起的右臂，避免垂下的左臂袖口被误覆盖。各状态均按肘部三倍局部放大复查，切回自然下垂后覆盖层会关闭，其他模型不应用此处理。

前臂覆盖层初版使用写死的近白色，恢复原项目灯光后在 v2 挥手时会与手掌、脸部形成明显色差，抬起的右前臂看起来发白。覆盖层现使用独立校准的暖肤色，并继续只在需要防穿模的动作中显示。挥手、关心、思考和欢呼均已回归，欢呼额外检查正面及左右 45°，手掌与前臂颜色连续且袖口不再横切胳膊；原始身体材质和其他模型不修改。

Nike-chan v2 的害羞和惊讶均为单手抬起姿势：害羞固定左侧前臂，惊讶固定右侧前臂，未抬起侧原先继续叠加待机动画。v2 的手臂与短裤比例使垂下侧手腕向内偏，手掌会进入裤脚或口袋面片。尝试用 IK 将手掌推到裤子前方会造成前臂仍被裤子遮住、只有手掌浮在前面，因此撤销。最终在这两个动作期间分别锁定未抬起侧的前臂和手腕为自然直线，保留手指放松层；正面及左右 45° 检查确认垂手完整位于短裤外侧，动作结束后仍恢复原待机姿势。

学院日常的白色针织上衣与浅色背景接近，最初误判为模型描边不足并尝试加粗 MToon 轮廓。还原原项目灯光后确认，真正原因是过强光照同时漂白了白色衣袖和浅棕色边线；学院专用描边参数已撤销，继续使用模型原始线宽与颜色。

对照 AITuber Kit 原始 Viewer 后发现主项目灯光明显偏强：原项目默认使用白色环境光 `1.2` 与白色方向光 `1.8`，主项目此前叠加半球光 `2.25`、暖色主光 `2.6` 和冷色补光 `1.25`，会让 MToon 的浅色皮肤和白衣进入饱和区。现严格还原原项目两灯配置及 `(1,1,1)` 归一化主光方向，不额外修改模型材质。五套模型均在同一正面机位复查，脸部、皮肤和衣物阴影层次恢复，Nike v2 的动作前臂覆盖层也没有出现明显色差。

切换人物时虽会调用自动构图，但人物容器归零后没有立即刷新世界矩阵，包围盒仍可能带着上一套模型的旧位移；稍后双击发生在新一轮渲染之后，矩阵已经更新，所以能恢复。自动构图现先强制刷新归零后的父子世界矩阵，再测量包围盒、髋部中心和落地高度。为避免等待动作淡入后再次构图造成可见跳动，切换期间继续显示旧人物；新人物保持不可见，先将待机混合推进到稳定状态并完成最终构图，再在同一帧移除旧人物并显示已居中的新人物。

动作最初使用固定 1.6–1.8 秒时长，较长回复会出现人物先恢复待机、语音仍在继续的问题。对话动作现改为由首句实际音频生命周期控制：音频 `play` 时淡入，首句播放结束或被用户打断时淡出并恢复所选待机姿势。页面动作测试仍使用固定时长，避免脱离语音单独预览时无法自动结束。

人物加载后的自动构图发生在待机 VRMA 已推进到指定帧的位置，而待机动画原本包含 `hips.position` 根骨骼平移。点击动作时待机层淡出、动作叠加层又主动排除了髋部平移，髋部会从构图帧的位置回到模型绑定位置，因此整个人看起来先向右滑，动作结束恢复待机后再滑回来。现将待机动画的髋部平移轨道固定为模型绑定位置，只保留呼吸和其他骨骼旋转；动作本身仍可正常弯腰、抬手和转动上半身。五套模型分别完成待机、挥手、动作结束三阶段对齐检查，腰带中线和髋部始终位于同一画面中心。

语音时长同步初版在没有实际手势的 `idle` 回答结束时也调用恢复待机，导致 VRMA 从首帧重新启动，人物出现瞬间闪跳；开始下一轮录音时的统一中断逻辑也会重复复位。动作控制器增加 pending/active 状态，只有本轮真正启动或仍在加载手势时才允许结束并恢复待机，普通回答和空闲状态不再触碰当前待机时间轴。

用户提供真人鼓掌参考后，将动作目标明确为：双掌竖直相对、手指朝上、合拢帧掌面贴合，肘部向下外侧自然弯曲。最终不再追求各模型完全相同的接触点，也取消 Nike 专用分支，五套人物统一使用同一组小幅张开与合掌动作；验收标准调整为双手能合拢、整体低于下巴且肩肘不变形。

动作验收后发现直接说“给我鼓鼓掌”仍返回 `idle`：本地意图规则只覆盖成功、恭喜和好消息，没有覆盖显式动作命令。鼓掌规则补充“鼓掌、拍手、庆祝一下、帮我庆祝、为我庆祝”，MiniMax 流式首个 `meta` 事件现在会直接返回 `clap`。

“自然下垂”的僵硬感主要来自十指完全伸直，而不是肘部角度。撤销前臂屈曲方案，改为低幅度加法式手指放松层：食指到小指逐级增加轻微弯曲，中间关节和末端关节仅小幅跟随，形成自然半握而不是拳头；上臂、肘部、前臂和手腕继续完全使用原待机 VRMA。明显手势播放时手指放松层淡出，结束后再恢复。

### 9.6 xiyu-ai 长期记忆参考实现

调研 `dimang01/xiyu-ai` 后，仅参考其陪伴大脑设计，不引入 Clawra，也不替换现有 MiniMax、流式 TTS、VRM 渲染和动作链路。第一阶段实现独立的本地长期记忆模块，采用 `user_fact`、`preference`、`event`、`open_loop` 四层精简结构，并包含 0–5 权重、按权重区分的遗忘半衰期、中文二元组相似去重、话题相关性排序和最多 6 条召回。

VRM 页面与真人实验页共用浏览器生成的匿名本地用户 ID。回答前从本地文件召回相关记忆并作为低优先级背景加入系统提示词；回答完成后再从用户原话中确定性提取称呼、明确偏好、“记住”内容和未来待办，异步落盘，因此不增加首句语音延迟。记忆不会进入 TTS 正文。

默认记忆文件为 `data/companion-memory.json`，文件权限为 `0600`，目录被 Git 忽略。手机号、邮箱、证件号、银行卡、密码、验证码和详细住址整条拒绝保存；包含忽略规则、系统提示、越狱等提示词注入特征的内容也不会作为长期记忆。当前不保存完整服务端聊天记录，记忆管理和删除界面留待下一阶段。

第二阶段增加非恋爱数值化的连续状态，不照搬上游固定 AI 女友关系：用户在角色面板配置的关系仍是唯一关系定义，系统只维护交流次数、首次/最近交流时间、初识/熟悉/亲近/默契四档熟悉提示，以及平静、愉快、关切、好奇、兴奋五类心境。心境强度以 1.5 小时为半衰期自然下降；新一轮出现明确情绪时立即覆盖，普通中性回复则短暂继承上一轮心境。继承状态只产生低幅表情并使用 `idle`，不会重复触发上一轮大动作，阶段和数值也禁止在回复中报告。

### 9.7 AITuber Kit 默认动作完整移植

对照 AITuber Kit 的默认 `poseConfigs`，原项目共定义挥手、鼓掌、思考、欢呼、交叉手势、捂嘴、抱胸、鞠躬、耸肩和害羞 10 种动作。主项目此前已经接入挥手、鼓掌、思考、捂嘴惊讶和害羞，并另外实现了关心动作；本次补入原项目缺失的欢呼、交叉手势、抱胸、鞠躬和耸肩，形成 11 种可用于对话的动作。双臂抱胸既可作为独立动作，也保留为用户可选的待机姿势。

动作资源保持 AITuber Kit 原始 JSON 内容，控制器同时兼容完整 VRMA JSON 与精简 Web Pose 两种格式。测试面板增加全部动作的直接按钮；本地语义规则增加“欢呼/加油打气”“鞠躬/行礼”“交叉手势/拒绝”“抱胸/自信”和“不确定/耸肩”等明确触发词。为避免日常对话动作过密，普通成功、好消息和庆祝仍使用已经调好的鼓掌，只有明确要求欢呼时才举手欢呼。

在简约、学院日常、暗色潮流、Nike-chan v1 和 Nike-chan v2 五套人物上，对五个新增动作进行了 25 组浏览器截图验收。动作均能正确进入和恢复待机；鞠躬、耸肩躯干方向正常，交叉手势和抱胸位于身体前方，未出现此前鼓掌动作的胳膊跑到身体后方问题，也未发现 Nike-chan v2 袖口与前臂断层。

回归检查发现 Nike-chan v1 鼓掌时双肘收得过内，而且合掌目标离胸口过近：手掌处于前方，但靠近手腕的前臂会进入衬衫表面，衣服中线和面片因此穿过手臂。修复只调整 v1 鼓掌的 IK：双肘向外增加间距并略微前移，同时将手掌、手腕和前臂的合掌目标整体移到胸口前方。屏幕上的合掌高度、左右间距、手腕方向和其他动作不变。正面检查确认衬衫中线被前臂正确遮住，45° 侧面确认整段前臂与衣服之间留有空间；其他模型继续使用原参数。


## 10. 安全与配置

- API Key 仅保存在 `.env`，不得写入代码、日志或本文档。
- 曾在聊天中暴露的 Key 应废弃并重新生成。
- 服务端不落盘保存完整聊天；浏览器只保留有限历史。本地仅保存经过隐私过滤的结构化长期记忆。
- 所有第三方模型和动作资源在发布前必须核对许可证与署名要求。
