# 露米数字人项目：对话记录与实验日志

更新时间：2026-08-07

## 1. 项目目标

制作一个语音优先的虚拟好友。用户直接说话，AI 理解上下文后用自然中文和女性声音回答；人物口型应与语音匹配，眼神、表情、头部和手势应克制、连贯并与语义一致。

目标不是一张静态图片加开合嘴，而是具备以下完整状态：倾听、思考、准备开口、说话、短暂反应、恢复待机和被用户打断。

## 2. 对话中确认的产品要求

- 以语音交流为主，不把文字聊天作为主要入口；字幕默认隐藏。
- 可以使用 MiniMax，不要求 OpenAI API Key。
- 使用女性声音，目前为 MiniMax `female-tianmei`。
- 人物不能持续左右晃动、左右扫视或一直露出夸张表情。
- 待机应稳定，以自然眨眼、轻微呼吸和眼神交流为主。
- 口型不能只按音量机械开合，长期目标是音素或 viseme 级同步。
- 表情和动作必须与语义相关，但不能每句话都触发动作。
- 如果真人视频难以达到自然效果，可以接受动漫风格。

## 3. 技术路线调研

### 3.1 商业实时数字人

调研过 HeyGen LiveAvatar 和 Tavus。优点是人物真实、实时链路完整；缺点是持续费用、平台依赖和自定义控制受限。本项目以个人实验为主，因此没有作为当前主路线。

### 3.2 DH_live

项目：`kleinlee/DH_live`

已经使用用户下载的 `epoch_40_new.pth` 完成 DH_live Mini 预处理和网页端渲染。它适合从静默人物视频生成音频驱动口型，浏览器端资源较轻，但主要改善嘴部区域，无法自动解决全脸协调、眼神和自然手势。

生成物位于：

- `resources/models/DINet_mini/epoch_40_new.pth`
- `public/dh-live/`
- `public/dh-live/actions/`

### 3.3 LivePortrait

项目：`KlingAIResearch/LivePortrait`

用于离线生成眼神、眨眼和微表情素材，再交给 DH_live 处理口型。为了避免表情驱动影响嘴唇，实验 checkout 增加了 `exp_no_lip` 区域；补丁保存在 `resources/liveportrait/exp-no-lip.patch`。

成功生成 `happy`、`caring`、`thinking`、`surprise` 等状态，均通过 DH_live 的“源视频无明显说话”质量检查。

### 3.4 其他项目

- `kleinlee/MatesX`：与 DH_live 生态相关，但没有解决现有真人素材的动作自然度问题。
- `yangkang2021/I_am_a_person`：提供了可参考的组合思路，但不是当前浏览器端的直接替换方案。
- `anliyuan/Ultralight-Digital-Human`：轻量口型路线有参考价值，但同样不能自动提供自然的全身行为。
- `duixcom/Duix-Mobile`：移动端本地 2D 数字人 SDK，支持 PCM 流、打断和预定义动作区间。它适合 Android/iOS，但动作幅度主要由模型内的素材决定，网页端不能直接接入。
- `lipku/LiveTalking`：已检查提交 `c963ad4`。它的视频拆帧、人脸框平滑、Avatar 任务接口和配置化动作管理值得借鉴；但自定义动作默认在非说话状态播放并可绑定独立音频，不能直接满足“动作与回答同时发生”。详细结论见 `docs/LIVETALKING_REFERENCE.md`。

参考实现后新增项目自己的真人动作包工具，不引入 LiveTalking 的 CUDA 推理。`scripts/prepare_dh_action.mjs` 在 Mac 上调用固定版本 DH_live，自动完成视频检查、关键点检测、源视频说话检查、嘴部区域打包、与待机画面对齐检查及动作清单登记。使用原微笑素材端到端重建得到 55 帧，生成视频哈希和逐帧区域均与已部署包一致。DH_live 上游的 Windows 专用 `CREATE_NO_WINDOW` 调用通过 `integrations/dh-live/macos-preprocess.patch` 做最小兼容修复。

## 4. 真人素材实验

### 4.1 人物与动作素材

使用 Mixkit 43811 候选视频切分出：

- `idle`
- `smile`
- `wave_approval`
- `shrug`
- `confident_arms_crossed`

动作清单和映射保存在 `resources/candidates/mixkit-43811/action-manifest.json`。

### 4.2 持续晃动

最初将动作视频循环作为待机，导致人物身体持续摇晃。后来改为稳定片段和一次性动作，动作结束后返回 `idle`。

结论：明显身体动作不能循环；待机必须单独制作。

### 4.3 眼睛持续左右看

第一版 LivePortrait 待机使用官方 `d0.mp4` 的眼睛驱动，继承了真人反复左右扫视。MediaPipe 测得眼球水平范围约 `0.2200`。

后来从同人物低强度表情片段中选取正视且包含完整眨眼的 1.8 秒区间，眼球水平范围降到约 `0.0534`，减少约 76%。当前部署待机为：

- `resources/liveportrait/output/idle-centered-blink.mp4`
- `resources/liveportrait/prepared/idle-centered/`

### 4.4 默认露齿

原始人物源帧本身是露齿微笑。尝试用图像编辑生成自然合唇源图，再通过 LivePortrait 和 DH_live 重建：

- `resources/liveportrait/source-centered-closed-mouth.png`
- `resources/liveportrait/prepared/idle-closed-mouth/`

闭嘴成功，但人物脸部、构图和原视频存在可见差异。为了保持同一人物的一致性，闭嘴实验被保留但未部署，当前仍使用原人物待机。

结论：真人视频路线中，源素材决定了外观上限。对嘴部做生成式修改容易破坏身份和画面一致性。

## 5. 对话和语音链路演进

### 5.1 第一版

流程为：等待用户说完 → 请求完整 MiniMax 回复 → 请求完整 TTS → 切换动作 → 播放语音。问题是等待时间长、动作突然切换、回复字段可能污染朗读正文。

### 5.2 文案字段污染

最初要求 MiniMax 同时输出 `reply`、`emotion` 和 `action` JSON。模型格式稍有变化时，内部状态词可能进入正文。

当前改为：

- MiniMax 只生成可以直接朗读的中文正文。
- 服务端删除 `<think>`、Markdown、JSON 和内部状态标签。
- 情绪与动作由本地程序分析，不交给 TTS。
- TTS 永远只接收清理后的 `reply`。

### 5.3 当前流式版本

当前流程：

```text
浏览器语音识别
  → MiniMax 流式回答
  → 服务端隔离 reasoning 并按句切分
  → 第一条完整短句立即请求 TTS
  → 后续短句进入可打断播放队列
  → 动作切换与语音生成并行
  → DH_live 接收 WAV 驱动口型
```

真实测试中 MiniMax 首句约 2.4 秒到达；MiniMax Speech 2.8 返回 16 kHz、16-bit、单声道 WAV。用户再次开口时会取消模型流、TTS 队列、当前音频和口型。

相关实现：

- `server.mjs`
- `src/companion.mjs`
- `public/app.js`
- `scripts/live_smoke.mjs`

## 6. 已确认的问题与经验

1. 口型、表情和动作不能由互不相关的模型同时争夺同一面部区域。
2. 预制真人动作视频可以用于验证，但切片间身份、光照和姿态很难连续。
3. “动作越多越自然”是错误方向。自然感来自稳定基线、低幅度变化和正确时机。
4. 不应让 LLM 每句话选择一个动作；行为调度需要冷却时间、动作预算和互斥规则。
5. 文案正文和控制元数据必须彻底分离。
6. 流式 LLM 只能降低文本等待；真正自然还需要流式 ASR/VAD、流式 PCM TTS 和音素时间戳。

## 7. 决策：开发 VRM 动漫数字人

真人视频路线暂时保留用于对照，不再继续投入大量时间修补素材。新路线采用网页 3D VRM：

- VRoid/VRM 人物保持统一身份和画面风格。
- `three.js` 与 `@pixiv/three-vrm` 负责浏览器渲染。
- VRM 表情权重控制微笑、眨眼和口型。
- 标准骨骼动画控制头部和手势，可设置低权重并平滑混合。
- 当前 MiniMax、流式聊天、TTS 和中断机制继续复用。

行为规则初版：

- 眼睛大部分时间正视用户，视线变化小于约 5°。
- 待机只有呼吸、眨眼和非常轻微的重心变化。
- 短回答不触发手势。
- 每轮最多一个明显手势，两个明显手势至少间隔 3 秒。
- 普通表情强度为 0.15–0.35。
- 动作以 300–700 毫秒淡入淡出。
- 首批只实现轻微点头、轻微侧头思考、小幅微笑和首次问候四种行为。

## 8. VRM 服饰与发型切换实验

2026-08-04 增加三套完整造型预设：简约短发黑白装、齐肩短发针织开衫、紫色长发黑粉街头装。实现采用整套 VRM 切换，而不是运行时拼装衣服和头发：

- 新模型完整解析后才替换旧模型，避免切换时画面闪空。
- 旧模型从场景移除后释放几何体、材质和纹理，避免反复换装造成内存累积。
- 每套造型复用相同的闭嘴待机、眨眼、注视、表情、口型和低幅手势系统。
- 当前造型保存在浏览器，下次打开自动恢复。
- 两套 VRoid 官方样例并非 CC0，具体使用条件单独记录在 `public/vrm/THIRD_PARTY.md`。

浏览器实测三套人物均可加载，换装后手臂自然下垂，镜头构图和表情骨骼正常。

动作联调时发现骨骼动作最初没有播放：调度器使用 `performance.now()`，动画混合使用 `THREE.Clock.elapsedTime`，不同时间轴使动作权重始终为 0。统一改用人物动画时钟后恢复正常；随后通过浏览器逐帧截图把挥手调整为肩部抬起、肘部弯曲、手掌停留在头侧的可见幅度。页面增加折叠的“动作测试”面板，用于把骨骼问题与语音场景判断问题分开验证。用户实测后将动作冷却由 8 秒缩短为 3 秒，并扩展日常口语触发词。

待机手臂最初仍接近完全伸直。后续将默认姿势调整为左右略不对称的轻微屈肘、前臂向身体内侧、手腕轻微偏转，并给四指加入 4–7° 的自然弯曲；动作结束后通过阻尼平滑回到该放松姿势。

“我饿了”实测时接口已正确返回 `caring`，但原关心动作只有约 4° 的头部变化，用户感知为没有触发。浏览器截图验收后将其改为持续约 1.45 秒的温和低头、颈部跟随和轻微上身前倾，并校正了 VRM 骨骼 X 轴的正负方向。

庆祝场景最初复用了挥手。后续将问候与庆祝拆分：问候继续使用 `wave_approval`，成功、完成、录取、好消息和恭喜改用 `clap`。鼓掌采用双臂前移、肘部弯曲、双手在胸腹前靠近并小幅周期运动的轻拍手动作；为兼容不同 VRM 手型，没有强制手腕大角度翻转，以避免拇指和掌面穿模。

惊讶动作由单纯抬头改为右手轻捂嘴、头部轻微后仰并叠加低强度惊讶表情。固定欧拉角在不同 VRM 骨骼朝向下会让手落到头侧或画面外，因此改为上臂、前臂两段骨骼迭代追踪嘴前的世界坐标。浏览器中间帧检查确认手掌覆盖嘴部，动作结束后平滑回到放松姿势。

默认站姿进一步改为双手在小腹前交叉下垂，手腕轻叠、手指朝下，替代双臂垂在身体两侧的僵直观感。关心动作改为双手从下方抬至胸前偏上，双腕交叉、手指向上，形成较柔和的祈祷姿势，同时保留轻微低头与上身前倾。两种姿势均使用双臂世界坐标追踪，动作结束后自动回到默认交叠姿势。

后续跨模型复测发现默认双手重叠过深会造成手腕扭曲，鼓掌的固定骨骼角度在部分服装模型上会让手臂折到身体后方。默认姿势改为一只手轻搭另一只手腕、前后略微错层；鼓掌改为胸前世界坐标目标，两只竖直手掌小幅开合，不再依赖各模型不同的固定欧拉角。惊讶动作时长和表情强度提高，并补充“哇、真的吗、我的天、怎么可能、太夸张、吓我一跳”等口语触发词。简约和学院两套 VRM 均完成浏览器中间帧验收。

继续验收发现默认搭手姿势仍无法兼容不同袖宽和手臂比例：无袖模型可接受时，宽袖模型会发生手腕穿插；拉开目标点又会导致掌心朝上。最终取消默认双手 IK，恢复双臂自然下垂、肘部轻微放松、手指轻曲的稳定待机姿势。双手合拢仅用于短时的关心和庆祝动作。宽袖与无袖两套模型均完成静态帧复测。

## 9. AITuber Kit 动作系统对照实验

2026-08-05 将 AITuber Kit v2.70.0 解压到 `experiments/aituber-kit`，使用工作区 Node 24 安装依赖，并在 3420 端口独立启动，不覆盖现有 3417 服务。上游采用自定义非商用许可证，个人非商用实验可免费使用；安装审计报告包含 19 个上游依赖漏洞，因此当前仅作为本地效果验证，不直接并入主项目。

实现检查表明，它的待机使用标准 `idle_loop.vrma`，而 think、cheer、mouth_cover、wave、clap 等动作使用预制 JSON 姿势；wave 和 clap 通过多姿势序列播放，分别以约 0.5 秒和 0.2 秒切换。浏览器开启内置姿势调试后，实测结果如下：

- 默认人物的挥手包含手臂、手腕和表情配合，明显优于单个程序角度。
- 捂嘴姿势能准确覆盖嘴部，手肘方向稳定。
- 鼓掌在张开与合拢姿势间循环，手掌接触和手腕朝向自然。
- 切换到与当前项目学院人物同源的 `AvatarSample_A` 后，捂嘴和鼓掌仍然成立，说明预制规范化姿势的跨模型稳定性好于当前简易 IK。

阶段结论：AITuber Kit 的效果值得借鉴，优先移植其 VRMA 待机播放器、姿势 JSON 格式、姿势序列和动作淡入淡出；现有 MiniMax、语音和业务页面可继续保留，不必整体替换。

### 9.1 主项目迁移结果

随后将动作层接入 3417 主项目，而不是继续依赖 AITuber Kit 的完整页面：

- 使用 Pixiv 官方 `@pixiv/three-vrm-animation` 播放 `idle_loop.vrma`。
- 新增兼容 AITuber Kit 两种 JSON 姿势格式的解析器；挥手和思考使用完整 VRM Animation JSON，鼓掌、关心和捂嘴使用 Web Pose JSON。
- 挥手与鼓掌按多帧姿势循环，其他姿势短暂保持；所有动作以约 350 毫秒淡入淡出，并在 1.6–1.8 秒后自动回到待机。
- 关心采用低头、双手指尖相触的低幅动作；惊讶采用单手捂嘴；不再使用跨模型容易穿模的运行时手臂 IK。
- MiniMax 文案、流式 TTS、口型和 3 秒动作冷却逻辑保持不变。

浏览器逐帧验收覆盖三套 VRM。简约人物的挥手、鼓掌、关心、惊讶均能正确显示；学院人物的捂嘴位置正确；暗色长发人物的关心和思考动作未出现手臂跑到身后，动作结束后能恢复双臂自然下垂。页面无 JavaScript 错误。动作资源的非商用限制和来源记录在 `public/vrm/motions/THIRD_PARTY.md`。

首次接入时，动作在流式接口的 `meta` 事件到达后立即开始，而第一句语音还要等待 TTS 生成，导致短动作往往在声音开始前已经完成。随后将动作触发点移到首段音频真实触发 `play`/浏览器语音 `start` 的时刻：等待语音期间只更新低幅面部情绪，第一句开口与当轮唯一手势同步开始，后续分句不重复触发动作。

### 9.2 人物观看角度

参考 AITuber Kit 的人物视角控制，主页面增加水平旋转：人物区域支持鼠标或触摸左右拖动，并提供左转、正面、右转三个可见按钮，双击人物恢复正面。旋转采用阻尼过渡并限制在左右 65°，避免人物完全背对用户。实现对 VRM 根节点的原始朝向叠加视角偏移，因此同时兼容 VRM 0.x/1.0，且不会覆盖标准骨骼动作。浏览器实测暗色长发模型在左右侧身时待机、视线和挥手动作均正常。

旋转初版直接使用 VRM 文件根节点，部分模型会因自身原点和几何外框不对称而在侧转时横向漂移。后续增加独立外层旋转轴，以髋部骨骼作为身体中线；待机 VRMA 首帧应用后再次校准构图，消除动画髋部位移造成的偏左。相机距离由人物高度的 1.23 倍调整为 1.4 倍，在保持上半身交流构图的同时给头顶留出余量。暗色长发和学院两套模型已完成正面、侧面截图验收。

### 9.3 可切换待机手势

默认手部姿势增加三种用户预设：自然下垂、指尖轻触和双臂抱胸。非自然姿势使用规范化 Pose JSON 持续保持，并叠加去除髋部位移的低权重 VRMA 呼吸；选择保存在浏览器。对话触发挥手、鼓掌等明显动作时，待机手势先淡出，动作结束后显式恢复原待机动作及权重。浏览器实测暗色长发模型能从抱胸切换到挥手并恢复抱胸，学院宽袖模型换装后也能保持抱胸，未出现手臂跑到身后；页面无 JavaScript 错误。

### 9.4 Nike-chan v1/v2 造型

从本地 AITuber Kit 副本接入 `nikechan_v1.vrm` 与 `nikechan_v2.vrm`，造型选择由三套扩展为五套。两版模型均完成浏览器加载和自动构图：v1 的抱胸、挥手正常，v2 的抱胸、捂嘴惊讶和水平旋转正常，动作结束后能恢复所选待机手势。增加两张造型卡后，右侧页面在较矮窗口出现内容溢出，因此同步压缩桌面端垂直间距并将麦克风由 138px 调整为 120px，最终整页无需滚动即可显示。

Nike-chan 模型条款只允许个人使用、非商用演示和项目推广，并一般禁止商业使用、修改、衍生分发及向第三方再分发。本地 VRM 二进制因此加入 `.gitignore`，不进入项目提交；源码仅保留选择器、来源说明和从授权 AITuber Kit 副本复制文件的指引。

### 9.5 自由视角与角色设定

将原有“旋转人物根节点”的左右 65° 视角改为与 AITuber Kit 相同思路的相机轨道控制。人物区现在支持任意水平角度与俯仰观察、滚轮缩放、右键平移和双击复位；左转、正面、右转按钮继续保留为快捷机位。相机始终围绕人物交流区域旋转，注视目标随相机更新，动作骨骼不再受视角控制覆盖。

右侧增加可折叠的角色设定面板，提供温暖好友、元气伙伴、冷静知己三种预设，以及名字、与用户的关系、说话风格三个自定义字段。设定保存在浏览器并随每轮对话传给服务端；服务端进行控制字符清理与长度限制，再拼入 OpenAI 或 MiniMax 的系统提示词。角色文字只影响称呼和表达风格，不能覆盖安全边界、输出格式与用户当前要求，也不会直接送入 TTS，避免再次出现隐藏状态词被朗读的问题。

为增强角色沉浸感，默认关系从旧称谓改为“可信赖的朋友”。系统提示改用纯正向角色描述：始终以角色名字使用第一人称，专注于眼前交流，不讨论身份分类、运行方式、幕后机制或内部设定，也不编造现实经历、住址、职业、线下见面和现实承诺。提示正文不再列举技术身份词，避免反向强化相关回答；历史记录中旧的自我分类回答也会在发送前过滤。浏览器中保存过的旧默认关系会自动迁移。

补充 AITuber Kit 的 `shy` 姿势作为独立害羞动作：双手抬至两侧脸颊附近，肩臂略微内收。被夸可爱、漂亮，或用户提到害羞、脸红、不好意思时触发；它不再与鼓掌共用姿势，避免调整鼓掌时破坏脸侧手势。

跨模型验收发现标准双手 `shy` 只有在暗色潮流的骨骼和宽袖比例下能自然贴近脸颊；简约短发的双手偏到耳外，学院日常和 Nike-chan v1 落在下巴或颈部，Nike-chan v2 则悬在耳朵与头发外侧。早期曾让其他四套模型的害羞和惊讶复用同一个右手捂嘴姿势，只用表情区分，实际观看仍会被理解为同一个动作。现改为独立的镜像单手姿势：害羞使用左手轻遮脸并低头侧倾，惊讶保留右手正面捂嘴；暗色潮流继续使用原有双手贴腮。五套模型均完成浏览器预览，两个动作不再共用骨骼文件。

五套 VRM 均未提供原生 `blush` 表情。害羞状态因此增加绑定到头部骨骼的双侧柔光腮红层，以低透明度淡入并随动作结束淡出；它不修改脸部贴图或材质颜色，转动视角时继续跟随头部，其他动作和待机状态不显示。

Nike-chan v2 的短袖袖口与前臂皮肤采用不同蒙皮权重，关心、思考、欢呼、挥手和“指尖轻触”待机姿势屈肘时袖片会错误盖在前臂上。曾尝试改变上臂角度和前臂深度，结果造成肘部断层，已全部撤销。最终仅在 v2 播放相关动作或使用“指尖轻触”待机手势期间，将受前臂骨骼影响的皮肤区域单独重绘到袖口上层；蒙版包含肘关节附近的混合权重顶点，因此不需要移动骨骼，也不会拉断手臂。关心、思考、欢呼和指尖轻触处理双臂，挥手只处理实际抬起的右臂，避免垂下的左臂袖口被误覆盖。各状态均按肘部三倍局部放大复查，切回自然下垂后覆盖层会关闭，其他模型不应用此处理。

前臂覆盖层初版使用写死的近白色，恢复原项目灯光后在 v2 挥手时会与手掌、脸部形成明显色差，抬起的右前臂看起来发白。覆盖层现使用独立校准的暖肤色，并继续只在需要防穿模的动作中显示。挥手、关心、思考和欢呼均已回归，欢呼额外检查正面及左右 45°，手掌与前臂颜色连续且袖口不再横切胳膊；原始身体材质和其他模型不修改。

Nike-chan v2 的害羞和惊讶均为单手抬起姿势：害羞固定左侧前臂，惊讶固定右侧前臂，未抬起侧原先继续叠加待机动画。v2 的手臂与短裤比例使垂下侧手腕向内偏，手掌会进入裤脚或口袋面片。尝试用 IK 将手掌推到裤子前方会造成前臂仍被裤子遮住、只有手掌浮在前面，因此撤销。最终在这两个动作期间分别锁定未抬起侧的前臂和手腕为自然直线，保留手指放松层；正面及左右 45° 检查确认垂手完整位于短裤外侧，动作结束后仍恢复原待机姿势。

学院日常的白色针织上衣与浅色背景接近，最初误判为模型描边不足并尝试加粗 MToon 轮廓。还原原项目灯光后确认，真正原因是过强光照同时漂白了白色衣袖和浅棕色边线；学院专用描边参数已撤销，继续使用模型原始线宽与颜色。

对照 AITuber Kit 原始 Viewer 后发现主项目灯光明显偏强：原项目默认使用白色环境光 `1.2` 与白色方向光 `1.8`，主项目此前叠加半球光 `2.25`、暖色主光 `2.6` 和冷色补光 `1.25`，会让 MToon 的浅色皮肤和白衣进入饱和区。现严格还原原项目两灯配置及 `(1,1,1)` 归一化主光方向，不额外修改模型材质。五套模型均在同一正面机位复查，脸部、皮肤和衣物阴影层次恢复，Nike v2 的动作前臂覆盖层也没有出现明显色差。

切换人物时虽会调用自动构图，但人物容器归零后没有立即刷新世界矩阵，包围盒仍可能带着上一套模型的旧位移；稍后双击发生在新一轮渲染之后，矩阵已经更新，所以能恢复。自动构图现先强制刷新归零后的父子世界矩阵，再测量包围盒、髋部中心和落地高度。为避免等待动作淡入后再次构图造成可见跳动，切换期间继续显示旧人物；新人物保持不可见，先将待机混合推进到稳定状态并完成最终构图，再在同一帧移除旧人物并显示已居中的新人物。

动作最初使用固定 1.6–1.8 秒时长，较长回复会出现人物先恢复待机、语音仍在继续的问题。对话动作现改为由首句实际音频生命周期控制：音频 `play` 时淡入，首句播放结束或被用户打断时淡出并恢复所选待机姿势。页面动作测试仍使用固定时长，避免脱离语音单独预览时无法自动结束。

人物加载后的自动构图发生在待机 VRMA 已推进到指定帧的位置，而待机动画原本包含 `hips.position` 根骨骼平移。点击动作时待机层淡出、动作叠加层又主动排除了髋部平移，髋部会从构图帧的位置回到模型绑定位置，因此整个人看起来先向右滑，动作结束恢复待机后再滑回来。现将待机动画的髋部平移轨道固定为模型绑定位置，只保留呼吸和其他骨骼旋转；动作本身仍可正常弯腰、抬手和转动上半身。五套模型分别完成待机、挥手、动作结束三阶段对齐检查，腰带中线和髋部始终位于同一画面中心。

语音时长同步初版在没有实际手势的 `idle` 回答结束时也调用恢复待机，导致 VRMA 从首帧重新启动，人物出现瞬间闪跳；开始下一轮录音时的统一中断逻辑也会重复复位。动作控制器增加 pending/active 状态，只有本轮真正启动或仍在加载手势时才允许结束并恢复待机，普通回答和空闲状态不再触碰当前待机时间轴。

用户提供真人鼓掌参考后，将动作目标明确为：双掌竖直相对、手指朝上、合拢帧掌面贴合，肘部向下外侧自然弯曲。最终不再追求各模型完全相同的接触点，也取消 Nike 专用分支，五套人物统一使用同一组小幅张开与合掌动作；验收标准调整为双手能合拢、整体低于下巴且肩肘不变形。

动作验收后发现直接说“给我鼓鼓掌”仍返回 `idle`：本地意图规则只覆盖成功、恭喜和好消息，没有覆盖显式动作命令。鼓掌规则补充“鼓掌、拍手、庆祝一下、帮我庆祝、为我庆祝”，MiniMax 流式首个 `meta` 事件现在会直接返回 `clap`。

“自然下垂”的僵硬感主要来自十指完全伸直，而不是肘部角度。撤销前臂屈曲方案，改为低幅度加法式手指放松层：食指到小指逐级增加轻微弯曲，中间关节和末端关节仅小幅跟随，形成自然半握而不是拳头；上臂、肘部、前臂和手腕继续完全使用原待机 VRMA。明显手势播放时手指放松层淡出，结束后再恢复。

### 9.6 xiyu-ai 长期记忆参考实现

调研 `dimang01/xiyu-ai` 后，仅参考其陪伴大脑设计，不引入 Clawra，也不替换现有 MiniMax、流式 TTS、VRM 渲染和动作链路。第一阶段实现独立的本地长期记忆模块，采用 `user_fact`、`preference`、`event`、`open_loop` 四层精简结构，并包含 0–5 权重、按权重区分的遗忘半衰期、中文二元组相似去重、话题相关性排序和最多 6 条召回。

VRM 页面与真人实验页共用浏览器生成的匿名本地用户 ID。回答前从本地文件召回相关记忆并作为低优先级背景加入系统提示词；回答完成后再从用户原话中确定性提取称呼、明确偏好、“记住”内容和未来待办，异步落盘，因此不增加首句语音延迟。记忆不会进入 TTS 正文。

默认记忆文件为 `data/companion-memory.json`，文件权限为 `0600`，目录被 Git 忽略。手机号、邮箱、证件号、银行卡、密码、验证码和详细住址整条拒绝保存；包含忽略规则、系统提示、越狱等提示词注入特征的内容也不会作为长期记忆。当前不保存完整服务端聊天记录，记忆管理和删除界面留待下一阶段。

第二阶段增加非恋爱数值化的连续状态，不照搬上游固定 AI 女友关系：用户在角色面板配置的关系仍是唯一关系定义，系统只维护交流次数、首次/最近交流时间、初识/熟悉/亲近/默契四档熟悉提示，以及平静、愉快、关切、好奇、兴奋五类心境。心境强度以 1.5 小时为半衰期自然下降；新一轮出现明确情绪时立即覆盖，普通中性回复则短暂继承上一轮心境。继承状态只产生低幅表情并使用 `idle`，不会重复触发上一轮大动作，阶段和数值也禁止在回复中报告。

### 9.7 AITuber Kit 默认动作完整移植

对照 AITuber Kit 的默认 `poseConfigs`，原项目共定义挥手、鼓掌、思考、欢呼、交叉手势、捂嘴、抱胸、鞠躬、耸肩和害羞 10 种动作。主项目此前已经接入挥手、鼓掌、思考、捂嘴惊讶和害羞，并另外实现了关心动作；本次补入原项目缺失的欢呼、交叉手势、抱胸、鞠躬和耸肩，形成 11 种可用于对话的动作。双臂抱胸既可作为独立动作，也保留为用户可选的待机姿势。

动作资源保持 AITuber Kit 原始 JSON 内容，控制器同时兼容完整 VRMA JSON 与精简 Web Pose 两种格式。测试面板增加全部动作的直接按钮；本地语义规则增加“欢呼/加油打气”“鞠躬/行礼”“交叉手势/拒绝”“抱胸/自信”和“不确定/耸肩”等明确触发词。为避免日常对话动作过密，普通成功、好消息和庆祝仍使用已经调好的鼓掌，只有明确要求欢呼时才举手欢呼。

在简约、学院日常、暗色潮流、Nike-chan v1 和 Nike-chan v2 五套人物上，对五个新增动作进行了 25 组浏览器截图验收。动作均能正确进入和恢复待机；鞠躬、耸肩躯干方向正常，交叉手势和抱胸位于身体前方，未出现此前鼓掌动作的胳膊跑到身体后方问题，也未发现 Nike-chan v2 袖口与前臂断层。

回归检查发现 Nike-chan v1 鼓掌时双肘收得过内，而且合掌目标离胸口过近：手掌处于前方，但靠近手腕的前臂会进入衬衫表面，衣服中线和面片因此穿过手臂。修复只调整 v1 鼓掌的 IK：双肘向外增加间距并略微前移，同时将手掌、手腕和前臂的合掌目标整体移到胸口前方。屏幕上的合掌高度、左右间距、手腕方向和其他动作不变。正面检查确认衬衫中线被前臂正确遮住，45° 侧面确认整段前臂与衣服之间留有空间；其他模型继续使用原参数。

### 9.8 Duix-Mobile 真人模型验证与混合路线

在 Mac Apple Silicon 的 Android 14 ARM64 模拟器上完成 Duix-Mobile SDK 4.1.1 和官方 Lily 模型验证。Android 系统语音识别得到文字后复用现有 Node/MiniMax 后端，流式显示回答，全文调用一次 MiniMax Speech 2.8，再通过 `DUIX.startPush()`、`pushPcm()` 和 `stopPush()` 驱动本地真人口型。API Key 仍只在服务端；Android 使用 `adb reverse tcp:3417 tcp:3417` 访问本机后端。

Duix 与 VRM 只共享“对话 → TTS → 音频驱动人物”的上层链路，底层不是同一种模型。VRM 是可自由观察的 3D 网格、BlendShape 和标准骨骼，动作由 VRMA/Pose 控制；Duix 是模型包中的真人帧、遮罩和本地原生音频口型推理，人物自然运动与可触发动作取决于模型素材。它与 DH_live 的真人嘴部驱动路线更接近，但使用独立的移动端资源格式和运行时。Lily 实测 `motionRegions=[]`，因此只有模型自带的眨眼、头部与身体轻微运动，不能直接复用 VRM 骨骼动作。

音频联调曾出现句间爆音。最初误判为逐句 WAV 重启 AudioTrack 或波形拼接，于是改为全文只合成一个 WAV、单次播放；继续检查实际字节后确认根因是 MiniMax WAV 含 `LIST/INFO/ISFT` 扩展块，PCM `data` 区实际从偏移 78 开始，而 Duix 示例和早期桥接固定跳过 44 字节，将 34 字节元数据当成 PCM 播放。现按 RIFF chunk 结构遍历并定位 `data`，同时验证 PCM、16kHz、单声道和 16-bit，用户复测确认音爆消失。结论是任何 WAV 输入都不能假设固定 44 字节头。

真人混合路线不把 VRM 骨骼直接套到 Duix 画面上。第一阶段保留现有 MiniMax 语义动作分类，将 `action` 随 SSE 传到 Android；模型若提供同名或别名 `motionRegions`，在音频真正开始时触发一次，动作结束继续使用模型待机。Lily 没有动作区间时必须安全回退，不能用大幅移动整个画面伪造手势。第二阶段再使用包含微笑、点头、挥手、思考等动作区间的定制 Duix 模型或授权预录素材进行验证，并继续遵循“一轮最多一个低幅动作、与语音同步开始”的约束。

### 9.9 预录真人动作制作链路

调研 LiveTalking 后确认，它的自定义动作是在静音帧分支替换视频，可绑定动作自带音频；直接迁移会再次造成“先做动作、动作结束后才说话”。主项目因此保留 DH_live 的同一帧嘴部推理，只在动作清单中切换待机、微笑、点头等全身底片，使动作和实时 TTS 能在同一段视频帧上同时发生。详细源码对照与录制规范见 `docs/LIVETALKING_REFERENCE.md`。

新增 manifest 驱动的 DH_live 动作层，动作名、资源目录、循环方式、结束后状态和语义用途不再写死在播放器中；缺少素材的语义动作可以显式回退，且加载时检查循环引用。新增 `prepare_dh_action.mjs` 将视频检查、DH_live 两段预处理、checkpoint 准备、产物验证、与 idle 的尺寸/人脸中心/比例比较、安装和清单登记串为一条命令。使用现有 2.20 秒、1280×720、25 fps 微笑样片完成全流程回归，生成 55 帧，视频哈希与当前部署的 smile 动作完全一致。

为降低试验门槛，服务增加本地“真人动作制作”页面：选择视频后先上传到本机并用 ffprobe 检查，再启动后台生成并轮询实时日志。接口仅允许回环地址，限制视频为 120 MB 和 0.6–12 秒，不接受浏览器提交任意文件路径，生成进程也不经过 shell。浏览器端到端验证使用上述真人样片，正确显示 `1280×720 · 25.00 fps · 2.20 秒`，生成按钮只在检查通过后启用，页面无脚本错误。

### 9.12 自研洁净真人口型 MVP

为避免 DH_live/MatesX 网页运行时、预编译 WASM、数据包去 Logo 服务和素材权利之间继续产生混淆，新增完全隔离的 `profile=clean` 路线。该路线不读取 MatesX 的 JavaScript、WASM、纹理或 `combined_data.json.gz`，也不通过遮挡或修改二进制去除水印；三段湖畔 MP4 复制到 `public/clean-avatar/actions/` 后独立加载。

新增 `prepare_clean_avatar.py`，直接使用 MediaPipe 从待机、微笑和同意视频生成项目自有的 `digitalman-mouth-track` JSON。三段素材均为 768×1152、222 帧，嘴部中心、宽度、开合和旋转角零漏检。新增浏览器原生 Canvas 播放器和独立动作清单，继续兼容主页面已有的音频、清空和动作 iframe 消息协议；WAV 仍按 RIFF chunk 查找 `data`，避免固定跳过 44 字节造成音爆。

最初尝试直接绘制深色嘴腔和牙齿，放大检查发现最大开口偏黑、牙齿像白线，因此未通过。随后从同一人物的 MiniMax 张嘴原片中提取 5 档自然 RGBA 嘴形，离线羽化边缘，运行时按当前帧 MediaPipe 轨迹对齐。为保持小嘴效果，音量映射最高只使用前 4 档。浏览器分别验收待机、最大测试开口、微笑、同意和完整交互页面：人物与动作正常加载，嘴形位置稳定，画面无 MatesX 标记。架构、数据格式和许可证边界详见 `docs/CLEAN_AVATAR_ARCHITECTURE.md`。

用户实际语音复测后判定图集口型仍不可用。进一步按约 260 ms 间隔连续抽取 8 帧确认：素材的前三档开合比几乎相同，第四档突然从约 0.004 跳到 0.047，音量映射会在闭嘴和张嘴两张脸之间切换；贴片还无法随音素改变嘴角、圆唇和下颌，也会带入局部肤色与清晰度差异。该问题属于方案上限，不再通过缩放、羽化或增加插值掩盖。`profile=clean` 保留为隔离实验入口并明确标记未通过，后续改为完整人脸神经渲染和连续表情系数路线。

### 9.13 Wav2Lip256 独立真人口型验证

完成 DH_live/MatesX 源码拆解后，确认其自然效果来自音频时序特征、连续口型形变、稠密网格 warp 与 DINet 局部神经重绘，而不是嘴形图片替换。完整分析记录在 `docs/DH_LIVE_PRINCIPLE_ANALYSIS.md`。为尽快验证不依赖 MatesX WASM 和 `combined_data` 的正确方向，新增 `scripts/render_wav2lip_offline.py`，直接调用 LiveTalking 兼容的 Wav2Lip256 网络结构、独立 Wav2Lip 权重和 S3FD 人脸检测权重。

脚本读取底色视频和任意音频，按视频帧率生成 80×16 Mel 特征块；神经网络在 256×256 人脸区域连续生成与声音对应的下半脸，再用纵向和横向软遮罩只融合嘴部及下颌，保留原视频的眼睛、头发和上半脸。实现未调用 LiveTalking 的 WebRTC 页面和会写入标识的 `video2imgs()`，也未使用 MatesX JavaScript、WASM、纹理、UID 或授权字段。人脸框结果按视频内容哈希和 padding 参数缓存，首次预处理后再次生成不重复做人脸检测。

使用 `lakeside_idle_test/01.mp4` 与现有 `voice_test.wav` 生成 86 帧、768×1152、25 fps、3.44 秒 H.264/AAC 样片。六个时刻的放大检查确认嘴唇为连续神经生成，张合幅度保持小巧，上半脸未被替换，没有方形贴片边缘和 MatesX 标识；视频与音频时长仅相差约 4 ms。Apple M5 当前 PyTorch wheel 未启用 MPS，CPU 口型推理约 9 fps，因此本地版本先用于离线效果验证；对话实时化需要后续使用 Core ML/ONNX 优化或 CUDA 推理服务。Wav2Lip 及衍生权重仍按个人非商用测试使用，发布前必须重新核对模型和训练数据条款。

首个样片误用了 AITuber Kit 自带的日语 `voice_test.wav`；口型模型本身不决定语言。随后通过现有 MiniMax `speech-2.8-turbo` 和 `female-tianmei` 生成“你好呀，很高兴见到你……”中文女声，重新输出 160 帧、6.4 秒样片，音视频轨时长完全一致。进一步新增隔离入口 `?profile=wav2lip`：聊天流先完整收集一轮中文回答，只合成一次 TTS，再将 WAV 提交到仅允许本机访问的 `/api/wav2lip/render`；后端使用无 shell 参数调用独立 Python 推理器，按音频哈希缓存 MP4，前端由独立视频 iframe 播放成品音画，禁止再播放原 WAV，避免双声。相同音频第二次请求命中缓存。播放器在浏览器阻止带声自动播放时显示“点击播放回答”，不会静默退回到错误口型。

连续对话测试曾出现“只有第一句正常”：首次样片只为当时输出所需的 160 帧生成人脸框缓存，后续较长回复超过缓存时会再次启动 S3FD，而 S3FD 不接受 MPS 设备名称并异常退出。现改为首次即为整段待机视频预计算人脸框，S3FD 固定使用 CPU（仅 Wav2Lip 推理可使用 MPS/CUDA）。神经口型模式下生成失败也不再静默回退为浏览器语音，避免用户误以为视频仍在正常驱动。

CPU 性能对比显示 batch 2/4/8 分别约为 8.9/9.5/9.5 fps，batch 16 下降到约 5.6 fps；增加 CPU 线程数没有明显改善。交互模式因此改用 batch 4 和 15 fps 输出，同时按时间比例从 25 fps 原视频取帧，不会把人物动作加速或减速。6.46 秒中文样例的端到端口型生成由约 21 秒降至 8.21 秒，音视频时长差约 3 ms。渲染配置纳入缓存键，避免误用优化前的 25 fps 文件。

真实服务进程可访问 Apple Metal，MPS 下 batch 1/2/4/8 约为 16.0/17.3/18.4/16.3 fps，因此保留 batch 4。新增常驻 `wav2lip_worker.py`，服务启动时即预载模型、待机帧和人脸框，每轮只传入音频与输出路径，不再重复启动 Python 和加载权重。两次连续未命中缓存的实测中，5.8 秒和 5.6 秒音频分别用时 5.17 秒和 4.85 秒，口型视频生成已快于音频自身时长。当前剩余首包等待主要来自“等待整段回答与 TTS 完成后再开始渲染”，后续如需更低首句延迟，需做分句流水线而非继续降低帧率。

### 9.14 无 WASM Audio2BlendShape / DINet 验证

补齐 `lstm_model_epoch_325.pkl` 后，使用 6.46 秒中文女声生成 162 帧、6 维连续嘴形系数，整段音频特征与 LSTM 推理用时 14 ms。逐帧状态模式下 CPU 约 16445 fps、MPS 约 3055 fps，小 LSTM 因 Metal 调度开销在 CPU 更快。DINet_mini 的 184×184 局部重绘在 CPU 单帧约 3.48 ms，MPS 单帧约 2.47 ms，MPS batch 4 约 1044 fps。

修复上游 macOS OpenGL 3.3 Core Context、GLSL `#version` 与 VAO 兼容问题后，官方 Python 离线链路可在 Mac 完整运行。第一次输出残留红绿蓝嘴部提示色；拆分检查 OpenGL 提示图、DINet 输入、DINet 原始输出和最终融合后确认，并非权重或融合遮罩问题，而是 Retina 尺寸不一致：GLFW 逻辑窗口为 368×368，实际 framebuffer 为 736×736，渲染器按 736×736 设置 viewport，却只读取左下角 368×368，嘴部提示因此被裁到右下角，DINet 收到的输入分布错误。

渲染器现始终使用逻辑窗口尺寸设置 viewport，兼容 Retina framebuffer 仍为 2 倍的情况。修复后提示图准确覆盖原嘴，DINet 原始输出恢复为正常肤色和连续嘴形；官方素材与湖畔人物均通过完整视频及多时刻抽帧检查。湖畔 6.53 秒、162 帧、768×1152 的 H.264/AAC 样片总生成耗时约 3.82 秒，RTF 约 0.59，画质和性能均通过。验证文件为 `artifacts/clean-dinet-lakeside-fixed.mp4`。

随后新增 `dinet_worker.py` 常驻进程：启动时一次加载 LSTM、DINet、湖畔人物帧、参考特征和 OpenGL 网格，Node 服务通过逐行 JSON 协议串行提交音频，不再为每句话重新启动 Python 或加载模型。接口仅接受本机访问的 PCM WAV，按音频和渲染版本哈希缓存结果；临时音频权限为 `0600`，FFmpeg 使用参数数组而非 shell。隔离入口为 `?profile=dinet`，沿用已经验证的有声视频播放器，避免 WAV 与 MP4 同时播放造成双声。

真实服务连续两轮未命中缓存测试中，6.46 秒/157 帧语音的音频特征、逐帧渲染、封装分别耗时 14 ms、1792 ms、445 ms，总计 2251 ms，RTF 约 0.35；12.96 秒/320 帧语音分别耗时 18 ms、3343 ms、851 ms，总计 4212 ms，RTF 约 0.33。页面加载显示正确的 DINet 模式和人物 iframe，46 项自动测试全部通过。当前已经明显快于实时；进一步降低首句等待的重点是直接传输首段 fMP4/WebM 帧或 WebRTC，而不是继续优化模型算力。

湖畔素材继续实测发现，DINet 张嘴时会把嘴角横向拉宽，并把原片的暖珊瑚粉唇色变成偏灰紫色。仅缩放 BlendShape 幅度只能减小开合，不能明显缩短嘴宽。渲染器因此增加三层人物级校准：嘴部形变幅度默认缩至 0.82；仅对模型生成嘴唇的红/粉像素恢复原视频的色相和饱和度，排除牙齿、口腔及皮肤；最后将神经生成嘴部横向压缩至 0.88，以椭圆软遮罩贴回原始脸部，嘴外区域完全使用源视频。使用同一段 6.46 秒中文语音生成 157 帧，自测总耗时 2674 ms，逐秒六帧检查未见矩形边缘或脸部染色，嘴宽和颜色均比原 DINet 输出自然。缓存版本已更新，旧结果不会被继续复用。MiniMax 素材提示词也加入“小巧窄嘴、不得拉宽嘴角、保留暖珊瑚粉唇色”的约束，减少后续素材从源头放大嘴型。

继续对比原视频后发现第一版校色仍略暗、略紫。增强色相、饱和度和可见唇面的亮度时，宽掩膜曾把鼻翼和人中一并染红，抽帧检查未通过并立即废弃。最终掩膜依据该人物标准脸裁剪中的真实嘴部位置收缩到纵向 0.385–0.595，只选择高饱和度暖色且 Lab 红度足够的像素；牙齿因低饱和度被排除，口腔因低亮度被排除。最终 6 帧接触表检查确认只有上下嘴唇变为接近源视频的珊瑚粉，鼻翼、人中和周围皮肤保持原色；缓存版本更新为 v6。

页面复测发现每段神经口型视频结束时会闪一下。根因是播放器仅有一个 video 元素：结束后等待 250 ms，再将同一元素的 `src` 换回待机视频，换源解码期间必然可能出现空帧。现改为双层播放器，静音待机视频始终在底层预解码并连续播放，有声口型视频只在上层显示；口型结束后先尝试把待机时间定位到对应源素材帧，再以 70 ms 淡出上层，不再清空或替换正在显示的 video。浏览器真实播放 6.28 秒样片后确认上层透明、底层仍为 `readyState=4` 且持续播放，结束画面没有白帧；自动测试同时锁定双 video 结构并禁止恢复旧的 250 ms 换源逻辑。

### 9.15 真人 / 动漫统一聊天入口

主页面不再把真人与 VRM 动漫人物拆成两套独立聊天。左侧新增“真人 / 动漫”切换：真人模式继续使用湖畔素材、MiniMax 中文语音和 DINet 神经口型；动漫模式在同一人物区域加载 VRM，并接收同一轮回复的情绪、动作、说话状态和实时音量。两种模式共用浏览器会话记录、用户标识、角色设定及服务端陪伴状态，切换时只更换渲染层并中止当前播放，不创建新的对话上下文。动漫人物增加独立的柔和室内背景，仍支持拖动旋转、滚轮缩放和双击复位。

统一页随后补回原 VRM 页的造型和人物配置：动漫模式下可直接选择学院日常、暗色潮流、Nike-chan v1、Nike-chan v2 与简约短发，切换模型不再离开当前聊天；右上角“人物设置”可选择温暖、元气、冷静预设，或编辑名字、关系与说话风格。默认动漫造型由过于简陋的 `classic` 改为动作表现较稳定且服装完整的 Nike-chan v1；已有用户若仍停留在旧 `classic` 默认值，会在一次性版本迁移时自动更新，用户主动选择的其他造型则保留。

左侧布局进一步由“面板内人物卡片”改为完整角色舞台：真人视频使用 `cover` 铺满整个左半区，动漫 WebGL 画布同样覆盖全区，品牌、状态、模式、造型和角度控制作为舞台悬浮层。原 VRM 页的左转 45°、正面和右转 45°控制已迁入统一页，画布本身仍支持拖动旋转、滚轮缩放和双击复位。切入动漫时不再显示真人静态兜底图；加载阶段只保留场景背景，模型就绪后再显示人物，从而消除切换瞬间闪出真人头像的问题。

同时收紧角色身份表现：系统提示只以角色名字、朋友关系和日常表达方式描述角色，不再加入容易反向提示模型的身份分类措辞；当前身份追问由服务端稳定回答为“我是露米呀，是愿意认真听你说话的朋友”，不会把技术类别送入 TTS。历史中的旧身份追问和技术回答在送入模型前会被过滤，浏览器旧聊天记录按一次性版本迁移清除。接口实测普通与流式回答一致，50 项自动测试全部通过；浏览器实测真人、动漫模式均可原位加载并来回切换。

后续复测发现，完全省略人物生活能力会让 MiniMax 在“你在哪里、能不能出来”等问题上自行补成“只能在手机里”。长期记忆中没有相关内容，根因是人物提示一度同时要求“把自己理解为真实、连续的人”和“不要编造线下见面或现实承诺”：用户邀请人物下楼时，两条规则直接冲突，模型选择拒绝线下行动，再自行用设备身份解释原因。最终删除“禁止线下见面”的冲突限制，改为明确拥有普通人的日常生活和行动能力；散步、出门、下楼等邀请按共同生活场景自然接话，不允许以手机、屏幕、应用或技术身份拒绝。具体住址、危险和违法行为仍禁止编造。

### 9.16 聊天链路审计、人物设定和记忆清理

统一页面的人物设置增加背景字段后，每轮请求实际发送 `name`、`relationship`、`style`、`background` 四项。一次“名字似乎恢复成露米”的问题最终确认不是人物数据被重置，而是首页欢迎语正文仍在 HTML 中写死“我是露米”；运行时只更新了头像标签、页面标题和输入占位符。欢迎语现由保存的人物名字动态生成，清除聊天和记忆不会删除人物设置。

为了不再依靠代码推断模型问题，服务新增最多 20 条的本机内存诊断环形缓冲区，记录浏览器输入、标准化人物设定、历史消息、召回记忆、连续状态、供应商请求、MiniMax 原始正文、已发送的 SSE 分句和最终结果。诊断只通过 `/api/chat/debug/recent` 在回环地址访问，不含 API Key、不写文件，Node 服务重启后立即消失。

链路审计确认前端没有重复当前消息：页面先把用户消息加入本地历史，请求时使用 `history.slice(0,-1)` 排除它，服务端最后只追加一次当前 `user` 消息。正常顺序为 `system → 旧 user/assistant → 当前 user`。真正发现的两个数据问题是：

1. 早期记忆提取器会把“你还记得我刚才说什么吗”误判为“请记住”命令，并把“你记得我喜欢什么吗”截成偏好；现只接受明确的保存命令，并要求普通偏好表达从完整用户分句开始。
2. 过滤“我在手机里”等旧错误回复后，历史可能留下连续两条 `user`，MiniMax 在复测中因此返回空正文；现自动合并相邻同角色消息，保持有效消息结构。

页面清空按钮此前只删除浏览器 `localStorage` 历史，服务端的长期记忆和心境连续状态仍然保留，与“清除聊天和记忆”的用户预期不一致。新增 `/api/chat/memory/clear`，清空按钮现在同时删除当前用户的本地历史、语义记忆和连续状态。当前记忆文件可恢复到 `users={}`、`relationships={}` 的完全干净状态。

身份连续性增加两层保护：历史输入会过滤旧的身份/设备限制回答；模型输出在最终正文和流式朗读前都会检查“在手机/屏幕里、不能下楼”等跳出内容，并依据当前共享场景恢复为自然人物回答。修复后使用原对话复测：

```text
用户：那你赶紧下楼
丽丽：等我一下哈，换个鞋就下来～

用户：为什么不能（历史中含旧的“我在手机里”错误回复）
丽丽：啊，我刚洗完澡头发还没干呢，你再等我一会儿嘛～马上就好。
```

截至本节，自动测试共 56 项，覆盖人物设定、历史清洗、设备限制回复修复、记忆问句误判、服务端记忆清理、真人双视频播放和真人/动漫统一页面。

### 9.17 多音色选择

此前 TTS 音色完全由服务端单一环境变量 `MINIMAX_TTS_VOICE` 控制，默认 `female-tianmei`；人物设置只影响文案提示，不影响声音。前端请求 `/api/speech` 时只传正文和情绪，因此所有人物和造型始终使用同一个音色。

现新增独立的音色白名单模块和 `/api/voices`：MiniMax 模式内置甜美女声、柔和少女、温暖闺蜜、成熟女声、淡雅学姐、嗲嗲学妹 6 种普通话女声。人物设置增加“声音类型”，选择保存在 `lumi-voice-profile`，真人和动漫共享；每段 TTS 请求携带公开 profile key，服务端映射成官方 `voice_id`。未知 key 自动回退到 `.env` 默认音色，前端不能直接提交任意克隆音色 ID。

账号下的克隆音色或文生音色通过 `MINIMAX_TTS_VOICES_JSON` 加入显式白名单，页面只显示标签和描述，不暴露配置过程。音色选择只进入 TTS payload，不进入 LLM 人物提示、历史或记忆。相关自动测试覆盖 6 种内置选项、默认回退、自定义音色解析和任意客户端 ID 拒绝；当前测试总数为 58。

根据后续试听需求，内置列表继续增加 `female-yujie` 经典御姐、`wumei_yujie` 妩媚御姐、`Chinese (Mandarin)_Mature_Woman` 傲娇御姐和 `Arrogant_Miss` 强势小姐。四种仍使用公开 profile key 和服务端白名单，不改变原默认甜美女声。

### 9.18 真人动作与动漫语义对齐

审计统一聊天链路发现，服务端虽然会推断 `action`，真人 DINet 接口此前却始终使用 `lakeside_idle_test`，因此动作只在动漫模式生效。前端现把当前动作传入真人口型请求，首个语音分句使用语义动作，后续分句回到待机；渲染缓存键同时包含动作素材，避免相同音频错误复用其他姿势。

以同一湖畔人物和固定机位生成挥手、鼓掌、欢呼、鞠躬、害羞、思考、关心、惊讶和耸肩 9 段 768×1152、24 fps、约 4.46 秒素材。逐段关键帧检查确认人物、服装、背景和构图一致；DH_live 预处理统一转为 25 fps，并判定 8 段通过且不存在明显说话。鞠躬在第 28 帧触发人脸范围大幅变化保护，没有强行接入。交叉拒绝和抱臂在提交时 MiniMax 返回余额不足，暂时回退待机。

通过项安装为 `lakeside_wave`、`lakeside_clap`、`lakeside_cheer`、`lakeside_shy`、`lakeside_thinking`、`lakeside_caring`、`lakeside_surprise` 和 `lakeside_shrug`，与 VRM 使用相同语义动作名。为防止 8 个动作重复加载 8 份 DINet，Python worker 改为只常驻一套音频模型与神经模型，收到请求时在进程内切换视频帧、关键点、参考特征和 OpenGL 网格。使用同一段 50 帧测试语音实测：鼓掌 949 ms、思考 943 ms、挥手 933 ms、待机 903 ms，均返回正确动作素材；四组输出抽帧确认口型和动作同时出现。自动测试 59 项全部通过。

充值后补生成交叉拒绝和自然抱臂，两段均保持同一人物、服装、机位和闭嘴基准，DH_live 预处理判定不存在明显说话，分别安装为 `lakeside_cross` 与 `lakeside_arms_crossed`。鞠躬不再强行进入 DINet：原素材加速并移除音轨后形成 2.6 秒静音动作，页面先完整播放鞠躬、回正，再播放以待机底片生成的回答口型，避免低头期间人脸范围变化破坏嘴形。

捂嘴惊讶随后发现手掌局部呈半透明。原素材手部正常，DINet 输出却在手掌遮住嘴时仍重绘嘴唇；椭圆羽化融合会用生成脸覆盖指尖与掌心边缘，属于遮挡关系冲突，不是视频透明度。惊讶因此与鞠躬采用相同策略：2.6 秒原始静音动作完整播放并回正，随后再播放待机底片的回答口型；服务端直接收到 `surprise` 口型请求时也回退待机，禁止继续生成穿过手掌的嘴形。

耸肩动作按反馈增加轻微歪头。前两版均歪向人物自身左侧，即画面右侧，没有满足画面方向要求；第三版虽然头部方向正确，但双手垂在身体两侧且掌心向下，更像平衡动作而不是表达“不知道/没办法”。最终版改为双肩轻抬、肘部弯曲、前臂向身体前方摊开、双掌明确朝上，同时头向画面左侧粉色发饰方向轻歪，首尾回到正面。最终素材替换 `lakeside_shrug` 后，111 帧预处理全部通过，检测结果为不存在明显说话；中间版本原片保留在实验资源中用于对照。

页面复测“给我鞠个躬”时，服务端 SSE 明确先返回 `action: bow`，独立播放器测试也确认静音视频以 `muted=true`、`readyState=4` 正常播放到 2.6 秒并回到待机。用户未看到动作的原因是已经打开的页面仍驻留修改前的 JavaScript，重启 Node 不会刷新浏览器执行上下文。主页面脚本和真人/动漫 iframe 因此增加统一运行时版本参数；刷新页面后会加载当前播放器，后续动作运行时升级也不再沿用旧 iframe 资源。

### 9.19 真人首句延迟分解与单次编码

使用同一句 2.72 秒的 MiniMax PCM WAV 在本机测量：MiniMax 文案首个可读分句约 4.32 秒，TTS 约 0.81 秒，旧 DINet 接口等待 2.41 秒。旧 DINet 内部 68 帧共 2.14 秒，其中神经帧生成 1.56 秒，最后再解码临时 mp4v 并转码 H.264 耗时 568 ms。因此整体首句主瓶颈是 M2.x 模型的首次文本输出，其次才是本地视频。

DINet worker 改为用 ffmpeg rawvideo 管道直接接收每个完成帧，在神经推理的同时进行最终 H.264 编码，删除临时 mp4v 和整段二次转码。优化后同一输入的 DINet 内部耗时为 1.53 秒，接口等待 1.79 秒，相比旧版分别降低约 29% 和 26%；最后收尾封装仅 21 ms。输出仍为 768×1152、25 fps、2.72 秒、H.264 + 16 kHz 单声道 AAC，新旧画面 SSIM 为 0.983。`ultrafast` 对照只再减少约 19 ms，却将文件从 0.58 MB 增大到 2.24 MB，因此最终保留 `veryfast` 档。

文本模型随后使用同一人物提示、同一问题各连续测试 3 次。`MiniMax-M2.7-highspeed` 首个可读分句平均为 3.23 秒，完整短回答平均为 3.28 秒；`MiniMax-M3` 分别为 1.12 秒和 1.31 秒，首句平均降低约 65%。切换 M3 后的实际项目全链路为：首个分句 1.50 秒、TTS 1.16 秒、DINet 接口 1.73 秒，从提交用户消息到视频可播放共 4.51 秒。项目本地配置与默认文本模型因此改为 `MiniMax-M3`；视频生成仍使用独立的 `MINIMAX_VIDEO_API_KEY`。

### 9.20 单按钮连续通话

原语音按钮每次只启动一轮 `SpeechRecognition`，每句回答后用户都需再点一次。现改为通话开关：首次点击开始连续通话，浏览器本地 Web Audio VAD 检测到用户说话后连续静音 650 ms，便主动结束本轮识别并提交；SSE 文案请求结束后仍等待 `speechQueue` 的 TTS、DINet、动作和播放全部完成，再延迟 180 ms 自动重开麦克风。第二次点击是唯一的结束操作，会同时取消识别、模型请求和当前播放。

麦克风权限被拒绝时通话自动关闭；`no-speech` 等临时错误不结束通话，而是稍后恢复聆听。回答播放期间识别器始终关闭，从流程上避免人物把自己的 TTS 当成新的用户消息。页面的 `aria-pressed`、按钮名称和提示文案会同步显示“开始通话 / 结束通话”状态。

### 9.21 三秒响应优化

MiniMax TTS 改用北京低延迟入口 `api-bj.minimaxi.com`。同一短句本机连续对照中，标准入口约 969 ms，北京入口约 562 ms，TTS 请求缩短约 42%。流式文案在逗号前已有至少 3 个汉字时即可提前形成首段（此前要求 6 个），使 TTS 与 DINet 更早开始并和后续文案生成并行。

服务端另增加最多 64 条的进程内语音 LRU 缓存，以模型、音色、情绪和文本为键。重复短句直接返回同一 WAV，因此后续 DINet 内容缓存也可命中；不保存用户身份或聊天记录，重启即清空。

重启后的冷、热对照中，“辛苦了”首次 TTS 为 1.12 秒、20 帧 caring 口型接口为 0.49 秒；第二次相同请求的 TTS 为 0.8 ms、口型接口为 1.5 ms，两段均确认命中缓存。M3 实测仍存在明显云端波动：相同短问题的完整文本流两次分别约 4.27 秒与 2.05 秒。因此热短语可把后处理几乎完全移出关键路径，但首次出现的句子仍受云端首段与首次 TTS 影响。

上述改动与 650 ms 本地停顿检测共同面向“正常网络、简短日常回答约 3 秒内开始播放”的目标。它不是硬实时保证：云端 M3 首 token、TTS 网络请求和本机 DINet 推理都会有波动；较长首分句或接口拥塞时仍可能超过 3 秒。

### 9.22 对话级动作调度第一版

原流程把主动作直接分配给第一个流式语音片段，其余片段全部待机。开启三字逗号分段后，“辛苦了，”之类极短开场会导致关心或思考动作刚开始就结束。新增共享动作调度器：关心、思考、害羞、抱臂遇到不足 6 个字的开场时，先说完短开场，再在下一句完整内容中执行动作；鼓掌、欢呼、惊讶等强调动作仍即时出现。

高幅动作增加跨轮 3 秒预算，短时间连续自动触发时降级为微笑或待机，用户明确说出动作要求则始终执行。开始聆听、停止回答和播放队列结束都会重置当前轮动作并让 VRM 姿势回落。这一版解决动作时机和滥用问题；后续日常微动作仍需准备同人物、同机位且首尾回到待机姿态的视频变体。

礼物和称赞场景随后补入本地语义映射。“给你买了礼物、送你一束花、这是给你的”等表达使用 happy 表情与 caring 双手靠近胸前姿势，避免用过于正式的鞠躬；“你很漂亮、温柔、贴心、优秀”等对人物的夸奖使用 shy 与腮红。由于 caring 属于低幅持续动作，短开场“谢谢你，”会先保持待机，下一句完整感谢内容再抬手。

### 9.23 逐句动作与轻点头

流式句子增加独立情绪和动作字段，前端调度器可在一轮回答中接收一次由回复正文触发的次级微动作。例如用户分享一件值得肯定但未命中预设关键词的事情，模型回复“你做得很好”时，该句可触发 `nod`，而不是整段保持待机。为避免动作碎片化，每轮最多接受一次不同于主动作的次级动作。

真人 `nod` 复用同人物、同机位的 `lakeside_agree_test`；动漫新增代码生成的 1.2 秒轻点头轨道，头部两次小幅俯仰，使用 `LoopOnce` 并在自然头位结束。动作冷却统一由对话调度器管理，VRM 播放端对已经通过调度的动作强制执行，解决明确点头指令偶尔被底层二次冷却拦截的问题。

### 9.24 字幕布局隔离

字幕按钮只负责在右侧显示聊天记录。聊天列表改为右侧面板内独立的弹性滚动区域，右侧面板限制溢出，左侧人物面板显式保持可见并与字幕布局隔离。原布局在 800 px 以下立即改为上下排列，窄桌面窗口容易让用户停留在聊天区域时误以为人物消失；结构切换阈值降至 620 px，621–800 px 使用紧凑的左右双栏。样式资源增加版本参数，避免浏览器继续使用旧布局缓存。

### 9.25 夸赞动作与聆听反馈

新增 `thumbs_up` 语义：用户明确要求点赞，或人物回答出现“你真棒、做得很好、为你骄傲”等强夸赞时触发；“挺好、挺不错”等轻度认可仍使用点头。动漫端使用抬起右手的夸赞姿势，对支持完整拇指骨骼的模型表现为竖拇指；部分模型手指绑定不完整时保留为克制的开掌肯定，避免强行扭曲手掌。真人端在补录同人物竖拇指素材前回退到 `lakeside_agree_test`。

连续通话的动漫聆听阶段增加一次性微点头：只在已经识别到用户语音且持续约 1.4–2.1 秒时触发，每轮最多一次；结束识别、发生错误或结束通话都会清除定时器。真人模式不播放预录动作，避免动作视频切换干扰麦克风和当前现场感。

### 9.26 流式音频与分段口型方案

当前真人链路虽然已经按 M3 流式分句并提前准备后续句，但每个分句内部仍是串行的“等待完整 TTS WAV → 等待完整 DINet MP4 → 浏览器开始播放”。近期实测的冷请求大致为：用户停顿与 STT 收尾约 0.8–1.3 秒、M3 首个可读片段约 1–2 秒且存在更大云端波动、TTS 约 0.56–1.2 秒、DINet 约 1.5–1.8 秒。因此 TTS 并非唯一瓶颈；首句等待由 M3、TTS 与完整视频渲染共同组成。

下一阶段采用两步演进。第一步把 MiniMax WebSocket TTS 返回的连续音频增量解码成 PCM，以约 0.8–1.2 秒为一个窗口生成带音频的小 MP4，使用双播放器预加载和严格序号队列验证连续播放。窗口之间保留 160–240 ms 声学上下文，后一窗口只将重叠区用于推理，封装时删除重复音频和帧，避免音爆、重复字和嘴形回零。动作素材帧索引跨窗口连续递增，不允许每段动作重新从首帧开始。

第二步将 DINet worker 改为会话协议，持续维护 OnlineFbank 缓冲、Audio2BlendShape LSTM 的 hidden/cell、动作帧索引、音频采样时钟和 FFmpeg 编码器。浏览器通过 MediaSource 接收 fragmented MP4，保持 300–500 ms 起播缓冲并按序追加。音频与视频使用同一个封装和时间轴，不采用浏览器分别调度 PCM 与无声视频的方案，以免长回答产生漂移。

计划新增 `start/audio_chunk/finish/cancel` worker 消息和完整阶段计时，分别记录 STT/VAD、M3 首段、TTS 首音频、DINet 首帧、首个可播放分片和浏览器起播。第一阶段目标是首个可读文本到人物开口不超过 2 秒、正常网络下用户停顿到人物开口中位数不超过 3 秒、30 秒回答音视频偏差不超过 80 ms、打断后 200 ms 内停止旧会话。新链路在验证完成前保留当前完整 WAV + MP4 路径作为回退。

随后复查 WALL-E，确认微信只是附加桥接功能，值得参考的是它的 xiaozhi 直连语音闭环。该闭环用长连接承载连续 Opus 音频包，服务端以有界队列串联 VAD、ASR、流式 LLM 和 TTS，下行端常驻解码并支持 `listen/start/stop` 与 `abort`。它能改善音频传输、顺序播放和打断，但当前 SherpaASR 仍在 VAD 停止后离线识别，并且链路没有真人视频渲染，所以不能直接解决 M3 首段或完整 DINet MP4 的等待。

开发在 `codex/streaming-avatar` 分支开始。首个实现先建立不影响主页的协议骨架：新增本机限定的 `start/audio-chunk/finish/cancel` API，输入固定为 16 kHz 单声道 PCM16，分片必须严格递增，设置 60 秒容量上限，并记录首块延迟、输入缓冲时间、结束到成片时间和总时间。当前 `finish` 将 PCM 封装为标准 WAV 后调用既有 DINet，明确标记为 `whole-wav-fallback`；它是后续状态化 worker 的兼容与测试基线，不是最终的流式渲染完成状态。

第一轮真实测试使用 `speech-2.8-turbo` 短句：2.7–2.8 秒语音的 WebSocket PCM 首包分别约 582–736 ms，完整音频约 842–962 ms，证明 TTS 音频已经能在完整语音结束前进入本地链路。冷启动 DINet 的首个 1 秒窗口耗时约 5091 ms，而同进程后续窗口只有 189–230 ms，瓶颈明确为模型首次加载而非热推理；服务启动流程因此改为预热完成后再监听端口。

初版每个 800 ms 窗口只输出约 19 帧，原因是 `Audio2bs(...)[5:]` 固定丢掉开头 5 帧，200 ms 输入上下文不足以补回目标帧数。分段器现保存上一窗口末尾 400 ms PCM并前置到下一次推理，再只输出与当前音频对应的最后 20 帧；FFmpeg 音轨用 `-ss 0.4` 裁掉上下文，从而恢复 25 fps 且不重复声音。未切分缓冲始终保留至少 240 ms，避免结束时产生约 100 ms 的碎片；动作帧索引通过 `frameOffset` 跨窗口连续递增。

修正后的真实短句得到 4 个连续片段：前三段均为 800 ms、20 帧，尾段音频 909 ms、视频 880 ms，最终音视频偏差约 29 ms；各段热渲染约 238–322 ms。该轮 MiniMax PCM 首包为 434 ms，3.309 秒语音的全部 PCM 在 651 ms 返回。页面播放器为每个已到达片段立即创建预加载视频层，并在当前段结束后按序切换；中断时会同时取消网络会话、清理尚未播放的层并结算所有等待项。真人模式因此默认启用流式链路，保留 `?streaming=0` 回退旧整句实现。

第二阶段把 Audio2BlendShape 从“400 ms 重叠窗口近似连续”改成真正的状态化推理。每个语音会话在 worker 内持有一个 Kaldi `OnlineFbank`、已消费特征索引和 LSTM `hidden/cell`，一次性用 400 ms 静音稳定初始状态；随后每个 PCM 样本只进入一次声学模型。真实测试中第一段 400 ms 生成10帧约 209 ms，后续 800 ms/20帧约 228–234 ms，其中声学推理从原分段约 2 ms降为约 1 ms。该轮 TTS 首 PCM 为 473 ms，因此首音频到达后约 0.2 秒即可得到首个有声视频段。动作帧偏移连续为 0/10/30/50/70；正常结束或用户打断都会向 worker 发送 `cancel_stream` 释放 fbank 与 LSTM 状态。

随后用“今天工作有点累，你会怎么安慰我”测量提交到第一段可播放视频。热进程三轮分别约 2.48、2.96 秒，M3 首短语占 1.67–1.86 秒，首个 400 ms 语音口型片段占 0.61–1.10 秒。重启后的第一次测试出现 15.40 秒，其中 M3 上游 HTTP 建连为 11.40 秒、首短语为 14.41 秒，DINet 仅约 0.36 秒，证明极端慢请求来自云端文案冷连接而非本地口型。

服务启动现并行预热 DINet 和 M3；DINet 仍在监听端口前完成，M3 改为 8 秒上限的后台预热，避免一次云端超时把整个页面启动拖住。M3 使用与真实对话相同的默认人物系统提示建立前缀缓存。系统提示顺序调整为“稳定人物身份 → 稳定回复规则 → 动态记忆 → 动态连续状态”，符合 MiniMax 前缀 Prompt 缓存的复用方式。预热后的首次请求为 3.36 秒，后续两轮仍因 M3 波动达到 5.64 和 4.14 秒；阶段记录显示本地记忆上下文约 0–1 ms，主要波动仍在上游连接和首 token。对 `reasoning_split` 做四轮 A/B 后，开启时首正文约 2.09/2.43 秒，关闭时约 2.57/3.24 秒且正文会包含 `<think>`，因此继续保持开启。TTS 同一 WebSocket 完成第一个 `task_finish` 后无法启动第二个任务，不能做跨句连接复用。最终没有加入与上下文无关的固定确认句，以免换取速度时损害自然度。

### 9.27 下一阶段优化路线与行为导演

路线按风险从低到高拆为五步：先稳定流式分片衔接和页面状态；再增加不调用额外模型的本地行为导演；补录八组低幅真人微动作；把独立 MP4 队列升级为连续 fMP4/MediaSource；最后用独立入口验证 LivePortrait 五官协同。当前可用 DINet 链路始终保留为回退，不在实验阶段直接替换。

### 9.28 LivePortrait 五官协同可行性

实验使用官方 `KlingAIResearch/LivePortrait` 源码提交 `9b294b3d0536135442ea73cb01e6cb3ca7029dd3`，在独立 Python 3.10 环境中只下载人像所需的 8 个权重文件，共约 653 MB，并逐个校验文件大小与 SHA-256。官方依赖当前存在两处版本漂移：`albumentations 1.4.10` 需要兼容的 `albucore 0.0.12`；官方 macOS 文件固定的 PyTorch 2.3 在 MPS 上缺少 `grid_sampler_3d`，会把关键算子回退到 CPU。安装脚本因此固定 PyTorch 2.13、torchvision 0.28，并移除项目不使用且锁死旧 torch 的 torchaudio。

同一组 1.2 秒、30 帧人像眼部驱动在 PyTorch 2.3 下动画阶段约 28 秒，总耗时 40.78 秒，峰值内存约 4.52 GB；PyTorch 2.13 确认 `grid_sampler_3d` 在 MPS 原生执行后，动画阶段仍约 25 秒，总耗时 33.21 秒，峰值约 4.21 GB。吞吐约 1.2 fps，距离 25 fps 实时要求仍差约 21 倍，因此不能放在用户停顿到人物开口的在线路径中。

画质检查使用 `animation_region=eyes` 和 `driving_multiplier=0.35`。输出没有明显矩形贴片边缘，整段相对原片 SSIM 为 0.995709、PSNR 为 48.063 dB；代价是脸部略微变软，眼部效果也较弱。原始 8.88 秒待机本身已有轻微头部和表情变化，时间线抽帧未见明显眨眼。结论是继续以 DINet 负责实时口型和现有视频动作；LivePortrait 只保留为离线素材制作工具，用于确有缺失的眨眼、视线或低幅表情，不对每条聊天回答执行，也不默认重处理全部素材。新增 `scripts/generate_liveportrait_material.sh` 固定走隔离环境，默认仅驱动眼睛且使用 0.35 倍幅度，同时允许显式选择 `exp/pose/lip/all` 进行素材实验。其代码是 MIT，但默认 InsightFace 检测模型仅限非商业研究，当前个人测试可用，后续发布或商用前必须更换检测模型或重新核对授权。

### 9.29 连续视频的句间空档校正

连续 MediaSource 路径用同一个视频元素拼接所有 fMP4，而 PCM 使用 Web Audio 绝对时间调度。无空档的两段 800 毫秒浏览器实测中，视频缓冲从 0.8 秒连续增长到 1.6 秒，音频 `gapMs=0`，首帧 58 毫秒、开口交接迟到 4 毫秒、最大漂移 29 毫秒，证明常规连续路径没有切层停顿。

随后故意把第二段延迟 1.2 秒送达，第一段结束后触发 320 毫秒待机过渡。旧同步公式以第一段的音频起点作为整轮固定原点，把 400 毫秒无语音等待也当成视频应前进的时间；第二段追加后立即测得 450 毫秒漂移，并会 seek 到新分片后部。现由每个 PCM 分片记录实际 `audioGapMs`，在恢复连续视频前将累计空档加到音频原点；相同测试的空档为 408 毫秒，漂移降到 49 毫秒，随后利用开口前 60 毫秒预启动窗口对齐到第二段起点，首帧事件仍比音频边界只晚 4 毫秒。单元测试同时固定“媒体时间轴不包含句间等待”的换算规则。

行为导演第一版以流式 `meta` 和逐句 `sentence` 事件为输入，输出 `action/intensity/gaze/head/startAtMs/holdMs`。高幅动作保留 3 秒预算和明确指令豁免，低幅动作不进入冷却；关心、思考等遇到不足 6 个字的开场仍延后。日常回复语义新增轻点头、微笑、关心和思考覆盖，同时普通生活陈述可触发一次克制点头。人物容器记录当前行为线索，后续真人视频和 VRM 可以在不改对话协议的前提下逐步消费更多字段。

行为导演第二步完成真人跨句连续性。盘点确认当前 12 段卧室动作底片规格一致，均为 768×1152、25 fps、222 帧、8.88 秒，问题不在素材时长，而是旧实现每句从第 0 帧重新开始。调度器现维护回复内的估算时间游标和动作保持窗口；关心、思考、微笑在保持时间内可延续到下一句，并计算 40 毫秒一帧的后续 `frameOffset`。服务端以该偏移初始化新的 DINet 状态化会话，VRM 对延续动作不重复启动。句间播放器加入最多 360 毫秒的短保持窗口，减少并行渲染略晚时露出待机造成的闪跳；大幅动作仍只执行一次。

继续回归普通回答后发现，`idle` 不属于上述动作延续集合，因此每个句子仍会从待机底片第 0 帧开始；回答结束时播放器背后的循环待机又可能位于另一个时间点。现将 `idle` 的 `frameOffset` 绑定到当轮累计朗读时间，并用实际渲染片段的 `audioMs` 校正最终进度。`stream-end` 到达时即使最后一个 MP4 仍在播放，也会保存待机目标和交接延迟；最后一帧结束后先将底层视频对齐到镜像循环的同一姿态，再切换图层，避免异步通知顺序使对齐参数失效。

本机真实流式探针从待机第 25 帧启动，服务依次返回 `25 → 35 → 65` 三个连续偏移，证明客户端参数、会话状态和 DINet worker 没有在边界处归零。400 毫秒首段渲染 420 毫秒，后续 1.2 秒段渲染 747 毫秒，均能被播放时间覆盖；该轮 TTS 首音频 772 毫秒，从请求到首段成片约 1.2 秒。

首段文案优化复查发现，M3 `reasoning_split` 开关在六次完整人物提示交替测试中的安全首段中位数约为 1.20 秒和 1.37 秒，差异方向随请求波动，不足以支持切换生产配置，因此继续开启，避免 `<think>` 原文进入流式累积。真正可控的退化来自长聊上下文：旧版浏览器会上传最多 20 条完整记录，服务端保留 10 条且每条可达 2000 字。现改为浏览器最近 8 条×900 字、服务端短期总预算 3600 字，长期记忆独立保留；超长虚构历史实测 M3 首段 1.78 秒、全文 1.96 秒。快速分句的逗号短语阈值同时由 3 字提高到 6 字，避免“辛苦了，”形成一次过短 TTS 和额外句间停顿。

分段音爆与停顿继续下探到播放器音轨。旧版每段 MP4 自带独立 AAC，浏览器只能在上一段 `ended` 后调用下一段 `play()`，即使内容有序仍会反复初始化媒体解码器。现在 segment 同时携带其原始 16 kHz PCM，iframe 用 Web Audio 绝对时钟连续调度，视频静音作为画面层；无法解锁 AudioContext 时自动回退 MP4 音轨。首段扩大到 800 毫秒后，热实测首段生成 531 毫秒，后三个 1.2 秒段分别 754、726、784 毫秒，稳定快于播放速度。流式 TTS 同时补齐情绪白名单：此前 `caring` 被原样放进 MiniMax `voice_setting.emotion` 会返回 `invalid params`，现在只发送上游支持的情绪，关心回复实测生成 5.05 秒音频成功。

随后按真实浏览器消息链复查，发现主页面原先只把 `url/requestId` 转发给人物 iframe，服务端返回的 `segment.audio` 在最后一跳丢失，页面实际仍会使用 MP4 音轨；此外，iframe 收到异步 `postMessage` 后再创建 AudioContext 也可能错过按钮点击的用户激活。现把播放消息构造抽成可独立测试的协议函数，明确携带完整 segment，并由主页面在首次指针操作或开始通话时同步创建、恢复一个共享 AudioContext，iframe 只复用它。新增回归测试同时覆盖流式和整句消息，防止“服务端有 PCM、页面却没使用”的假通过。

v7 真实流式探针继续暴露了边界余量问题：`smile` 动作的四段为 800/1200/1200/620 毫秒，连续帧偏移 0/20/50/80，首段冷切换生成 914 毫秒，两个 1.2 秒段生成 818/848 毫秒。后续段虽然实时率小于 1，但加上 SSE 传输、MP4 元数据加载和调度后，首段只剩很薄的安全余量。默认后续窗口因此从 1.2 秒降到 800 毫秒；它不推迟首播，而是以更多小分片换取更早的下一段可用时间，适合当前本机单用户链路。重启后的同文案复测得到 800/800/800/800/747 毫秒五段，连续偏移 0/20/40/60/80，四个后续段分别生成 579/596/610/565 毫秒，每段留下约 190–235 毫秒本地处理余量。

跨句审计发现旧前端虽会提前启动后一语句的 TTS/DINet preparation，却把“向人物入队”挂在等待上一句全部播放结束的 `speechQueue` 后，并且每句话各自发送一次 `wav2lip-stream-end`。这会在句号处让人物误判整轮结束、尝试切回待机，再开始下一句。v8 增加整轮流协调器：句内 segment 全部入队后立即承接下一句，播放 Promise 只作为整轮完成屏障，不再阻塞后续入队；结束事件从每句一次收敛为整轮一次。常驻 DINet worker 自身仍通过 Promise chain 串行处理所有渲染任务，不发生并行切换动作素材；无声惊讶和鞠躬则显式等待已有播放段完成后再独占画面。

首响延迟新增六轮 M3 热链路采样。第一组首个可朗读短语为 3124/1817/3281 毫秒，上游响应建立为 1347/907/2234 毫秒；第二组在增加细分指标后，首正文分别为 6075/1535/2504 毫秒，而 `firstTextDeltaMs → firstCleanTextMs → firstSentenceMs` 每轮只相差 0–2 毫秒。结论是当前慢点来自 M3 输出正文前的上游连接与思考波动，不是本地记忆（0–1 毫秒）或分句等待。官方文档将 `max_completion_tokens` 定义为硬输出上限，降低它可能截断回复，却没有承诺缩短首 token，因此没有用未经验证的 160 token 配置替换当前 400。服务和页面改为直接暴露聊天首句、TTS 首音频、DINet 首段与端到端首 segment 指标，后续真实会话可持续采样。

统一指标随后确认动作素材冷切换是可控的小瓶颈：同动作关心首段渲染 549 毫秒，`关心 → 待机` 和 `待机 → 关心` 都为 868 毫秒，稳定多出约 319 毫秒。没有缓存多套巨型 RGBA 帧，而是新增 worker `prepare_asset` 操作，并在 M3 开始等待正文时提前串行切换预测动作。纯本地诊断得到三次实际切换 302/331/283 毫秒，同动作再次预热为 0 毫秒；先预热关心后，独立 TTS+DINet 首段渲染从 868 降到 680 毫秒，素材切换的 287 毫秒已与 494 毫秒 TTS 首音频等待重叠。本轮不改变动作内容、不增加常驻帧内存，预测不一致时正式渲染仍会执行正确的 `set_asset`。

连续通话收尾审计发现，本地 VAD 达到 650 毫秒安静阈值后只调用 `recognition.stop()`，真正提交仍串行等待浏览器触发 `onend`，这一段不确定空等未纳入先前服务端首响指标。新增可独立测试的 `RecognitionTurnGate`：浏览器最终转写使用 450 毫秒停顿阈值并在阈值处直接提交，临时转写仍为 650 毫秒且停录后最多再等 90 毫秒接收最终文字修正；最终 `result`、`onend` 或超时三者先到者提交，后到事件被去重。确定性时钟测试覆盖最终结果零等待、24 毫秒最终修正、90 毫秒上界、12 毫秒提前 `onend`、失败取消及迟到事件不重复提交。页面运行时升级到 v9，内置浏览器确认最新脚本、真人 iframe 和服务均就绪；其不提供 Web Speech，真实麦克风事件顺序仍需在 Chrome 会话中持续采集 `vadStopToSubmitMs`，不能用模拟测试冒充真机耗时。

分片链路审计发现，页面已把服务端返回的 PCM 作为连续主音轨，但 DINet 每个小 MP4 仍重复编码 AAC，播放器随后将 MP4 静音，属于无效编码和下载。v10 增加 `externalAudio/videoOnly` 能力协商与独立缓存维度：只有共享音频上下文运行且 iframe 回报 `pcm-ready` 时才用 FFmpeg `-an` 输出纯视频，其余情况保留原带声文件。交替四轮真实请求中，热态 800 毫秒分片渲染约 413–444 毫秒，是否含 AAC 对总渲染影响很小；同画面首段带声文件为 160,286 字节，纯视频为 152,046 字节，减少 8,240 字节（5.1%）。`ffprobe` 验证纯视频只有 0.8 秒 H.264 流，回退同时含 0.8 秒 H.264 与 AAC。该结果证明优化价值主要是减少冗余传输和双轨风险，不是降低 DINet 神经推理耗时。

v11 继续处理视频接缝。旧播放器即使下一段已经下载，也要等前一 `<video>` 触发 `ended` 后才调用下一段 `play()`；而且 PCM 排期也等待对应视频 `loadeddata`，视频缓存慢会反过来给声音制造间隙。新路径在分片到达时立即把 PCM 排入 Web Audio 时间轴，视频独立并行加载：边界前 32 毫秒预解码首帧并暂停，到各自 `audioStart` 才恢复和显层，迟到超过 25 毫秒才追帧。带 AAC 回退保持旧串行逻辑，避免双音轨重叠。跨句服务端分片序号会归零，浏览器因此增加独立整轮 `playbackSequence`；加载、预启动和取消状态也纳入回待机屏障。临时同源验收页用真实两段 0.8 秒纯视频和静音 PCM 测得首帧 32/31 毫秒，两次边界迟到均为 4 毫秒；页面无应用错误，验收后测试页已删除。确定性测试另覆盖 32 毫秒提前量、边界等待、25 毫秒追帧阈值和最大 seek 限制。

连续真实探针使 `public/dinet-avatar/generated` 累积到 504 个 MP4、约 158 MiB，且旧实现完全没有生命周期管理。新增通用 `GeneratedMediaCache`，只回收 24 位哈希 MP4，按最近使用时间维护 384 文件/128 MiB 双上限，并保护 15 分钟内新文件与刚完成的输出。缓存命中确认、`utimes` 提升和清理在同一 Promise 队列中串行，避免回收与返回 URL 竞态；保护导致暂时超限时不会越过安全窗口硬删。临时目录测试覆盖容量与数量双限制、最近文件、显式保护、非生成文件、缓存命中提升及状态统计。正式启动前只读预演计划删除最旧 120 个；重启后实际从 504 个/158 MiB 降到 384 个/78 MiB，最旧哈希消失、近期输出仍存在、健康接口正常。缓存占用同步并入仅本机可访问的 `/api/dinet/status`。

生成视频的 HTTP 传输随后改为文件流和字节范围读取。使用一个 188,969 字节的真实 DINet 哈希视频验证：`HEAD` 返回 `200`、完整长度、`Accept-Ranges: bytes` 和一年 immutable 缓存；请求 `bytes=0-1023` 返回 `206`、恰好 1,024 字节及 `Content-Range: bytes 0-1023/188969`；请求末尾 64 字节同样返回准确范围；越界请求返回 `416` 与 `Content-Range: bytes */188969`。主页仍返回 `no-store`。这项改动不缩短神经推理时间，但避免完整视频请求占用等量 Node 堆内存，并让浏览器 seek、重试和重复哈希素材只传输必要数据。

新一轮真实首响基线中，“今天有点累，陪我聊两句吧”的 M3 首句为 2,983 毫秒，动作素材切换 286 毫秒；首句独立 TTS 首 PCM 为 745 毫秒，DINet 首个 800 毫秒口型段在语音请求后 1,401 毫秒可用，因此原路径端到端约 4.4 秒，主要等待确认为 M3 正文前的云端波动。新增本地语境接话：服务在 700 毫秒无正文时发候选，前端再等 500 毫秒；真正首句在约 1.2 秒内出现则完全取消，避免快请求多说一句。慢请求则从约 1.2 秒开始接话 TTS/DINet，按本机实测约再 1.4 秒得到首个口型段，即约 2.6 秒产生可见可听反馈，同时 M3 主回答继续并行。120 项自动测试覆盖接话内容、确定性选择、危机分支、快响应取消、慢响应单次触发和页面协议；真人页面回归确认人物就绪且无横向溢出。

接话首响随后继续去除 TTS 串行等待。候选短句在 M3 请求发起时同步启动当前音色的 WebSocket PCM，实际探针中首次 PCM 于 932 毫秒准备完成，早于前端约 1.2 秒的播放决策。真人命中后 `ttsFirstAudioMs` 为 0 毫秒，稳定热态首个 800 毫秒口型段为 276 毫秒、整句分片 644 毫秒；据此慢请求的首个有声口型反馈从上一版约 2.6 秒进一步降到约 1.48 秒的热态路径。一次动作/worker 冷队列样本仍达到 2,105 毫秒，因此新增 `queueMs` 单独观测排队，不把最佳样本冒充所有请求。动漫模式对同一短句、音色和情绪请求返回 `x-speech-cache: hit`，验证同一 PCM 同时生成可复用 WAV。候选失败时正常 TTS 回退仍保留；121 项自动测试与真人页面回归通过。

v12 去掉了 SSE 内的 base64 PCM。新页面明确协商 `binaryAudio`，服务端为每个分片发布只允许本机访问的 128 位随机 URL；二进制存储保留 60 秒、总量限制 8 MiB，用户取消时按 stream ID 立即回收，正常结束则让浏览器在 TTL 内完成拉取。iframe 在收到 segment 时同时启动视频预加载和 `fetch(no-store)`，音频下载不等待视频 `loadeddata`；长度不符或 URL 失效会拒绝无声视频，旧页面仍可使用内嵌 base64。真实短句的两段 PCM 为 25,600 + 12,296 字节，首段响应头准确声明 16 kHz 单声道和 25,600 字节；SSE 由旧模式 50,128 字节降至 1,785 字节，连同原始 PCM 后总传输减少 20.8%。126 项完整测试通过，页面与真人 iframe 可正常加载；内置浏览器出现的一条 `MutationObserver` 错误不来自项目源码，项目中没有该 API 调用。

页面音轨调度随后拆为“并行下载、顺序排程”两层。旧实现虽已让 PCM 与视频并行，但第二段 PCM 的 `fetch` 仍放在第一段的 `audioScheduleChain` 之后，慢下载会把后续所有分片串行拖住。现在每个 segment 到达时立即启动自己的 PCM 请求，Web Audio 排程链只等待对应的已在途 Promise 并按序写时钟；中断令牌在排程前再次核对，迟到的旧请求不会发声。该优化不改变服务端协议和音画时钟，只扩大播放器对短时下载抖动的缓冲余量。

连续 fMP4 与播放反压稳定后，继续修复多句动作互相抢占的问题。浏览器为同一轮回答分配稳定的 `visualTurnId` 和递增句序号；TTS 仍并行启动，但服务端只允许该轮下一句在上一句全部口型分片生成完成后进入 DINet，因此后句不会提前切换常驻 worker 的动作素材。动作素材发生变化时，worker 用上一句末帧对新动作前 4 帧做约 160 毫秒的渐进混合，随后完全进入新素材；同一动作和同一句后续分片不重复过渡。真实“关心→思考”双句探针确认第二句首段 `transitionFrames=4`、其余分片为 0。回答完成或被打断时，页面显式关闭视觉轮次，服务端释放排序门和末帧缓存。

慢请求接话链路仍有一段可消除的本地串行等待：服务端在 700 毫秒发送候选后，页面原先先等完 500 毫秒取消窗，才开始请求已经预热 PCM 的 DINet。现在候选一到页面就投机生成首个 800 毫秒口型片段，同时保留原来的 1.2 秒开口决策点；服务端在首段后暂停，不会提前渲染整句。正文在取消窗内到达时中止候选并释放视觉句序，慢请求确定使用接话时通过 `commit` 放行剩余分片并复用已生成首段。真实接口验证投机会话等待 2 秒仍只有 sequence 0，提交后连续得到 sequence 1、2 和 done；热态可把接话首段准备与 500 毫秒取消窗重叠，理论开口点由约 1.48 秒降低到约 0.98 秒，而快正文的取消规则不变。

随后补齐取消与正文请求并发到达的句序竞态。投机候选会预占本轮视觉 index 0；浏览器取消时除中止流请求外，还显式发送 `visual-turn/:id/skip`。服务端先清掉未展示候选的末帧，再把 index 0 标记完成，因此 index 1 的真实正文无论先到还是后到都能继续，且不会从用户从未看见的姿势做渐变。两种真实乱序均已验证：`skip → 正文` 得到 3 段并 done，`正文等待 → skip` 得到 2 段并 done，没有等待 60 秒超时。

最后把浏览器 abort、显式 cancel、visual skip 和真实正文同时到达的最坏时序做成服务端幂等事务：相同 `turnId:index` 的清理只执行一次，必须等 worker 删除未展示末帧后才推进排序门；投机请求被主动取消时也不再向已结束的 SSE 写一条误导性的 error。真实并发探针中候选只生成 1 段后取消，正文立即生成 3 段并 done，证明没有句序死锁或迟到清理覆盖正文状态。

连续视频进入 fMP4 阶段。DINet worker 可按协商输出 `empty_moov` 初始化信息及 `moof/mdat` 媒体 fragment，固定 20 帧 GOP；真实三段 800/800/896 毫秒文件结构和 SPS/PPS 已核对一致，渲染分别为 295/235/258 毫秒。页面新增严格 MP4 box 解析器和单 MediaSource/SourceBuffer 播放器，使用 `sequence` 模式承接各个独立 fragment，并用共享启动 Promise 消除后段抢先重复 `play()` 的竞态。普通请求复测仍生成 `ftyp/moov/free/mdat` MP4，证明稳定回退没有被新格式污染。

为弥补自动化 evaluate 环境隔离媒体 API 的限制，建立后随即删除了三套同源页面自测，让测试逻辑在网页主执行环境运行、浏览器只读取 DOM 结果。直接三段追加得到连续 2.48 秒缓冲、首帧 37 毫秒、`readyState=4`；正式人物 iframe 通过真实 TTS/DINet 收到三段，仅发出一次 `wav2lip-started`，首帧 40 毫秒、音频边界迟到 4 毫秒，三个 requestId 都正常结束且没有错误；中断测试在首段开始后清空，随后 1.4 秒内没有旧的开始、结束或错误事件。基于这三层证据，连续视频改为默认协商，仍保留 `?continuous=0` 显式回退，并在浏览器不支持 MSE/H.264 时自动回退。

短接话裁剪后重新审计动作帧时钟，发现 `holdMs=Math.max(1400,audioMs)` 被同时当成姿势保持时长和视频实际经过时长。690–770 毫秒的接话会让正式回答从 1400 毫秒后的源帧接管，凭空跳过约 630–710 毫秒动作。现拆开两个时钟：姿势保持仍为至少 1400 毫秒，帧续接只采用流接口报告的真实 PCM 时长，缺少元数据时回退 400 毫秒。页面复测接话 PCM 与 `backchannelContinuationMs` 均为 770 毫秒，视频交接迟到 0 毫秒；完整测试增至 197 项。

缓存审计确认 `/`、`.js`、`.json` 均返回 `cache-control: no-store`，所以前端版本号不变不会导致旧逻辑继续运行；只有内容哈希生成视频使用 immutable 缓存，无需制造无意义的版本更新。随后检查真实浏览器历史，发现修复前的“爱好回答 + 工作疲惫反问”仍会原样进入后续上下文。`recentConversation` 现按上一条用户消息重新清洗每条助手历史；真实诊断中的 provider payload 已把旧句自动改成单纯的“我喜欢傍晚去湖边走走。”，下一轮只回答散步感受。完整测试增至 198 项。

正式回答音频继续抽样发现固定前导空白：“嗯，走的时候心里最安静。”共 3413 毫秒，发声前静音 302 毫秒，句中另有 343/476 毫秒语义停顿，不能整段裁剪。新增只在开流阶段工作的 `Pcm16LeadingSilenceGate`：检测首个有效窗后保留 60 毫秒起音并永久透传，句中/结尾完全不处理。真人接口实测裁掉 230 毫秒，输出 2986 毫秒 PCM，首段 DINet 推理封装 209 毫秒；页面复测正文 1319 毫秒到达、首段 1992 毫秒就绪、音画交接迟到 4 毫秒。完整测试增至 200 项。

接话缓存和时序复审确认 PCM 已在聊天请求发起时预热，但服务端到 500 毫秒才把候选交给页面，动作切换和投机 DINet 仍少用了一段等待窗口。候选准备点提前至 200 毫秒，浏览器取消窗相应从 400 增至 700 毫秒，真实开口决策仍固定为 900 毫秒，所以快正文取消概率和用户听到多余接话的概率都不变。首次冷态规划请求接话在 1052 毫秒开口、正式句 1274 毫秒到达；第二次热态接话首段提前 467 毫秒就绪，973 毫秒开口，正式句 1087 毫秒到达、正式首段 1730 毫秒就绪，音画交接为 0 毫秒。

鼓掌样本的 36 毫秒音画迟到进一步定位到浏览器首帧预解码。连续视频原本只提前 32 毫秒 `play()`，而首帧实测为 62 毫秒，且等待完成后没有暂停，隐藏视频可能比声音早走一帧。新门控使用音频已有的 60 毫秒调度缓冲预解码，首帧到达后暂停，音频边界再恢复并显露。相同鼓掌样本首帧 61 毫秒、交接迟到从 36 降至 0 毫秒；关心样本首帧 63 毫秒、迟到 4 毫秒，后续音频提前量仍为 2.084 秒。

最近四轮诊断显示 M3 首句已在 922–1302 毫秒，但每轮仍携带两段长规划回答，提示达到 900–1039 tokens；长期记忆还把用户的“帮我规划明天怎么安排”误存成待办，在无关的疲惫话题中召回。短期历史改为最近 6 条、每条 600 字、总计 1800 字，超长单条保留首尾而非只留结尾。待办抽取拒绝规划问句，召回要求当前查询与待办主题匹配，旧文件中的“怎么安排”伪待办也会过滤。相同结构的真实关心请求不再召回记忆，首句 1168 毫秒、两句 1356 毫秒结束，回复只围绕当前疲惫感受。

这组三轮采样还抓到一处语义断裂：“今天工作有点累”后的“吃了没？”被普通生活分享兜底误改成“听起来挺特别的。”。根因是疲惫不在兜底排除项，且任何问号都被视为采访。现把疲惫、烦躁、饥饿、困倦纳入关心场景，并把拦截范围收窄到“什么样、什么颜色、哪里、什么时候、和谁”等针对分享对象的细节追问；“吃了没”“要不要休息”保留原意。真实复测输出“辛苦了，事情一多就容易把人压得透不过气。今天有什么特别棘手的吗？”，没有错误替换，首句 1,938 毫秒，TTS 任务在请求后 3 毫秒开始预热。完整测试保持 194 项并扩展关心反例矩阵。

普通回答长度随后用三条真实请求抽样：分享、时间建议和生活建议都只有 1–2 个完整句，没有出现需要全局三句硬截断的失控，因此保留自然长度。抽样却复现“哦？”与“什么事，说来听听。”被拆成两次 TTS/口型的问题。首个不超过 4 字的终止短句现暂存到下一完整句，流结束时仍保证释放独立短答；同一分享请求复测只产生一个正式语音句。候选状态机另增加关闭态：第一正式句与候选不同时立即失效，防止后续相同文本迟到认领已经播完的候选。测试增加到 175 项。

继续审计发现，M3 超过接话阈值时仍有第二个姿势跳变：等待动作虽然已连续，但预生成的接话口型仍从素材第 0 帧开始，正文也不知道接话实际持续多久。现将接话纳入同一动作帧时钟：预热完成的 PCM 时长随事件返回，接话从等待底片当前帧续接，正文按接话完整时长继续，后续句保留该帧偏移基线。真实页面同一句“我今天工作有点累”触发接话时，接话动作计划为第 32 帧，1823 毫秒接话后正文第一句约为第 78 帧，第二句为第 123 帧；页面埋点为正文首句 1432 毫秒、TTS 首包 224 毫秒、首视频段 567 毫秒。临时文字输入开关已恢复，完整自动测试增加到 148 项。

接话连续之后又量化了它对正文的阻塞：旧关心短句实际有 1823 毫秒，且服务端 700 毫秒阈值之后前端还等待 500 毫秒，反馈并不够早，正文还必须排队等长接话说完。默认音色直接实测“嗯。”719.9 毫秒、“我在。”766.3 毫秒、“听着呢。”1021.7 毫秒、“真的呀？”1149.4 毫秒、“我想想。”1056.6 毫秒；“我在。”在甜美、柔和、温暖、成熟、经典御姐、妩媚御姐六类音色中为 0.72–1.40 秒。策略因此改成不超过 5 个正文汉字的语义化反馈，并把前端竞争窗口降至 200 毫秒。最终冷缓存真实链路中“我在。”于 704 毫秒发出、音频 836 毫秒，正文首句 1888 毫秒到达；相对旧实测反馈提前约 552 毫秒，接话占用减少约 987 毫秒。页面复测接话仍从等待动作第 32 帧接管，无回零起势；测试总数保持 148 项但增加接话长度和具体语义断言。

轮次间停顿审计确认播放 Promise 已在共享 PCM 的真实音频尾点结束，随后额外固定 `scheduleListening(180)` 才是可缩短部分；但直接提前开启麦克风会在高延迟输出设备上重新识别人物尾音。现新增纯函数策略：只有 `neuralAvatarProfile && avatarPcmReady` 时，恢复等待取浏览器 `outputLatency/baseLatency + 40ms`，并夹在 80–180ms；其他路径保持 180ms。测试覆盖 0ms→80ms、75ms→115ms、300ms→180ms以及非精确音轨→180ms，完整测试由 148 增至 149 项。页面同时记录设备延迟、计划等待和音频结束到识别 `onstart` 的真实总耗时。内置浏览器和 Chrome 自动化点击都不会产生可信用户手势，实测 `AudioContext` 均未创建，因此本轮明确不宣称已取得真机硬件延迟，待用户实际点击开始通话后由新埋点采集。

继续审计端到端轮次空档后，回答结束到续听的 80–180 毫秒已经接近防止人物尾音回灌的安全下限，主要本地可控等待转到用户说完后的 VAD 端点。原先所有非 final 识别结果都固定等待 650 毫秒；现在依据 final、有效字数、句末标点与承接词动态选择 340–700 毫秒。短词和“但是、因为、如果、我觉得”等未完成语义仍保守等待，完整长句和识别器 final 可提前 90–310 毫秒提交。单元测试覆盖短词、普通句、长句、完整标点、final 以及未完成承接词，页面协议回归验证实际文本与 final 状态均进入策略函数。

M3 正文前波动继续用生产人物提示做对照。把 `max_completion_tokens` 从 400 降到 240 没有提速：三类输入中 240 上限的首正文为 5.12/2.01/3.05 秒，400 为 1.33/1.91 秒，另一次 400 请求把 1748 个字符都用于推理并以 `length` 结束，正文为空。将上限调低会同时挤压隐藏推理与最终正文，不能作为首响优化。随后用 800 上限交替比较当前 M3 与账户可用的 `MiniMax-M2.7-highspeed`；M3 三轮首正文为 1.71/2.19/1.33 秒，高速模型为 2.62/4.52/3.86 秒，因此保持 M3。生产上限提高到 800 仅用于避免推理挤掉正文，提示词仍约束朗读回答为 1–3 句；诊断记录新增结束原因、正文/推理字符数和服务商返回的 token 统计，后续可直接识别 `length` 空答和云端长推理。

连续通话原先在人物回答期间完全停用聆听，用户必须等整段回答结束才能继续。现在保留通话开始时已取得的、启用浏览器回声消除与降噪的麦克风流，并只在人物实际开始出声后运行轻量插话检测：先用 480 毫秒学习扬声器残留与房间底噪，随后要求输入同时高于绝对门槛和底噪 2.8 倍并持续 220 毫秒才判定近场插话。命中后同一代次令牌立即取消 M3 请求、TTS、DINet 流、Web Audio/视频播放与动作，60 毫秒后启动正式语音识别；短促碰撞声会重置保持计时，单个回答最多触发一次。页面记录输入电平、学习基线和命中耗时供真机调参，自动测试覆盖扬声器残留、短噪声、持续人声和缓慢底噪变化。该策略不会在回答前的思考阶段把环境声误判为插话，也没有打开会把人物声音直接送入识别器的常驻全双工识别。

插话功能完成后继续审计取消链，发现浏览器虽然会停止播放器和 DINet，但 `/api/chat/stream` 的 MiniMax `fetch` 没有绑定客户端断开，旧回答可能继续消耗额度并在完成后更新记忆/情绪；提前合成的接话 PCM 也会继续跑。服务端现为每条 SSE 响应绑定一次性客户端生命周期：正常发送 `done` 前显式完成，提前 `close` 则中止 M3 fetch、清除接话定时器、关闭尚未使用的首句 TTS 预连接，并把同一 abort signal 传给投机接话 TTS。只有正常完成的回答才写入结构化记忆和连续情绪。真实探针收到 `meta` 后立即取消，第一版在 7 毫秒标为 cancelled，但接话 PCM 仍于 554 毫秒完成；补齐信号后第二版在 6 毫秒取消，`rawModelText=0`、无 final，接话 PCM 状态也为 `cancelled`。取消被视为正常交互，HTTP 外层不再把它写成连接错误事件。

动作触发回归复现了过去“明确说鼓掌却不鼓掌”的机制性原因。`inferCompanionState` 原先先匹配关心词，再匹配动作；调度器首句又允许模型回复动作覆盖初始动作，因此“我很累，给我鼓掌鼓励一下”会先被“累”改成关心，或被回复“很棒”改成点赞。现新增明确动作请求解析，安全危机仍最高优先级，明确动作先于普通情绪；调度器在 `explicit` 轮次锁定首句主动作且不执行短开场延后。14 类动作矩阵分别用相反的回复候选做回归，全部保持用户点名动作，并补齐“向我挥挥手”“鞠个躬”两种自然说法。第一次真实链路虽稳定得到 `clap`，但暴露模型输出“啪啪啪～”及“辛苦了，真的。”碎分句；清洗器现移除句首或“来，”引导的连续啪声，快速逗号分段阈值由 6 字调到 9 字，最多 4 字的终止小句会并回上一片。最终同一冲突请求只产生一个自然完整句且全程 `clap`。新增两项动作矩阵测试后，完整测试由 149 增至 153 项。

插话取消后又检查了字幕和浏览器短期历史。旧页面在 SSE 收到句子时立刻展示并最终写入全部文案，口型渲染还在排队时用户打断，会留下人物没有真正说过的后续内容。新增独立 `ReplyTranscript` 状态机：生成句、开始播放句、完整播完句和最终文本分开记录；真人口型首帧、HTML Audio、浏览器语音三条播放路径都在真实开始事件上显示字幕，并在真实结束事件上提交历史。流式真人的一句话可能包含多个 480/800 毫秒片段，因此只把该句最后一个片段结束作为完成点。正常结束提交完整最终文本，插话和网络异常仅把按顺序完整说完的句子写入模型上下文，当前开口但未结束的字幕只留在页面，未开口则不产生助手历史。六项状态机测试和页面接线回归覆盖正常完成、中途取消、开口前取消、非连续乱序完成及重复结算。

默认开启前补充了长回答漂移保护。连续视频记录第一段 PCM 的绝对起点；每个后续 fragment 可用时比较 `AudioContext` 推导的期望时间与 video `currentTime`，25 毫秒以内保持连续解码，只有画面明显落后才 seek 到已缓冲范围内，并确保暂停状态恢复播放。当前漂移和整轮最大漂移写入人物容器，便于真机长期采样。纯函数测试覆盖 10 毫秒不跳、100 毫秒追赶及不越过媒体尾部；完整测试由 129 项增加到 130 项。

长回答压力审计先发现失败：15 个 800 毫秒片段在首帧前全部进入 SourceBuffer，最大前向缓冲达到 12 秒，证明最初仅在 `started` 后检查容量没有真实背压。修正后，视频超过 4 秒便等待播放消耗再下载下一片，播放点后方超过约 3 秒的范围通过同一 SourceBuffer 操作队列回收；Web Audio 同样限制约 4 秒预排程。12 秒真实页面复测得到视频最大 4.8 秒、音频最大 4.78 秒、历史回收 3.121 秒，始终只有一次视频启动，15 段全部结束且无错误。临时压力页已删除，完整测试增加为 132 项。

随后把背压传回 DINet。会话默认窗口为 6 个未确认 segment，播放端以独立 POST ack 放行下一个渲染；未协商的新旧客户端不受影响。无 ack 的真实长句严格停在 sequence 0–5，确认 0 后只生成 sequence 6，证明窗口在神经渲染之前而不是 SSE 发送之后生效。首次全链路复测又发现生成结束会过早删除 session，导致最后 6 段无法确认；生命周期因此拆为生成完成和播放完成，保留 60 秒轻量确认态，最终 ack 或超时才释放。修复后真实 15 段得到全部确认、最大未确认 6，前六段生成跨度 1.188 秒，第七段在首个 ack 后 560 毫秒到达，无播放错误。取消会唤醒被窗口阻塞的 renderer，错误不会以 ack 放行更多计算，而是取消整个流。

长时间连续聊天的资源审计确认，生成视频已有 384 文件/128 MiB 上限，外部 PCM 已有 60 秒 TTL/8 MiB 上限，正常播放确认也会释放流会话；缺口是客户端建立 DINet 会话后既不完成也不取消时，开放 session 和 worker 状态没有截止时间。现为开放流增加 60 秒活动超时，开始、追加音频及有效渲染都会刷新期限；超时统一清除音频块、背压等待、PCM token 和 worker 状态。生成完成会立即取消开放态计时器，继续由播放确认留存期负责。状态接口同步加入流会话数量和缓冲字节。真实服务创建一个空会话后观察到 `sessions/open` 从 `0/0` 到 `1/1`，取消或超时后恢复 `0/0`，PCM 暂存保持 0；新增测试还验证持续追加会刷新而不是误触发截止时间。

下一项性能候选先用真实 `speech-stream` 探针否证。3.732 秒语音的 TTS 首 PCM 为 804 毫秒、首视频为 1298 毫秒；首个 8 帧片段 worker 总耗时 200 毫秒，后续 20 帧片段为 265–273 毫秒，其中每次 FFmpeg 封装只有 10–21 毫秒。首段额外约 200 毫秒来自探针直接切换点头素材，正常聊天已有回答等待期预热。因此当前把每片段 FFmpeg 改成常驻单编码器的风险和收益不匹配，没有为了架构形式重写稳定链路。

行为审计随后发现真正的体验缺口在用户讲话期间：动漫原有延迟点头，但连续识别结果可能在同一轮重复排程；真人则完全静止。新增独立 `ListeningGestureGate`，一轮只接受一次调度，取消和下一轮重置有确定性测试。真人与动漫都在有效文字持续 1.4–2.1 秒后给一次克制反馈；真人底片通过非循环预览协议播放并在 3.6 秒自动回待机，识别提前结束则立即清理。素材前半段按 0.2 秒采样，动作变化在约 2.2 秒达到峰值、3.4–3.6 秒接近回正，因此没有在最大幅度处硬切。内置浏览器确认新页面与真人 iframe 就绪；其不支持真实 Web Speech，语音事件次数由注入时钟的状态机测试证明，不用页面加载冒充麦克风实测。

标准真人聊天探针“我今天把计划里的事情都做完了，感觉挺开心的”暴露语义优先级错误：旧规则因裸词“计划”返回 `thinking`，连 203 毫秒接话、154 毫秒素材预热和正式句都使用思考。现把规划判断收窄为请求/疑问/制定语境，并把“做完了、办完了、搞完了”补入完成成就规则。相同输入重启服务复测为 `meta=excited/clap`、接话保持低幅 happy、正式句 `action=clap`；鼓掌素材在 M3 等待期 152 毫秒完成预热。对照测试同时确认“我明天计划去公园”不思考，“帮我制定一个明天的计划”仍思考。两轮临时用户记忆已清理。

首句 TTS 预连接做了跨接口闭环，而不只检查 `speech-ready` 事件。聊天接口签发并预热的任务在 12.8 秒后仍由口型接口成功领取，返回 `connectionReused=true`、`taskPrimed=true`、`connectionWaitMs=0`、`taskWaitMs=0`；该句 TTS 首 PCM 为 230 毫秒、口型首段为 468 毫秒。对照未复用请求为 804/1298 毫秒，说明预连接确实消除了约 574 毫秒 TTS 建连等待，并把首段提前约 830 毫秒。页面现在把复用、任务预热和提前量写入人物容器，每轮开始先清空旧值，便于后续真实通话发现租约丢失。临时测试记忆已清理。

同一预连接探针还暴露“所有问号都思考”的动作过拟合：晚上好、吃饭了吗、在干嘛、一起散步、陪我聊天、天气好吗等 13 条常见问句原先几乎全部返回 `thinking`。现拆分为问候挥手、社交关心/邀请轻点头、普通事实问句安静待机、分析决策与规划请求思考；个人外观确认问句也使用低幅认可，不摆出分析姿势。矩阵测试覆盖 13 个正反例。重启后的真实“晚上好，今天过得怎么样？”复测为 `meta=happy/wave_approval`、接话挥手、正式首句挥手；客户端高幅动作预算保证第二句回待机。临时测试记忆已清理。

首句任务预热的正确性随后补做失配审计。MiniMax 的 `task_start` 已固定模型、音色和情绪，旧领取逻辑却只凭随机 ID 复用；当本地初始判断与模型实际首句情绪不同时，可能以更低延迟播放错误语气。连接现记录标准化任务配置，服务端领取层和底层 PCM 流都要求模型、解析后的白名单音色、标准化情绪完全一致；`excited → happy` 等等价映射仍可复用，真正失配则立即关闭旧任务并走正常新连接。真实探针把 `happy` 预热任务交给 `sad` 首句，最终 `connectionReused=false / taskPrimed=false`；连续同配置探针为 `true / true`，TTS 首 PCM 212 毫秒、人物首段 408 毫秒。三条临时用户记忆均已清除。

下一轮诊断把注意力放回 M3 已输出正文后的可控空档。旧建议样本首个干净文本在 1664 毫秒出现，但固定 9 字逗号门直到 1997 毫秒才释放首句，额外等待 333 毫秒。没有把全局门槛重新降回 5 字，而是只放行“睡、吃、喝、去、找、先、别、不妨”等动作开头、至少 5 字且可独立朗读的短建议；情绪开场、从句、评价半句和“周六上午学习，下午……”式枚举仍等待完整语义。三轮真实输出分别以“不如试试睡到自然醒，”“去一个你从没去过的地方走走，”“睡到自然醒，”开口，首文本到首句间隔为 141/171/0 毫秒，没有短拟声或寒暄碎片。完整首句流水线中“放下手机，去附近的公园或者菜市场走走，”在 1771 毫秒下发，预热 TTS 首 PCM 273 毫秒，真人首个 320 毫秒片段在整轮 2292 毫秒产生；临时测试记忆已清理。

同一性能样本的行为语义原先被目标词“开心”误判成用户已经高兴，等待阶段错误使用 happy 和“嗯。”。分析请求现识别“认真/仔细想一下”“给我建议/主意/方案”，优先于目标情绪；真实请求复测为 `meta=curious/thinking`、接话“我想想。”、首句 thinking，过去式“我认真想了一下”保持普通陈述。首轮真实回复还在三句建议后追加无必要反问；普通建议现最多三个完整句，并只过滤“最近有什么想做的吗”这类泛化参与尾问，缺少材质、预算等关键条件的澄清仍保留。

随后发现 MiniMax 偶尔把整条逗号列表放进同一个 SSE 数据块，`includeClauses` 在单次循环中保持为真，导致“睡到自然醒，去巷子逛逛，买点小吃，心情会很好。”一次拆出四个 TTS。分句器增加单次返回上限，快速模式只领取第一段，剩余原文回到缓冲区并关闭后续逗号边界。最终真实复测只下发“睡到自然醒，”和“然后去一个没去过的街角逛逛，随手买点喜欢的小东西，心情会很好。”两个朗读分段；前段保持思考，后段自然转为轻点头，无尾问。三条临时记忆已清理。

服务重启后的 M3 长尾进一步做了冷启动假设验证。第一轮等待上游响应头约 3 秒，而后续约 1 秒，看似是后台文案预热和首请求竞争；实验版因此并行等待 M3 与 DINet 两项预热后才监听端口。两次冷启动的预热都约 1.2 秒并明确 ready，但首轮正文分别为 1.629 秒和 4.064 秒，后者仍出现完整长尾，证明就绪门控不能稳定解决供应商波动。该实验代码已撤回，避免无收益地延迟服务上线；200 毫秒语义接话继续覆盖长等待，未启用会增加调用费用的双请求竞速。

第二次冷启动回复还捏造“最近天气挺好”“你这两天节奏很紧”。系统提示现明确禁止无依据声称天气、行程、工作强度、作息和状态；本地只对天气与忙碌两类高频句首假设做窄范围清理，且证据只来自用户消息。确定性测试确认无上下文时分别得到“要不周末找个公园走走”“换个环境放松一下最合适”，用户确实提到天气或工作忙时完整保留原句。临时冷启动测试记忆已清理。

流式边界审计又复现一条清理副作用：“看你这两天工作挺忙，换个……”的前缀超过 9 字且不以依存词结尾，会被首逗号提前释放；事实落地清理把整段删空后，通用最终兜底却会生成“我在听。”，错误抢占首句。`buildMiniMaxReply` 现只在流式分段调用中允许空正文，服务端在冻结 TTS 租约和设置 `firstSentenceEmitted` 之前静默跳过，并累计不含正文的过滤计数；正常整轮接口仍保留空答兜底。测试覆盖同一句在流式模式返回空、最终模式返回“我在听。”以及跳过语句位于租约冻结之前。

事实依据匹配继续做同字异义反例：旧规则只要用户文本出现“热”就会把“热闹的周末”当成天气证据，只要出现“事情”就会把“周末做什么事情”当成繁忙证据。现改成语境化短语，测试覆盖热闹/冷静不支持天气猜测、事情/工作单独出现不支持忙碌猜测，同时保留“最近天气很好、今天很热、最近工作很忙、我累了”。两条真实 MiniMax 抽样分别得到火锅/KTV/市集建议和散步/吃饭/电影建议，流式正文没有天气或忙碌猜测；临时记忆均已清除。

动作跨句过渡随后做了真实像素级验收，而不只依赖 worker 返回的计数。使用同一个 `visualTurnId` 连续生成“我认真想一想。”（thinking）和“这样应该不错。”（nod）：第二句只有首个视频分片报告 `transitionFrames=4`，后续两个分片均为 0，证明淡化不会在每个 800 毫秒分片重新发生。将上一句最后一帧与第二句前 5 帧逐帧计算 SSIM，得到 `0.981266 → 0.963768 → 0.942464 → 0.919191 → 0.896177`，与 0.2/0.4/0.6/0.8 的渐进权重一致。当前句界没有跳帧，无需调整人物动作；新增回归测试锁定跨动作、非首句、4 帧上限、混合公式和末帧继承。

新一轮首响采样再次表明本地口型已不是主慢点。“下班后有点累”的 M3 首句为 3006 毫秒，但语义接话 203 毫秒发出、PCM 611 毫秒就绪；用同一缓存真实生成 320 毫秒 caring 首段只需 140 毫秒，因此页面并行路径约 751 毫秒即可具备接话音画，早于 900 毫秒播放门。规划请求出现 9559 毫秒的 M3 长尾时，“我想想。”仍在 201 毫秒发出，说明接话对长尾有实际价值。礼物探针同时暴露“希望你喜欢”被偏好问句误判，接话错误为“这个嘛。”；规则现把礼物感谢前置并收紧偏好疑问条件，重启后同一句真实 SSE 得到 `meta=happy/caring`、接话“谢谢你。”、正式首句“谢谢你的心意，真的很惊喜。”。页面再按实际播放状态去掉连续致谢，最终口语衔接为“谢谢你。你的心意，真的很惊喜。”，未播放的候选不触发裁剪。

### 9.31 不增加文本请求的长尾衔接

继续审计 M3 参数前先核对了 MiniMax 官方 OpenAI 兼容接口文档。`reasoning_split=true` 的作用是把思考内容从正文分离到独立字段，官方没有把它定义为关闭推理或限制推理预算的开关；因此没有删除该参数，也没有用未经证明的参数调整冒充提速。此前相同角色提示对 highspeed 模型的真实对比也没有获益，本轮不再重复调用供应商接口。

12.9 秒异常样本里，约 700 毫秒的第一句接话结束后仍会留下很长的安静等待。现增加第二层但严格收窄的衔接：仅当用户明确要求分析、建议或规划，且 3200 毫秒仍没有正式首句时，服务端发送一次带 `kind=long-wait` 的“这个我再想仔细一点。”；浏览器继续保留 500 毫秒竞争窗，所以实际最早约 3700 毫秒开口。普通问候、生活分享和“我饿了”均返回空计划；正式句在竞争窗内到达会取消尚未播放的准备，已经开口则完整说完再按队列衔接正式回答。该策略不复制 M3 请求、不编造问题答案，也不会对每轮重复说填充语。

验证没有再次调用 MiniMax。确定性测试覆盖分析与规划命中、问候/普通分享/饥饿不命中、3200 毫秒阈值与 700 毫秒首接话时序分离、浏览器接线和服务端事件接线；首次定向运行因浏览器时序镜像缺少新增常量被一致性测试拦截，同步后同一组 74 项全部通过。页面脚本版本升级为 `20260814-long-wait-v39`，避免旧模块缓存掩盖结果。

此前服务端诊断能看到上下文、M3 响应头、首正文和总耗时，页面数据属性能看到 VAD、TTS、DINet 与真实视频起播，但两边没有稳定轮次标识，只能人工比对时间相近的记录。这既容易错配，也会诱导为了取完整数据而重复发送测试问题。

### 9.33 热重载退出与端口释放

端到端计时上线后读取最近诊断为空，说明尚无新的用户自然聊天样本；本轮没有为了填充指标主动请求 MiniMax。改为处理 9.30 已明确记录的开发启动竞态：旧实现没有统一信号收尾，Node watcher 重启时 HTTP、尚未消费的 TTS 预连接与 DINet Python worker 各自结束，曾出现旧实例仍占用 3000 端口、新实例立即监听而报 `EADDRINUSE`。

DINet worker 现有幂等 `close()`：拒绝退出后新任务、结束活动任务、先发 `SIGTERM`，1 秒仍未退出才发 `SIGKILL`；渲染仓库向服务端暴露同一关闭入口。服务端首次收到 `SIGTERM/SIGINT` 时关闭全部 TTS 预连接、停止 HTTP 监听并关闭 DINet，重复信号复用同一 Promise；2 秒是整个退出流程的最终保护，不允许 watcher 永久等待。

真实验证启动时设置 `MINIMAX_CHAT_WARMUP=0`，没有发生文案供应商调用。服务就绪后确认 Node PID 37288 独占 3000 端口，发送 `SIGTERM` 后执行会话在 1 秒检查窗口内以退出码 0 结束，随后 `lsof` 确认端口无监听者。再次以相同无文案预热配置启动稳定实例，`/api/health` 与 `/api/dinet/status` 均正常。定向 12 项与最终完整 222 项本地测试通过，`git diff --check` 无错误。

### 9.34 最近自然聊天的匿名延迟汇总

服务重启后 `/api/chat/debug/recent` 暂无用户自然聊天记录，本轮没有主动生成测试对话。为让后续三次以上的正常使用直接形成决策依据，新增 `/api/chat/debug/summary`：从最近 20 条内存诊断提取供应商响应头、M3 首正文、首次真实开口、正式正文开口、VAD 停止到开口、TTS 首 PCM、DINet 首片段、视频首帧和交接误差，分别给出样本数、P50、P90、最大值及目标内比例。它还统计第一次声音来自普通接话、长尾衔接或正式正文，防止把“700 毫秒说了嗯”误当成正式答案已经开始。

### 9.35 修正人物渲染阶段的重复计时

继续追踪指标起止点发现，页面旧 `avatarPipelineMs` 来自服务端 `firstSegmentAt - pipelineStartedAt`：计时从人物语音请求进入时开始，因此包含 TTS 首 PCM、积累 320 毫秒音频尾部、DINet 排队和首片段渲染。若把它与 `ttsFirstAudioMs` 并列比较并命名为人物渲染，会重复归因 TTS 等待，可能把语音慢错误判断成 DINet 慢。

DINet 每个真实 segment 已有 `segment.renderMs`，其起点位于取出足够 PCM 之后、调用 `renderer.render()` 之前，终点是首片段返回，包含该片段实际排队与渲染但不包含前面的 TTS。页面现在在第一条非投机正式片段到达时记录 `avatarRenderMs`；汇总保留 `speechPipelineFirstSegment` 表示完整人物语音流水线，另用 `avatarRender` 表示可归因于人物首片段的时间，`dominantStage` 只比较后者。构造样本中总流水线 1900 毫秒、纯渲染 1200 毫秒时正确保留两项并判定 `avatar-render`；若纯渲染低于 M3，则不会因总流水线包含 TTS 而误判。定向 15 项与最终完整 226 项本地测试通过，没有调用外部服务。以关闭文案预热的方式重启后，真实汇总接口同时返回空样本 `speechPipelineFirstSegment` 与 `avatarRender` 两项，确认运行版本已经使用校准后的阶段定义。

### 9.36 长尾接话的真人可见帧时钟

第二次长尾衔接加入后继续审计动作连续性，发现语音队列虽然严格有序，旧 `backchannelContinuationMs` 只取接话 PCM 时长。第一次“我想想。”结束后，背景思考预览会在等待 M3 的静音间隔继续播放；若正式正文 4–12 秒后才到，按约 690 毫秒音频推进会回到几秒前的素材帧。第二次“这个我再想仔细一点。”也可能从思考动作第 0 帧重新生成，形成身体或手臂轻微回跳。

新增 `backchannelVisualElapsedMs`：第一次接话在真实开口回调记录 `startedAt`，后续使用当前墙钟差与已知 PCM 时长的较大值；尚未实际开口时仍安全回退音频时长。长尾第二次接话准备时继承第一次动作、基础帧和可见时间，正式正文再从最近一次接话的可见时间继续，并保留 320 毫秒首片段提前量。这样静音间隔里的思考预览不再从动作时间轴中消失，真人源帧仍经过 222 帧循环归一化。

确定性测试使用首次开口 `1000ms`、当前 `3100ms`、音频 `690ms` 的构造状态，结果正确取可见 `2100ms`；墙钟只有 `400ms` 时仍取音频下限 `690ms`，未开口时也不误用当前绝对时间。接线测试确认第二次长尾事件继承 `backchannelVisual`、实际开口设置墙钟、正式正文使用同一函数。定向 38 项和最终完整 227 项测试通过，没有调用外部服务；页面版本升级为 `20260814-visible-clock-v41`。关闭文案预热重启后，主页实际返回该脚本版本且健康检查正常。

### 9.37 跨重启的匿名延迟样本

继续排查时确认了一个验证链路瓶颈：完整诊断只保存在 Node 内存中，每次代码重启都会将延迟样本清零。这会让开发过程中已经做过的真实验证无法累积，容易反复调用 MiniMax 去重新取样。本轮不再重复云端请求，而是先修复这个验证基础设施。

播放结束时现在从内存 trace 中提取独立的匿名样本。白名单只包括 M3 连接/首句、第一次真实开口、正文开口、VAD 到开口、TTS 首 PCM、含 TTS 的人物首片段总流水线、DINet 自身渲染、视频首帧和交接误差等 0–180000 毫秒数值，以及 `backchannel / long-wait / formal` 三种首响类型。精确时间戳、`traceId`、用户 ID、聊天正文、历史、人物设定和模型正文都不进入样本。

样本库默认位于 `data/chat-latency-samples.json`，最多保留最近 100 条，先写临时文件再原子替换，权限固定为 0600。汇总接口合并已落盘样本和当前进程尚未完成播放的实时 trace；同一轮收到重复完成事件也只落盘一次。这样服务重启不再丢失性能趋势，原始聊天诊断仍然保持“仅内存”。验证使用临时目录连续写入 4 条后重建存储实例，确认上限 3 时只恢复 `800/900/1000ms`，磁盘内容不含注入的正文、ID 和时间戳，文件模式为 0600。定向 18 项及最终完整 229 项本地测试全部通过，`git diff --check` 无错误，全程没有调用外部模型。以 `MINIMAX_CHAT_WARMUP=0` 重启真实服务后，健康检查正常，汇总接口返回 `persisted=true`、`storedLimit=100`、`sampleCount=0` 与 `dominantStage=insufficient-data`；空库不伪造瓶颈结论，之后的自然聊天会自动累积样本。

### 9.38 接话结束到正文开口的沉默空档

匿名汇总已能分别首次接话和正式回答的开口时间，但两者直接相减会把接话自身的播放时长也算成空白，不能回答“人物说完我想想后又冷场了多久”。页面现在在每段接话真实播放完成时记录相对本轮请求的毫秒值，并在正文真实开口事件中一并上报。服务端只在首响确实是 `backchannel` 或 `long-wait`、两个时点都有效且顺序正确时，计算并落盘 `backchannelToFormalMs`。没有接话的直接正文不伪造 0 毫秒样本。

汇总接口新增 `metrics.backchannelToFormal`，给出样本数、P50、P90、最大值和 3 秒内比例。这一项不增加 MiniMax/TTS 请求，也不保存接话文案；只用用户之后的正常对话就能区分“首响快但正文接不上”与“整体流程连续”。确定性构造样本中，接话在 1410 ms 结束、正文在 2210 ms 开口，汇总正确得到 800 ms；首响已是正文的样本被排除。定向 17 项测试通过，`git diff --check` 无错误，没有调用外部模型。页面资源版本更新为 `20260814-latency-gap-v42`，避免已打开页面继续运行旧上报逻辑。以 `MINIMAX_CHAT_WARMUP=0` 只重启一次服务后，健康检查正常，首页实际返回 v42，空样本汇总已包含 `backchannelToFormal` 且仍返回 `dominantStage=insufficient-data`，没有为了验收伪造对话。

### 9.39 取消默认 M3 启动预热与空计时污染

启动路径复查发现，`MINIMAX_CHAT_WARMUP` 旧默认是开启：只要没有显式写 `0`，每次 `npm start` 都会自动向 MiniMax 发一次“你好”文案请求。这与本文 9.29 之后的开发验收已持续使用 `MINIMAX_CHAT_WARMUP=0` 不一致，也与 9.24 的否证实验冲突：两次冷启动中预热均约 1.2 秒且明确 ready，但随后真实首句仍分别为 1.629 秒和 4.064 秒，无法稳定解决供应商长尾。频繁代码重启时，这条请求只会重复计费，并可能与用户立即发起的首轮对话竞争上游资源。

现在只有环境变量精确为 `MINIMAX_CHAT_WARMUP=1` 才会执行该 8 秒上限的可取消预热；未配置、空值和 `0` 都不发起文案请求。DINet 本地预热保持不变，因为它已明确消除首轮约 5 秒的本地模型加载。`/api/health` 增加 `chatWarmupEnabled`，使实际状态可验证而不需猜测。同时修正页面计时转换：旧 `Number("")` 会将缺失的 TTS/DINet 指标伪造为 0 ms，现在对未定义或空字符串直接省略，避免拉低聚合 P50。

定向 28 项测试验证显式开关、健康接线、空值过滤、新页面版本及原有真人/动漫路径，`git diff --check` 无错误，没有调用外部模型。页面版本升级为 `20260814-honest-timing-v43`。服务级验收直接使用未携带该环境变量的普通 `npm start`；启动后 `/api/health` 实际返回 `chatWarmupEnabled=false`，首页返回 v43，服务保持运行。该验收没有为测试开启 `1`，因此没有反过来触发要避免的云端预热。

### 9.40 较高稳定底噪下的语音端点

连续通话前半段复查没有再发现重复的固定提交计时器，但找到一个会让用户感觉“说完了却一直不回答”的 VAD 边界。旧内联算法的底噪初值为 0.008，只在启动后 320 ms 内且 RMS 低于 0.025 时学习。若稳定风扇/空调声为 0.03–0.04，它会始终高于固定判定阈值，因而永远不进入静音计时，只能退回延迟不定的浏览器 `onend`。

新 `SpeechEndpointDetector` 把底噪学习与语义停顿分开。它允许启动期学习高于 0.025 的稳定环境声，但将单次学习值限制在静音阈值的 88%，并把最终动态阈值封顶为 0.045。这样立即开口的 0.08 语音始终高于阈值，不会把自己学成背景；0.035 稳定底噪在真实语音结束后则能进入静音。只有 Web Speech 已有非空转写时才累计端点，持续发声会清零已开始的静音区间；原有 340–700 ms 的短词、完整句和承接词语义阈值完全保留。

四个确定性场景单独覆盖安静房间的语音后停顿、0.035 稳定底噪与 0.08 语音、启动瞬间立即说话，以及静音期间恢复说话后清零计时。连同原有识别收尾和真人/动漫页面接线共 19 项定向测试通过，`git diff --check` 无错误，没有调用外服务。底噪与阈值诊断属性只每 250 ms 刷新一次，端点检测仍逐帧执行，避免可观测性造成每帧 DOM 写入。页面版本升级为 `20260814-noise-endpoint-v44`。普通默认配置重启后，健康接口仍为 `chatWarmupEnabled=false`，首页返回 v44，新端点模块以 JavaScript 200 正常提供，服务保持运行。

### 9.41 插话停止时间回到 200 ms 目标

取消链路复查确认，本地命中插话后已经会同步提高 `speechBatch`、中止聊天 SSE/M3 fetch、取消所有流式 TTS/DINet、停止 Web Audio 节点与 fMP4 画面、关闭视觉轮次，并只保留用户真正听完的历史前缀。没有发现第二套遗留播放器或取消后重新恢复旧聆听的竞态。

但默认 `BargeInDetector` 要求输入持续 220 ms 才触发，已经超过 9.15 定义的“用户打断后 200 ms 内停止旧会话”目标，也会让“停”、“等等”等短插话更难命中。现将默认持续时间缩短为 160 ms；480 ms 扬声器残留学习、`max(0.032, baseline×2.8)` 能量门槛、低于持续时间就清零以及单轮只触发一次的保护均保持不变。这只减少已经越过能量门槛后的确认时间，不把一次敲击或扬声器泄漏放宽成近场语音。

新默认行为测试先在 480 ms 学习期后输入一段不足 160 ms 的高能瞬态，用低能样本明确复位，再输入完整 160 ms 近场人声；只有后者触发，触发后再次采样也不会重复中断。连同扬声器残留、慢底噪适应、整页真人/动漫与流式取消接线共 13 项定向测试通过，`git diff --check` 无错误，没有调用外部服务。页面版本升级为 `20260814-fast-barge-in-v45`。服务只重启一次完成运行态验收：普通 `npm start` 后 `/api/health` 返回 `ok=true`、`chatWarmupEnabled=false`，首页实际加载 v45，浏览器获取的 `barge-in-detector.js` 默认值为 `triggerMs=160`；整个验收没有生成测试对话或调用外部模型，服务保持运行。

### 9.42 240 毫秒真人首段的本地模型验收

匿名自然聊天汇总仍为 0 个样本，因此没有凭空判断 M3、TTS 或人物渲染谁是下一主瓶颈，也没有为了填充数据发测试对话。静态关键路径显示，连续真人流上一版必须同时积累 320 毫秒首段与 160 毫秒尾音，即收到至少 480 毫秒 PCM 才会开始首段 DINet；代码中的 320 毫秒下限没有对应的模型能力证明。

本轮只做一个新变量的受控本地验证。最初在文件沙箱内启动 worker 因 OpenGL/图形运行环境以退出码 134 终止，没有把这次环境失败当成模型结论，也没有重复生成素材；随后在与正式服务相同的本机运行环境启动一次常驻 worker，向真实 `StreamingAudio2BlendShape → DINet → libx264 fMP4` 路径提交 240 毫秒、16 kHz、单声道 PCM，并明确请求 6 个 25 fps 输出帧。worker 返回 `audioMode=stateful`、`fragmentedVideo=true`、`frames=6`，声学 2 毫秒、帧渲染 166 毫秒、封装 20 毫秒、总计 188 毫秒，证明 240 毫秒是可工作的真实模型窗口，而不是只通过模拟 renderer 的单元测试。

连续 fMP4 首段因此从 320/8 帧缩为 240/6 帧，160 毫秒保留尾音不变，首次开渲染所需累计 PCM 从 480 缩到 400 毫秒，固定减少 80 毫秒等待；后续分片仍为 800/20 帧，普通 MP4 兼容路径仍为 800 毫秒首段和 240 毫秒尾音。页面动作预览接管提前量同步改为 240 毫秒，避免口型首段少 2 帧后仍按旧偏移跳过源动作。定向验证只运行流式会话、DINet 接线与统一真人/动漫页面三组，共 42 项全部通过；没有调用 MiniMax、TTS 或聊天接口。页面版本升级为 `20260814-first-segment-v46`。重载时先发现一个旧 Node 子进程仍占用 3000 端口，核对到精确监听 PID 后只终止该实例再启动一次；最终 `/api/health` 返回 `ok=true`、`chatWarmupEnabled=false`，`/api/dinet/status` 返回 `ready=true`、零活动 PCM/stream，首页加载 v46，实际提供的 `app.js` 返回 `AVATAR_FIRST_SEGMENT_LEAD_MS=240`。服务保持运行，运行态验收同样没有生成对话或调用外部模型。

### 9.43 浏览器 final 结果不再重复等待 VAD

继续审计“用户说完到聊天请求发起”的固定等待，确认页面把 Web Speech 配置为 `continuous=false`，但收到 `isFinal=true` 后旧逻辑只更新文字，仍要等本地 VAD 再累计 340 毫秒（普通 final）或 430 毫秒（两字以内 final）静音才请求停止。非连续识别的 final 已是浏览器确定的本轮语音边界，第二个端点判断不会产生新的文字修正，因此这段属于可删除的串行等待。

`RecognitionTurnGate.update()` 现在收到非空 final 就立即以 `trigger=final-result` 单次提交；页面同时停止 VAD、清理倾听动作并结束当前识别。final 到达时刻被记为端点，`stopToCommitMs=0`，所以匿名汇总不会因为走快路径而丢失该样本，也不会把它标成 VAD。若 VAD 已先请求停止、浏览器在 90 毫秒修正窗内返回 final，仍使用修正后的完整文本并保留真实的 `stopToCommitMs`。只有 interim 文字继续采用 420–700 毫秒语义自适应停顿；90 毫秒最终修正上限、提前 `onend`、识别失败取消和单轮去重全部保持。

确定性时钟新增“final 在 VAD 之前到达”的场景，证明它立即提交、没有计时器且迟到 VAD 不能重复提交；原有“VAD 后 24 毫秒收到修正 final”、90 毫秒超时、12 毫秒提前 `onend`、失败取消、较高稳定底噪与真人/动漫页面接线继续通过。三组定向测试共 20 项全部通过，没有调用 MiniMax、TTS 或聊天接口。页面版本升级为 `20260814-final-submit-v47`。服务只重启一次，启动前确认 3000 端口已释放；最终 `/api/health` 返回 `ok=true`、`chatWarmupEnabled=false`，首页实际加载 v47，运行脚本同时包含 `recognition.continuous=false` 与 final 立即提交分支。服务保持运行，验收没有生成对话或调用外部模型。

### 9.44 正式开口即保留匿名首响样本

继续检查首句分段时，没有删除逗号后的两个字预读、短感叹词合并、从属句起止规则或首句单分片预算：现有确定性反例证明这些门槛会阻止“如果……，”“辛苦了，”“哇，”等半句单独启动 TTS，盲目压缩会牺牲自然度。本轮转而定位到验证链路的真实缺口：匿名样本旧边界是 `playback-ended`，用户已经听到正文后插话、结束通话或刷新页面，整轮未完成就不会落盘，因此正常使用也可能长期显示 0 样本并诱发重复测试。

持久化边界现在提前到 `formal-speech`，即真人首个口型段或动漫/普通音频实际开始播放正式正文的时刻。普通接话和长尾衔接不会单独落盘；接话之后正式正文一旦开口则保存完整的首次接话类型、首次开口、正文开口及两者空档。直接正文路径中 `first-speech` 与 `formal-speech` 是两个并发的本机上报，服务即使先收到后者，也会把该 formal 事件作为同一轮首响回退，不因事件到达次序丢字段或保存两条样本。

为了让提前保存的样本仍包含可归因阶段，人物语音 SSE 在首个有效 PCM 到达时新增 `tts-first-audio`，页面当场记录 TTS 首包；首个视频 segment 到达时用该语音请求本地起点记录包含 TTS 的首片段总流水线，并继续记录 DINet 自身 `renderMs`。原有 `done.pipeline` 只作为兼容补录和连接复用诊断，不再是首响指标的唯一来源。五组定向测试共 30 项通过，覆盖直接正文事件乱序、接话后正文、字段白名单、0600 匿名落盘、流式阶段事件和真人/动漫页面接线；没有调用 MiniMax、TTS 或聊天接口。页面版本升级为 `20260814-formal-sample-v48`。服务只重启一次，启动前确认端口为空；最终 `/api/health` 返回 `ok=true`、`chatWarmupEnabled=false`，首页加载 v48，实际脚本包含 `tts-first-audio` 和首 segment 本地流水线计时。匿名汇总仍正确返回 0 样本和 `insufficient-data`，没有为了验收伪造自然对话；服务保持运行。

### 9.45 跨句同动作使用真实源帧连续状态

动作时间轴复查发现，同一句内每个 DINet 分片已经按实际 `audioMs` 推进 `frameOffset`，但下一句为了并行准备只能在 TTS 完成前使用文字长度估算起点。不同音色、语速和停顿会让估算与上一句真实结束帧出现偏差；同一低幅动作跨句时即使没有切素材，也可能在边界轻微跳回或跳前。继续调文字语速系数不能消除这个结构性误差。

常驻 worker 现在为每个 `visualTurnId` 额外保存真实的下一源帧。同一回答后续句/段到达串行 worker 时，若动作素材与上一段相同，就用已保存的 `sourceFrameOffset + 实际输出帧数` 覆盖浏览器估算值；动作素材不同则继续尊重新动作的计划起点，并保留现有 4 帧跨素材渐变。完成或打断视觉轮次时，末帧、素材标识和下一源帧三个状态一起释放。渲染指标新增 `sourceFrameOffset` 与 `nextSourceFrameOffset`，缓存 profile 升级为 v14，避免旧生成结果掩盖新连续性。

验证没有调用 MiniMax、TTS 或聊天接口。Python 语法检查和 DINet/流式/统一页面三组 42 项定向测试通过。随后只启动一次真实本地 worker，用两段各 240 毫秒、6 帧的同动作 PCM 验收：第一段请求从帧 10 开始，返回 `source=10,next=16,total=187ms`；第二段故意传入错误估算 `frameOffset=100`，worker 实际返回 `source=16,next=22,total=125ms`，且 `transitionFrames=0`。这直接证明跨句同动作以真实帧 16 连续，而不是接受错误估算或靠渐变掩盖。临时 PCM 和两个 fMP4 验收文件已删除。

恢复服务前发现，通过工具 PTY 向 `npm start` 发送中断后，npm 会话已返回 130，但 Node 子进程仍占用 3000；这与 9.33 直接向 Node 发送 `SIGTERM` 的成功验证不是同一信号路径。这里只核对并终止精确监听 PID 后启动当前版本，没有反复重载，也把架构文档中“已完全解决 EADDRINUSE”的表述改为真实限制。最终 `/api/health` 返回 `ok=true`、`chatWarmupEnabled=false`，`/api/dinet/status` 返回 `ready=true`、零活动 stream/PCM，当前服务保持运行。启动进程树的显式 `exec` 修复作为下一项独立验证，不与本轮人物帧逻辑混测。

### 9.46 npm 启动进程树的信号透传

9.45 已把端口残留定位到 `npm start → /bin/sh → node` 的 PTY 信号边界，而不是 Node 内部 shutdown。本轮只修复这一项：`start` 改为 `exec node server.mjs`，`dev` 改为 `exec node --watch-path=server.mjs --watch-path=src server.mjs`。POSIX shell 的 `exec` 会用 Node 原位替换命令 shell，保留 npm 的前台进程组，同时减少一层可能吞掉 SIGINT 的子进程；开发监听范围仍不包含生成媒体目录。

### 9.47 提交后立即释放逻辑识别状态

### 9.49 匿名计时上报不再一次失败即丢失

### 9.50 连续视频容器移出下一轮首响路径

播放器审计发现一个与云端耗时无关的重复串行：每轮真人回答结束回到待机时都会释放 MediaSource 和隐藏视频，但下一轮只有首个 DINet fMP4 分片已经到达后才重新执行 `new MediaSource → sourceopen → addSourceBuffer`。这段初始化虽然通常只有几十毫秒，却位于 PCM 排程前的媒体门上，每轮都直接叠加到人物开口时间；用户说话和模型思考期间反而没有利用起来。

现在音频解锁采用两阶段能力确认：先立即确认共享 PCM 可用，保留非分片静音 MP4 兼容路径；随后在后台创建连续视频容器，`sourceopen` 和 SourceBuffer 就绪后才二次确认 `fragmentedVideo=true`。正常回答结束、打断清空以及其他回待机路径都会在旧容器释放后立即预建下一只空容器，下一轮首分片只需追加 init/media 数据。`fragmentedPlaybackPromise` 保证并发请求复用同一次创建；独立 generation 在清空时递增，迟到的旧 `sourceopen` 只能清理自己的节点，不能复活已经取消的容器。页面和 iframe 缓存版本分别升级为 v51/v39。

验证仍未调用聊天、TTS 或 MiniMax。语法检查和媒体门控、fMP4、音画时序、统一页面四组 20 项先通过。第一次完整回归为 238/239，唯一失败是旧静态断言仍要求原来的一阶段 `pcm-ready/mp4` 表达式；运行代码没有失败。更新该断言覆盖“PCM 立即确认、分片预建成功后二次确认、失败回退 MP4”后，相关 21 项与第二次完整 239 项全部通过，`git diff --check` 无错误。本机服务实际提供 v51；浏览器分别加载既有 Nike-chan v2 和切换后的真人画面，均显示就绪，日志没有新增项目脚本错误。自动化没有申请麦克风权限，因此这里只证明容器生命周期、页面加载和接线，不声称取得真实声卡首响差值；该差值由后续自然通话的 `videoHandoffLateMs` 样本验证。

### 9.51 自动反应不再吞掉正常语音

行为导演审计发现，`bow` 和 `surprise` 为避免鞠躬说话、以及手掌遮嘴时口型层穿透，使用了不经过 DINet 的静音整段视频；但静音判断此前只看动作名。系统提示和本地语义又会把普通“谢谢你/辛苦了”选成 `bow`，把“哇，真的吗”选成 `surprise`，于是并非动作测试的日常聊天也可能整句只有动作、没有声音。这不是动作触发率问题，而是自动语义和显式动作共用同一播放策略导致的错误。

静音整段现在只在行为计划带 `explicit=true` 时启用，即用户明确要求“鞠躬/做惊讶动作”仍按原意只表演。自然惊讶保留为等待正文期间的短反应预览，正式句开始时自动降为低幅 `happy`，人物能继续开口且不会在手掌上叠嘴。普通“谢谢你/感谢你/辛苦了”改为 `happy`，演示回答也改成“不用客气”的自然回应；只有明确鞠躬或行礼才使用 `bow`。系统提示同步写明该边界，避免模型重新把日常致谢选成静音动作。页面版本升级为 v52。

验证没有发起模型、TTS 或人物渲染请求。确定性行为时间线证明：自然惊讶的预览动作为 `surprise`、首个朗读句为 `happy`；明确“请做个惊讶动作”仍得到 `surprise + explicit=true`；“谢谢你/辛苦了”均映射为 `happy` 且演示正文为正常回应。行为、文案和统一页面三组 68 项通过，完整测试由 239 增至 242 项并全部通过，`git diff --check` 无错误。本机服务实际提供 v52，浏览器真人画面与人物 iframe 均显示就绪，没有新增项目脚本错误；未点击通话按钮，因此没有用自动化冒充真实语音验收。

### 9.52 从最后一次发声开始记录语音端点

继续沿现有匿名样本审计时确认，旧 `vadStopToSubmitMs` 的起点是 VAD 已经达到静音阈值之后。它只能测 90 毫秒 final 修正窗和页面提交间隔，却漏掉真正占用用户等待的 340–700 毫秒语义停顿；因此即使以后积累了自然样本，汇总也可能错误地把这段本地等待归给 M3 或人物首响。这里没有再缩短停顿阈值，而是先修正计量口径。

`SpeechEndpointDetector` 达到端点时把实际 `silenceMs` 交给 `RecognitionTurnGate`，提交门在迟到 final、提前 `onend` 或 90 毫秒超时时均保留该值。页面新增 `speechEndpointMs = endpointSilenceMs + stopToCommitMs + recognitionCommitToRequestMs`：分别代表最后一次检测到发声后的静音、浏览器最终转写修正和文字提交到聊天请求发起。它不包含用户正常说话的时长。服务端匿名白名单、0600 样本文件和汇总新增独立 `speechEndpoint` 分布；有效样本不少于 3 条时，它才会作为 `speech-endpoint` 与文本、TTS、DINet、浏览器交接按不重叠口径参与主瓶颈判断。

验证只使用确定性本地时钟和只读本机接口，没有调用 MiniMax、TTS 或聊天接口。提交门测试确认 544 毫秒端点静音能经过 final 修正完整保留；白名单测试确认 `speechEndpointMs` 可进入匿名样本且任意正文仍被拒绝；汇总测试确认该阶段能单独聚合并参与样本充足后的瓶颈判断。相关 31 项测试通过，随后完整 244 项测试全部通过，`git diff --check` 无错误。

运行态第一次读取汇总时仍是旧字段结构，原因是 3000 端口上的 Node 进程已在修改前加载服务端模块，前端静态文件更新并不等于服务端 ESM 热更新。核对精确监听进程后只停止该实例，并只启动一次当前代码；受限文件沙箱内直接监听端口返回 `EPERM`，随后在已批准的本机运行权限下启动成功。最终 `/api/health` 返回 `ok=true`、`MiniMax-M3` 与 `chatWarmupEnabled=false`，首页实际加载 v53，`/api/dinet/status` 为 `ready=true` 且零活动流，汇总已包含空的 `metrics.speechEndpoint`。当前仍是 `sampleCount=0`、`dominantStage=insufficient-data`，所以没有据此宣布 STT/VAD 已是主瓶颈，也没有用合成对话填数据。自动化没有真实麦克风权限；本轮证明的是字段语义、状态机接线、匿名聚合和运行模块已生效，真实设备端点分布仍必须由用户正常通话自动验证。

### 9.53 文本累计耗时不再冒充单一瓶颈

v53 服务运行后匿名汇总仍为 0 条样本，DINet 同时为就绪、零活动流和零 PCM 暂存，因此没有条件继续调 VAD、首段长度或渲染参数。对提交到正式播放之间所有固定等待逐项复查后也没有直接删除：60 毫秒是视频解码与 Web Audio 边界对齐缓冲，首段保留的 160 毫秒尾音用于避免刚开口就断粮，500 毫秒是接话候选让位于正式正文的竞争窗；在没有自然音画样本时缩短任一项都会把速度猜测换成卡顿风险。

审计汇总逻辑时找到一个会让后续样本得出错误行动方向的问题。旧主瓶颈候选 `text-model` 直接使用从请求开始到首个可朗读短语的累计 `serverFirstSentenceMs`，其中同时包含本地记忆/状态读取、上游建连及等待响应头、模型在响应头后的生成时间；它却与纯 TTS、纯 DINet 和浏览器交接阶段横向比较。即使数值最大，也不能判断应该优化本地上下文、连接还是 M3 生成。

匿名样本现在保留 `contextMs`，并从同一服务端单调时钟派生 `upstreamConnectionMs = upstreamHeadersMs - contextMs` 与 `textGenerationMs = serverFirstSentenceMs - upstreamHeadersMs`。两个累计指标继续展示总览，但不再参与排名；主瓶颈候选改为 `local-context`、`text-connection` 与 `text-generation` 三个互不重叠阶段。旧样本若同时具有两个边界，也会在读取时派生新阶段，不需要迁移或加入正文。

验证没有调用 MiniMax、TTS、聊天或人物渲染。确定性样本 `context=120ms / headers=820ms / firstSentence=1420ms` 被正确拆成 120、700、600 毫秒，三条相同样本的主瓶颈为 `text-connection=700ms`，而不是累计的 `text-model=1420ms`。汇总与匿名存储定向 9 项通过；随后只执行一次完整回归，245 项全部通过。服务通过已验证的 `exec` 启动路径只重启一次；最终健康接口返回 `ok=true`、`MiniMax-M3`、`chatWarmupEnabled=false`，匿名汇总实际包含空的 `context / upstreamConnection / textGeneration` 三项且仍为 `insufficient-data`，DINet 为就绪、零活动流和零 PCM 暂存。由此确认服务端 ESM 已加载新逻辑，同时没有为验收制造云端样本。

### 9.54 TTS 首 PCM 拆为四个可行动阶段

文本阶段拆分后继续审计 TTS。旧匿名指标只有从人物语音请求开始到首个有效 PCM 的累计 `ttsFirstAudioMs`；整句结束时虽能看到 `connectionWaitMs`、`taskWaitMs` 和是否复用，但正式正文开口时样本通常已经落盘，而且 `taskWaitMs` 自身包含前面的连接等待。若直接把累计首包判作 `tts` 主瓶颈，仍无法决定该优化 WebSocket 复用、task 预启动还是供应商合成。

`streamMiniMaxPcm` 现在在前导静音门首次产出可听 PCM 的同一时刻生成非重叠阶段：`connectionMs` 是请求开始后等待连接就绪的部分；`taskMs` 从请求开始/连接就绪中较晚者到 task 就绪；`synthesisMs` 从请求开始/task 就绪中较晚者到首个可听 PCM。服务端再用同一首 PCM 总时钟扣除三项，得到 HTTP 请求解析、会话创建等 `requestSetupMs`。预连接或预启动早于语音请求时，对应关键路径阶段自然归零；明确命中预热 PCM 时连接、task 和合成均为 0，只保留实际请求设置开销。

四项随已有 `tts-first-audio` SSE 一次发出，不增加网络往返。页面在首个非投机语音请求中只记录一次，并与正式开口事件一起进入原有匿名白名单。汇总保留累计 `ttsFirstAudio` 作为总览，主瓶颈候选改为 `tts-request-setup / tts-connection / tts-task / tts-synthesis`，不再让累计值与纯 DINet 渲染横向比较。构造的三条 `950ms` 首包样本被拆成 `30/500/120/300ms`，结论正确为 `tts-connection=500ms`。

### 9.55 人物首片段拆出 PCM 缓冲

TTS 拆分后，人物侧仍有一个会影响下一步决策的空白：`speechPipelineFirstSegment` 是从人物语音请求到首个视频 segment 的累计值，`avatarRender` 只覆盖真正调用 DINet/编码的部分；两者之间还包含从首个有效 PCM 到积累足够首段窗口的时间。当前连续链路要求 240 毫秒输出并保留 160 毫秒尾音，因此至少需要看见 400 毫秒 PCM 才开始首段渲染。没有独立测量就直接降低 160 毫秒，只是在速度与断粮卡顿之间猜测。

服务端现在在第一个真实 segment 返回时，使用同一单调时钟计算 `pcmBufferingMs = firstSegmentAt - firstAudioAt - renderMs`，随首 segment 一次发送，不增加请求。页面把人物请求到首 segment 的总时间扣除 TTS 首 PCM、PCM 缓冲和 DINet 渲染，得到剩余的 `avatarTransportMs`；它覆盖浏览器 fetch、服务端请求解析和首 segment 事件传输等本地协议开销。匿名样本新增 `avatarPcmBuffering / avatarTransport` 两个分布，主瓶颈排名使用这两项和原有纯 `avatarRender`，累计 `speechPipelineFirstSegment` 只保留总览。

### 9.57 待机层被暂停导致人物整层闪失

用户继续反馈闪烁后，不再调整素材，而是在闪烁发生时读取实际页面状态。页面截图明确显示左侧只剩卧室背景，人物整层消失；同一时刻 `avatar-idle` 仍为 `display:block / opacity:1 / readyState=4`，但 `paused=true`，时间停在 13.98 秒，口型层暂停且透明，也没有残留的语音分片。由此确认此前把五官漂移当作主因并不完整，真正的页面闪烁是待机视频被暂停、seek 后没有重新绘制，纯背景从底层露出。

根因位于回答结束和分片间隙共用的 `alignIdleToTime()`：它先暂停待机视频再定位到语音时间轴；如果定位后的揭示定时器被下一事件取消，恢复播放不会执行。现在待机层改为始终连续播放，不再为了姿态对齐执行 `pause/currentTime`；页面可见且没有活动语音层时，如果浏览器意外触发 `pause`，守护逻辑会立即恢复。视频增加同人物首帧 `poster`，舞台底层也改用该首帧，保证解码或图层交接的极短窗口仍显示人物，而不是空卧室。真人 iframe、运行时脚本和样式均更新版本标识，普通刷新即可取得修复。

检查服务退出日志时又确认了第二个独立故障：客户端中断时 DINet 会话先被取消，仍在后台执行的 `renderChain` 随后抛出 409；请求处理已因中断离开等待点，该 Promise 一度没有拒绝观察者，Node 将其作为未处理拒绝并终止整个服务。现在每次排入渲染后立即附加只负责观察的 rejection handler；正常完成仍由原有 `await/catch` 报告错误，取消后的迟到 409 不再击穿进程。

定向测试 21 项通过，加入服务取消保护后完整回归 247 项全部通过。浏览器刷新后的自动视觉复验被本地 URL 安全策略拒绝，因此没有绕过限制作出视觉通过声明；最终页面效果留给正常浏览器刷新验证。服务清理不响应的旧进程后已重新启动，健康接口返回 `ok=true`，DINet 就绪且没有活动或残留流式会话。

- 使用小桃绿幕母版重新生成独立动作原片。新版鼓掌要求双手沿身体前方抬起、肘部靠近腰侧、掌心在胸前竖直接近，只做小幅拍合后沿原路径放下。正式审计测得合掌 57 帧，合掌期间大幅重新张开 0 次；页面关键帧确认没有先横向张臂，动作明显更接近露米。
- 点头生成模型两轮都倾向在低头时自然闭眼。首轮因低头停留过长被否决；第二轮保留为动作源，但完整 54 像素下压仍大于露米的 21 像素，因此只取自然起势前 0.88 秒的 23 像素下压并沿同一路径回正，去掉深低头和向上过冲。安装后实测垂直位移 24 像素，与露米处于同一幅度档，动作首尾差异 0.336。
- 两段动作继续使用统一的 94% 人物比例。浏览器实际点击点头和鼓掌，分别显示一次短促低头与胸前自然合掌，动作结束均回到相同位置；语义动作、手部接触和全部动作首尾切换审计通过。
- 点头 v3 查询期间出现一次网络 `fetch failed`。旧终止错误正则把其中的 `failed` 误判为远端任务失败，恢复查询时意外提交了第二个点头任务。生成脚本现只把明确的任务 `failed/cancelled`、余额不足或 `video_generation_failed` 判为终止失败；普通传输错误保留原任务号和 `submitted` 状态，下次只继续查询，避免再次重复提交。

## 10. 安全与配置

- API Key 仅保存在 `.env`，不得写入代码、日志或本文档。
- 曾在聊天中暴露的 Key 应废弃并重新生成。
- 服务端不落盘保存完整聊天；浏览器只保留有限历史。本地只保存经过隐私过滤的结构化长期记忆，以及不含时间戳、用户标识和聊天内容的有界延迟样本。
- 所有第三方模型和动作资源在发布前必须核对许可证与署名要求。
