# 当前系统架构

更新时间：2026-08-12

本文只描述当前可运行实现；调研过程、失败方案和参数演进统一记录在 `EXPERIMENT_LOG.md`。

## 1. 主链路

```text
浏览器语音识别 / 文字降级输入
  → POST /api/chat/stream
  → 人物设定标准化
  → 召回相关长期记忆和连续状态
  → MiniMax 流式文案（或 OpenAI / demo）
  → 服务端正文清理、身份连续性保护、按句 SSE
  → POST /api/speech
  → 真人：Audio2BlendShape + DINet → 有声 MP4
     动漫：Web Audio 音量 → VRM 口型、表情和动作
  → 播放结束后恢复常驻待机
```

浏览器再次开始录音时会同时取消当前模型流、待处理 TTS、音频/视频播放和动作，保证旧回答不会覆盖新一轮。

## 2. 前端模块

| 文件 | 职责 |
| --- | --- |
| `public/index.html` | 统一聊天页面和控制区 |
| `public/app.js` | 语音识别、聊天历史、SSE、TTS 队列、真人/动漫切换 |
| `public/wav2lip-avatar/avatar.js` | 真人常驻待机层与口型视频层播放 |
| `public/dh-live/actions/bedroom_idle_test/01-seamless.mp4` | 真人常驻待机的正反向无缝循环素材，避免人脸在首尾硬切 |
| `public/vrm-embed.js` | 统一页内嵌 VRM 桥接 |
| `public/vrm-avatar.js` | VRM 加载、表情、口型、动作和相机控制 |

`/` 是唯一产品主入口。`/vrm.html`、固定 `profile` 和动作制作页只用于单独调试或方案对照。

## 3. 服务端模块

| 文件 | 职责 |
| --- | --- |
| `server.mjs` | HTTP/SSE、聊天和语音供应商、诊断环形缓冲区、本地渲染接口 |
| `src/companion.mjs` | 人物提示词、上下文清理、回复正文清理、情绪和动作推断 |
| `src/memory.mjs` | 本地结构化记忆、召回、去重、衰减和清理 |
| `src/voices.mjs` | TTS 音色白名单、默认项和自定义音色配置解析 |
| `src/dinet-render.mjs` | DINet worker 生命周期、串行任务、缓存和临时文件 |
| `scripts/dinet_worker.py` | Audio2BlendShape、OpenGL 提示图、DINet 重绘和封装 |

所有本地模型、动作上传和诊断接口只允许回环地址访问。外部供应商 Key 从 `.env` 读取，不返回浏览器。

## 4. 聊天请求结构

浏览器每轮发送：

```json
{
  "message": "当前消息",
  "history": [{ "role": "user|assistant", "content": "..." }],
  "userId": "浏览器本地匿名 ID",
  "persona": {
    "name": "人物名字",
    "relationship": "与用户的关系",
    "style": "表达风格",
    "background": "人物背景"
  },
  "fastSpeech": true
}
```

服务端只取最近 10 条有效历史，过滤旧的身份分类、设备限制和位置跳出回答，并合并过滤后相邻的同角色消息。MiniMax 的最终消息顺序是：`system → 历史 user/assistant → 当前 user`。

MiniMax 只生成可朗读正文。`emotion` 和 `action` 在本地推断，不要求模型输出 JSON，因此不会把控制词送进 TTS。流式正文和最终正文都会经过身份连续性保护。

## 5. 音色控制

页面通过 `/api/voices` 取得可选择的公开音色 key。`/api/speech` 只接收 key，服务端再用 `src/voices.mjs` 的白名单映射为 MiniMax `voice_id`，避免客户端直接指定任意账号音色。

内置普通话女声包括甜美、柔和、温暖、成熟、淡雅和嗲气 6 类陪伴音色，以及经典、妩媚、傲娇、强势 4 类御姐音色。选择保存在浏览器 `lumi-voice-profile`，真人和动漫模式共用；切换音色不改变人物提示词、记忆或动作。`MINIMAX_TTS_VOICES_JSON` 可将当前账号的克隆/文生音色加入服务端白名单。

## 6. 人物连续性规则

- 人物以配置的名字、关系、风格和背景作为稳定第一人称。
- 普通生活邀请按共享场景自然继续，例如散步、逛湖边和下楼。
- 不以手机、屏幕、应用、模型或技术机制解释自己为何不能行动。
- 不生成具体住址、危险行为或违法行为；安全边界仍高于人物设定。
- 旧错误回答在进入下一轮模型上下文前过滤，避免一次错误持续污染后续对话。

## 7. 记忆和诊断

结构化记忆落盘到 `data/companion-memory.json`，完整聊天不在服务端持久化。清空按钮调用 `/api/chat/memory/clear`，同时清理该 `userId` 的记忆和连续状态。

`/api/chat/debug/recent` 提供最近 20 次请求的内存诊断，用于比较：

1. 浏览器实际发送的人物设定和历史；
2. 服务端召回的记忆和连续状态；
3. 发给供应商的最终消息数组；
4. 模型原始正文；
5. 已发送的 SSE 分句；
6. 页面应采用的最终结果。

每轮 `meta` 还携带只在本机使用的 `traceId`。浏览器在人物真正开口时，将白名单内的用户最后一次实际发声到请求发起、请求到真实开口、停顿到真实开口、M3 首句、TTS 首 PCM、DINet 首片段、视频首帧和交接误差合并回同一条诊断；第一句是普通接话、长尾衔接还是真实正文会单独标记。语音端点只计算 VAD 已观察到的静音时长、最多 90 毫秒 final 修正窗和识别提交到请求发起的页面间隔，不包含用户正常说话的时长。TTS 首个有效 PCM 到达时立即发送轻量阶段事件，首视频段到达时页面直接记录该语音请求的总流水线，因此这些指标在人物正式开口时已经齐全，不需要等整句生成完成。上报接口只接受本机请求，只保留有限枚举和 `0..180000` 毫秒的数值，不接收聊天正文、人物设定或任意附加字段。

`/api/chat/debug/summary` 将最近样本进一步聚合为不含正文的样本数、P50、P90、最大值与 3 秒达标率，同时统计第一次开口属于普通接话、长尾衔接还是真实正文。语音端点、M3 首句、TTS 首 PCM、从语音请求到人物首片段的总流水线、DINet 首片段自身 `renderMs`、浏览器交接和“最后一段接话结束→正文开口”都有独立分布。后者只在真实播放过接话时记录，不把接话自身时长误算为冷场。文本累计时钟另外拆成 `context`（本地记忆与连续状态）、`upstreamConnection`（上下文就绪到收到上游响应头）和 `textGeneration`（响应头到首个可朗读短语）三个不重叠阶段；累计的 `upstreamHeaders` 与 `serverFirstSentence` 只用于总览。TTS 首 PCM 同样拆成 `ttsRequestSetup`、`ttsConnection`、`ttsTask` 和 `ttsSynthesis`；已提前建立连接或启动任务的关键路径等待为 0，`ttsSynthesis` 从请求时刻与任务就绪时刻中较晚者开始，并包含为可听首 PCM 去除供应商前导静音所需的等待。人物首片段继续拆成 `avatarPcmBuffering`（首个有效 PCM 到进入首段渲染）、`avatarRender`（真实首段 DINet/编码）和 `avatarTransport`（浏览器发起请求与收到首 segment 中未被前三段覆盖的本地协议/传输开销）。累计的 `ttsFirstAudio` 与 `speechPipelineFirstSegment` 都只用于总览。主瓶颈判断只比较上述非累计阶段与 `speech-endpoint` 和浏览器交接。少于 3 个有效样本时只展示数据，不给出结论。

含聊天内容的原始诊断不落盘，服务重启后清空。人物正式正文真实开口时即提取一条匿名样本，不再等待整轮播放结束；用户听到回答后插话、结束通话或刷新页面也不会丢掉已经成立的首响证据。只有普通接话而正式正文尚未开口的轮次不落盘，避免把“嗯”当成回答完成。样本只保留 0–180 秒范围内的各阶段毫秒耗时和有限的首响类型，不保留时间戳、`traceId`、用户标识、聊天正文、历史、人物设定或模型输出。样本以 0600 权限原子替换写入 `data/chat-latency-samples.json`，最多保留最近 100 条，因此重启后仍可继续判断瓶颈，又不会把对话记录变相持久化。浏览器上报或样本写入失败不会阻塞语音或人物播放。

浏览器计时上报使用独立的非阻塞有界重试器：首次立即发送，网络异常、5xx 或短暂 404 时分别在 120/480 毫秒后重试，最多三次；400 等永久错误不重试。每轮回答开始先清除上一轮的 TTS、DINet、视频首帧和交接指标，避免真人/动漫切换后混入旧值。页面只暴露 `data-latency-report-status` 与尝试次数用于本机诊断，不显示技术信息，也不把对话正文加入上报。

服务退出现在统一处理 `SIGTERM` 和 `SIGINT`。Node 收到信号时会先停止 HTTP 监听并关闭尚未消费的 TTS 预连接，再终止 DINet 常驻 Python worker；退出流程幂等，DINet 最多等待 1 秒后强制结束，整个 Node 进程最多等待 2 秒。`start` 和 `dev` npm 脚本使用 shell 内建 `exec node ...`，中间命令 shell 被 Node 原位替换，PTY 中断不会只结束 npm 会话而把 Node 留在后台。真实 `npm start` 验收中监听 PID 42875 收到 SIGINT 后立即消失，3000 端口同步释放；随后正常恢复的服务使用新 PID，不再需要手工清理残留进程。

## 8. 真人渲染边界

DINet 当前采用“LLM 流式可读短语 → MiniMax WebSocket TTS 连续 PCM → 状态化 Audio2BlendShape/DINet 分片 → fMP4/MediaSource 画面 + Web Audio 主时钟”的流水线。后续句在当前句播放期间并行准备，首句不等完整 TTS 或整段 MP4。DINet 帧通过 rawvideo 管道直接送入 H.264 编码器，不再先编码临时 mp4v 后二次转码。当前本地首片段已快于播放；继续降低首句等待应优先依据自然对话样本处理文本模型长尾、TTS 租约失配或浏览器交接，而不再降低帧率/分辨率或重写已稳定的分片层。

### 已完成：流式音频与分段口型渲染

历史串行关键路径是：

```text
完整首段文字 → 完整 WAV → 完整 DINet MP4 → 播放
```

当前已改为：

```text
可朗读文字片段
  → MiniMax WebSocket TTS 连续返回音频块
  → 服务端增量解码为 16 kHz 单声道 PCM
  → PCM 窗口进入状态化 Audio2BlendShape + DINet
  → 连续视频分片
  → 浏览器保持小缓冲边收边播
```

当前每个可读短语使用一个 MiniMax WebSocket TTS 任务直接返回 PCM；`task_finish` 后连接会关闭，不跨句复用已完成任务。首句通过聊天等待期的一次性预连接/预启动租约减少建连等待，且只在模型、音色和标准化情绪一致时领取，避免为了速度播放错误语气。官方接口参考：<https://platform.minimaxi.com/docs/api-reference/speech-t2a-websocket>。

WALL-E 的非微信主链路已验证了可借鉴的音频半链路：终端把 16 kHz 单声道音频编码成连续 Opus 小包，通过一个长连接按序上行；服务端维护 VAD、ASR、LLM、TTS 队列和打断状态；下行音频由常驻解码器按序播放。这里吸收的是它的**长连接会话、严格序号、有界队列、连续解码、阶段事件和取消语义**，不移植微信桥，也不把当前 M3 换成 WALL-E 的 Kimi。WALL-E 当前配置的 Sherpa 是离线识别，不能直接消除停顿后的 ASR 等待；它也不包含 DINet，因此不能代替下面的视频增量渲染工作。

实施经过两个可回退阶段：

1. **分段 MP4 验证版（保留为兼容回退）**：以 PCM 窗口生成带声小 MP4，严格按序号播放，用于浏览器不支持共享 Web Audio/MediaSource 时的安全回退。
2. **状态化 PCM + fMP4 版（当前默认）**：OnlineFbank、Audio2BlendShape LSTM、DINet 动作帧时钟保持整轮会话；服务端输出可连续追加的 H.264 fMP4，浏览器通过单个 MediaSource 和 Web Audio 绝对时钟播放。每片段仍独立做轻量 FFmpeg 封装；实测封装只约 10–21 ms，不值得为了形式上的“单编码器”重写稳定链路。

Node 层的 `DINetStreamSessionStore` 已实现 `start / append / drain / complete / cancel / acknowledge` 会话状态。Python worker 仍按可播放分片接收渲染命令，但使用稳定 `streamId` 跨分片保留声学状态，并接受 `cancel_stream` 显式释放。两层共同为每轮保存：

- `OnlineFbank` 尚未消费的声学帧；
- Audio2BlendShape LSTM 的 `hidden/cell`，不能像当前 `Audio2bs()` 一样为每块重置为零；
- 当前动作素材、ping-pong 视频帧索引和已输出帧数；
- 音频采样数、视频时间戳、分片序号、播放确认反压和取消状态。MiniMax TTS 租约位于 Node 服务层，不进入 Python worker，避免网络连接和模型进程耦合。

第一阶段已经增加本机专用的 DINet 流式会话 API：

- `POST /api/dinet/stream/start`：建立 16 kHz、单声道 PCM16 会话并固定本轮动作；
- `POST /api/dinet/stream/:id/audio-chunk`：通过 `X-Chunk-Sequence` 严格按序提交 PCM；
- `POST /api/dinet/stream/:id/finish`：结束输入并返回渲染结果和分阶段计时；
- `POST /api/dinet/stream/:id/cancel`：立即释放缓冲，迟到分片不再进入新一轮。

当前生产链路已是可运行的分段流。`/api/dinet/speech-stream` 通过一个 MiniMax WebSocket 持续接收 16 kHz 单声道 PCM，在共享 PCM + 连续 fMP4 模式下累计 240 ms 发声音频并保留 160 ms 尾音后即开始首段 DINet，后续每 800 ms 一段，不等待完整 WAV。兼容 MP4 路径保持 800/240 ms，`?streaming=0` 可回退整句链路。服务启动前会完成 DINet 模型预热，避免第一轮用户请求承担约 5 秒模型加载。

分段音频不再依赖每个 MP4 内部独立 AAC 的 `ended → play()` 交接。服务随 segment 返回对应的原始 `pcm_s16le`（16 kHz、单声道），主页面在用户首次点击时同步创建 Web Audio 上下文，人物 iframe 复用该同源上下文并把所有 PCM 按同一个 `AudioContext.currentTime` 无缝排程；视频分段成功排程 PCM 后静音，只负责口型画面。主页面必须把完整 `segment.audio` 转发给人物 iframe，不能只发视频 URL。若浏览器不支持或拒绝启动 AudioContext，则保持 MP4 原声自动回退。停止通话会取消所有已排程音源，最后一段音频结束前不会切回待机。

多句回答现在使用整轮 `AvatarStreamTurn` 协调器。每个句子的 TTS/DINet preparation 在文本分句到达时立即启动；人物入队仍按句子顺序进行，但入完上一句的所有 segment 后就开始接收下一句，不再等待上一句视频全部播放结束。协调器累计整轮 PCM 时长和播放 Promise，只在最后一句完成入队后发送一次 `wav2lip-stream-end`，并在全部视频真正播放结束后才恢复聆听。惊讶、鞠躬等无声全身动作继续使用播放屏障，必须等前面的有声段结束再执行，避免覆盖当前说话画面。

首视频段经过 800→600→480→400→320→240 ms 的递进验证，当前连续 fMP4 路径使用 240 ms/6 帧。独立本地 worker 使用真实 Audio2BlendShape、DINet 和 H.264 fMP4 路径完成 240 ms 验收：声学 2 ms、帧渲染 166 ms、封装 20 ms，总计 188 ms。后续仍使用 800 ms/20 帧，典型热态生成时间明显低于自身播放时长，保留数百毫秒下载和解码余量。

Audio2BlendShape 现已改为真正的会话状态：worker 为每轮语音保存一个 `OnlineFbank`、已消费特征位置和 LSTM `hidden/cell`，开始时只用一次 400 ms 静音预热，后续 PCM 不再重叠、不再重复重采样既有音频。动作底片使用跨段 `frameOffset`，不会每段从首帧重新开始；完成和取消都会显式释放 worker 会话状态。当共享 PCM 可用时，输出是无声 H.264 fMP4 分片，浏览器追加到单个 MediaSource 并以 Web Audio 作为整轮主时钟；兼容模式才使用带声 MP4。因此“等完整 TTS/整段 MP4”和“下一步再做 fMP4”已不是当前状态。

端到端复测表明，热链路从提交问题到首个可播放视频为 2.48–2.96 秒，其中 M3 首个可朗读短语约 1.67–1.86 秒，WebSocket TTS 加首个 DINet 片段约 0.61–1.10 秒。服务重启后的首次 M3 请求曾因上游建连达到 15.4 秒，但两次冷启动门控实验在 M3 预热明确就绪后，真实首句仍分别为 1.629 秒和 4.064 秒，无法证明稳定收益。因此 DINet 仍在监听端口前本地预热；M3 启动预热改为默认关闭，只有 `MINIMAX_CHAT_WARMUP=1` 才发起一次 8 秒上限的可取消请求。这避免开发重启重复计费和与首轮用户竞争。人物身份与固定回复规则仍放在系统提示前部，变化较频繁的记忆和连续状态放在尾部，以利用供应商前缀缓存。云端 M3 仍可能把总首段推到 3.3–5.6 秒，因此 3 秒是正常网络中位数目标，不是硬实时保证；不使用与语义无关的固定套话掩盖模型延迟。

首响诊断进一步细分为 `firstTextDeltaMs`、`firstCleanTextMs`、`firstSentenceMs`、TTS `ttsFirstAudioMs` 和 DINet `firstSegmentMs`。页面人物容器同步记录 `data-chat-first-sentence-ms`、`data-tts-first-audio-ms`、`data-avatar-pipeline-ms` 与从提交到首个 segment 的 `data-avatar-first-segment-ms`，不用再从两套日志手工对表。MiniMax 三轮热测中，首个正文 token 与首个可朗读短语只差 0–2 毫秒，说明当前中文标点/逗号分段没有增加首响延迟；主要波动发生在模型输出任何正文之前，不能靠更激进地切碎文案解决。

聊天请求开始时签发并预热一个 MiniMax WebSocket TTS 任务，首个可朗读句只领取最新有效租约；长推理期间每 8 秒替换一次，旧任务立即关闭，首句出现后冻结，15 秒仍未领取则自动释放。页面额外记录 `data-tts-connection-reused`、`data-tts-task-primed` 与 `data-tts-connection-lead-ms`，可直接确认首句是否真正使用预连接，而不是只看到聊天接口提前发过 ID。

最新三类真实文案探针（日常分享、情绪关心、简单规划）在不启动 TTS/口型的情况下，M3 首句分别为 2.91、2.20、5.36 秒，总响应为 3.02、2.46、6.24 秒；长尾明确发生在上游连接和正文前推理。生产路径因此没有启用会让每轮模型成本近似翻倍的双模型竞速，而是强化 500 毫秒后的本地语义等待回应：关心使用“我在。”与关心动作，分析、安排、规划和计划使用“我想想。”与思考动作，分享、问候和好消息各自使用克制的短回应。等待回应不写入正式聊天历史。

流式朗读只允许第一段使用至少 9 个有效字的逗号快速开口，首响之后恢复到句号、问号、感叹号和分号等完整边界，避免把规划建议拆成大量零碎 TTS/口型任务。服务端同时移除模型偶发返回的 Markdown 强调、标题、列表符与行内代码；用户明确要求“一句、两句、简单、简短”时确定性限制最终回答长度，并删除已有实质规划答案后的“你觉得这样可以吗”式机械确认，真正缺信息的具体追问不受影响。动作推断会先去掉“不累、不会太累、没压力”等否定表达，防止思考动作在结尾误跳成关心。

第一段若只得到不超过 4 个有效字的完整短句，例如“哦？”“真的？”，不会立即单独启动 TTS/DINet，而是暂存并与紧随其后的完整句合并；若流最终确实只有该短句，则在结束刷新时正常释放。这样不改变有内容首句的快速逗号开口，却消除“哦？”播放完再重新起一次“什么事，说来听听”的机械停顿和额外口型任务。三类普通真实探针均只产生 1–2 个完整句，没有证据支持对所有日常回答增加强制三句截断，因此默认仍尊重模型自然长度，只有用户明确要求简短时启用本地预算。

显式简短请求使用增量句预算，而不是在 `done` 阶段事后截断。达到一句、两句或三句预算后，服务端立即停止读取上游剩余流，不等待供应商确认取消；已接受并发送为 `sentence` 的文本拼接结果成为 `done.reply` 的唯一来源。因此声音、字幕、最终文案和下一轮历史不会出现“已经播放但最终被删”或“最终仍包含未播放后续句”的分叉。诊断以 `finishReason=local-length` 和 `localLengthReachedMs` 标记本地提前结束点。

M3 的 `max_completion_tokens` 同时包含隐藏推理和最终正文。真实请求曾在 400 上限内生成 1748 个推理字符后以 `finish_reason=length` 结束且没有正文；降低到 240 的对照也没有改善首正文延迟。当前上限因此设为 800，作用是保障短回答能在长推理后落出正文，而非鼓励更长文案，实际朗读长度仍由 1–3 句提示约束。当前账户的 `MiniMax-M2.7-highspeed` 三轮相同人物提示首正文均慢于 M3，因此不切换模型。本机诊断接口的 `providerStream` 记录 `finishReason`、正文/推理字符数及可用 token 统计，用于把模型推理波动与 TTS、DINet 耗时分开。

MiniMax 流式请求显式开启 `stream_options.include_usage`，诊断同时记录 `promptTokens`、`cachedPromptTokens`、`completionTokens` 与 `reasoningTokens`。同一稳定人物提示实测为 558–559 个输入 token，供应商缓存可从首轮约 128 token 扩展到后续 558 token；但以独立短请求预热新的自定义人物时，首轮和延迟复测仍只命中 128/547、145/547，无法证明人物感知预热有稳定收益，因此没有保留额外预热接口或页面调用。当前官方 OpenAI 兼容接口公开的是 `reasoning_split`、`max_completion_tokens`、`temperature` 和 `top_p`，没有低推理强度参数；继续优化 M3 长尾应以真实 `cachedPromptTokens` 和正文首字指标为依据。

自定义人物缓存还验证过两种提示结构：把稳定规则移到同一 system 消息前半段后，不同人物仍只命中 128/553；拆成“稳定 system + 动态 system”两条消息后，连续两个新人物也仍为 128/551。原因是固定规则本身没有达到供应商 512-token 缓存门槛，继续填充提示只会增加每轮输入成本。两种结构均已撤回，生产继续使用语义最直接的单 system 人物提示，不为不可证实的缓存收益牺牲清晰度或费用。

DINet 动作素材采用“提前切换、单套常驻”，不缓存多套完整视频帧。单套 768×1152 RGBA 动作解码后内存很大，多动作 LRU 会带来不可控内存压力；而本地探针表明关心/待机切换只需 283–331 毫秒，同动作命中为 0 毫秒。服务在 M3 请求开始时用用户语义推断首动作，并把 `prepare_asset` 排入同一个常驻 worker；该切换与 M3 的 1.5–6 秒正文前等待并行，真正 TTS/DINet 渲染仍重新核对动作。身份、位置等本地直接回复也走同一预热入口。`/api/dinet/prepare-action` 只允许回环地址访问，用于不调用外部 AI 的冷热诊断。

同一轮回答跨句使用相同动作时，worker 使用上一真实分片结束后保存的下一源帧，覆盖浏览器在 TTS 时长未知时给出的文字估算偏移。动作素材不同时不再混合两张完整画面：旧 4 帧渐变会把位置略有差异的黑发、手臂和衣袖同时显示，形成头发虚影和瞬时黑块。播放器会先等待新视频首帧解码完成，再原子切换到新动作；各动作首尾均回到共享自然站姿，因此无需用双轮廓换取连续性。

连续通话的浏览器识别收尾不再完全依赖 Web Speech 延迟不定的 `onend`。当前识别器使用 `continuous=false`：一旦浏览器给出 `isFinal=true`，该事件本身就是本轮语音边界，页面立即提交并停止 VAD，不再重复等待 340–430 毫秒静音。仍是临时转写时继续由本地 VAD 与语义完整度判断停顿，再设置最多 90 毫秒的最终修正窗口；`onend` 提前到达也会立即提交。final 或 VAD 已请求 `recognition.stop()` 时，页面会立即把本轮逻辑捕获状态标为停止，而不是继续用迟到的 `onend` 控制 `recognitionRunning`；这样人物开口后的本地插话检测不会被旧识别状态挡住，迟到的 final/onend/error 仍由同一个单次提交门安全吸收。浏览器 final 与 VAD 边界都把已观察到的静音时长传入同一个提交门；匿名 `speechEndpointMs` 再加上 final 修正与请求发起间隔，才表示最后一次实际发声到请求发起的完整本地端点耗时。触发源分别标记为 `final-result` 与 `vad-timeout/recognition-end`，便于真机复测且不混淆来源。该优化削减的是“用户说完到 M3 请求发起”的本地空等，不改变或掩盖 M3 首正文的云端波动。

流式真人分片采用显式音频能力协商。点击开始通话后，父页面先解锁共享 `AudioContext`，人物 iframe 再回报 `pcm-ready`；只有两项同时成立，`/api/dinet/speech-stream` 才设置 `externalAudio=true`，worker 输出 `-an` 的纯 H.264 MP4，声音由分片对应的 PCM 按 Web Audio 绝对时钟连续播放。不满足协商条件时仍生成带 AAC 的完整 MP4，保证不支持或未解锁 Web Audio 的环境有声音。`videoOnly` 进入渲染缓存键，纯视频与带声回退不会交叉命中。800 毫秒实测首段由 160,286 字节降到 152,046 字节（约 5.1%），`ffprobe` 确认纯视频只有 H.264，回退文件仍有 H.264+AAC；神经推理占主耗时，因此本轮不宣称显著降低渲染时间，收益是去除无用音轨、减少传输并消除双音频轨潜在干扰。

连续 fMP4 播放进一步把“视频已经追加到 MediaSource”设为对应 PCM 进入 Web Audio 时间轴的前置条件。旧顺序在收到 segment 后立即把声音安排到约 60 毫秒后播放，同时才下载和追加视频；首段或偶发慢追加时声音会先走，画面随后只能跳到当前音频位置。现在每段先完成本机视频获取、解析和 SourceBuffer append，再按统一音频尾时钟排入 PCM。热态实测后续 800 毫秒视频只需约 237–247 毫秒生成，仍保留约 550 毫秒播放余量，因此该屏障减少追帧和卡顿而不会在正常负载下制造句内静音。

PCM 不再以 base64 字符串嵌入 SSE JSON。支持外部音频的页面发送 `binaryAudio=true`，服务端把每段原始 PCM 放入有 60 秒 TTL、8 MiB 总上限的内存暂存区，segment 只携带同源随机 URL、长度和格式；iframe 在视频预加载的同时用 `fetch(no-store)` 拉取二进制并立即排入 Web Audio。接口仅允许回环地址，token 为 128 位随机值；取消会立即释放该会话尚未过期的 PCM，正常结束依靠 TTL 清理，以免 SSE 完成早于浏览器取音频。旧客户端未协商时仍收到 base64，兼容回退不变。短句实测中 SSE 从 50,128 字节降至 1,785 字节（事件流减少 96.4%）；连同 37,896 字节原始 PCM 计算，总传输从 50,128 降至 39,681 字节（减少 20.8%），同时避免浏览器在主线程解析和解码约 48 KiB base64 文本。

外部 PCM 模式的视频分片不再等待前一 `<video>` 的 `ended` 后才启动。PCM URL 和视频一到页面就分别并行下载，音频下载本身不进入前一分片的排程队列；只有把已下载样本写入 Web Audio 绝对时钟时才严格按序。音频排程不等待对应视频的 `loadeddata`；每段视频并行加载并等待自己的 `audioStart`，边界前 32 毫秒短暂播放以完成解码，取得首帧后暂停，到绝对开始时间再恢复播放并切换可见层。超过 25 毫秒才按迟到量追赶 `currentTime`，正常边界不跳帧；这样任一视频或后段 PCM 的下载波动不会串行阻塞其他资源。浏览器侧另维护整轮递增 `playbackSequence`，不会把跨句时重新从 0 开始的服务端分片序号误判为旧段；加载中、预启动中、串行回退中三类任务都计入回待机屏障，取消则统一由 `playToken` 失效，并阻止已经在途的旧 PCM 在取消后重新排入音轨。使用两段真实 800 毫秒纯视频和 PCM 的浏览器验收中，首帧准备为 32/31 毫秒，两次显层相对音频边界均迟到 4 毫秒。主页面记录 `videoFirstFrameMs` 与 `videoHandoffLateMs`，后续可用真实对话持续监测。

DINet 生成目录使用有界磁盘缓存，而不是无限保留每个随机流会话的分片。只识别 24 位十六进制哈希命名的 `.mp4`，默认上限为 384 个文件且 128 MiB；两项任一超限便按最近使用时间删除最旧文件。新生成或刚命中的文件更新使用时间，15 分钟内文件与本轮刚返回的输出受保护，因此回收不会抢在浏览器取 URL 之前删除；命中确认、时间提升和回收共用同一串行文件队列，避免并发返回已删除 URL。动作素材、上传视频及其他项目文件不在扫描范围内。`/api/dinet/status` 在回环地址上返回当前文件数、字节数、上限、保护期与是否超限。首次启用时实际将历史目录从 504 个/158 MiB 回收到 384 个/78 MiB，服务与最近生成结果保持可用。

流式会话也有独立的资源上限。开放会话若连续 60 秒没有收到音频、继续渲染或其他有效活动，会被判为客户端遗弃：立即清空尚未渲染的 PCM、唤醒背压等待者、释放外部音频暂存并取消 worker 会话。正常生成完成后不再受该空闲计时器影响，只按原有的 60 秒播放确认留存窗口等待最终 ack。`/api/dinet/status` 的 `streams` 字段公开当前总会话、开放/已完成会话、缓冲字节和两种超时，便于长时间通话时确认资源没有逐轮增长。真实服务生命周期探针已验证空会话从 `0 → 1 → 0`，清理后 `streams.sessions=0` 且 `pcm.entries=0`。

静态视频响应不再先用 `readFile` 把完整 MP4 装入 Node 内存，而是直接从磁盘流向浏览器。MP4 支持单段 `Range` 请求：合法范围返回 `206 Partial Content` 与准确的 `Content-Range`，越界或格式错误返回 `416`，`HEAD` 只返回元数据。以 24 位内容哈希命名的 DINet/Wav2Lip 生成视频使用一年 `immutable` 缓存，同一个嘴形分片无需重复下载；主页、脚本和 JSON 继续使用 `no-store`，其他非内容寻址素材保持 `no-cache`，避免开发过程中缓存旧页面。

长时间聊天的短期上下文现采用双层预算：浏览器只上传最近 6 条、每条最多 600 字；服务端再次限制为最近 6 条、短期正文合计最多 1800 字，并确保裁剪后不以孤立的 assistant 消息开头。超长单条不再只截取末尾，而是保留约 62% 开头和 38% 结尾，中间用省略号连接，避免丢掉回答的主题。人物设定、长期偏好和连续状态仍走独立上下文，不因短期裁剪丢失。快速朗读的逗号分段最低从 3 个有效字提高到 6 个，避免把“辛苦了，”之类短开场单独启动一次 TTS；完整句号、问号和感叹号仍立即释放。

云端正文尚未返回时，连续通话支持一次不虚构答案的语境接话。服务根据已确定的情绪和低幅动作，在 200 毫秒仍无可朗读正文时发送仅用于投机准备的 `backchannel` 候选；前端再保留 500 毫秒抢答取消窗，约 700 毫秒到达播放决策。首个口型片段尚未就绪时不会空画面开口，而且正式 `sentence` 在真实首帧前到达仍会精确取消候选，因此缩短决策窗不等于强制插话。随后主回答仍按同一轮顺序衔接。接话不写入聊天历史或长期记忆，不替代危机场景的正式安全回复，也不会额外调用语言模型。

候选和正式句的重复消除由浏览器实际播放状态决定，服务端始终发送正式 `sentence`。若正式句在约 700 毫秒决策前到达，候选被取消，正式句正常合成；若决策已到但视频仍未产生首帧，候选同样可以撤销。只有候选已经进入音画播放且文本相同，正式句才一次性认领该候选的真实 `onStart/onComplete` 生命周期，直接作为字幕和历史中的正式句，不再生成第二遍 TTS/口型。这样以真实开口而不是定时器作为不可撤销边界，不会因服务端猜测候选是否已播放而产生静音，也不会重复说同一句。

接话语义优先区分“用户送给人物的礼物”和“询问人物偏好”。礼物句即使包含“希望你喜欢”，也会先说克制的“谢谢你。”并使用关心/感谢动作，不再误命中偏好问句的“这个嘛。”；偏好规则本身要求疑问词或疑问语气，普通的“你平时喜欢看电影”陈述不会被当成问题。若“谢谢你。”已经真实开口，而正式首句是“谢谢你的心意……”或“谢谢你呀，……”，浏览器只裁掉重复致谢部分，继续朗读“你的心意……”或后续正文；接话未播放、正式句不同或后续句均不改写。

候选认领资格只保留到第一条正式句。第一条正式句文本不同，就立即关闭并释放认领监听；后续即使偶然出现与旧候选相同的句子，也必须正常合成和播放，不能迟到复用已经结束的候选。认领本身仍只能成功一次。

候选到达后的 500 毫秒取消窗同时用于投机准备首个口型片段，而不是空等。投机请求最多生成一段并暂停；正文及时到达就取消并释放临时音频、渲染会话和视觉句序，确定播放时才提交并继续生成剩余分片。真实竞态探针中，较冷样本在整轮 844 毫秒取得首段并立即开口，旧决策要等到约 931 毫秒；缓存热态首段在 367 毫秒就绪，实际于 732 毫秒决策点开口，较旧策略约 930 毫秒减少 198 毫秒。两轮正式首句分别到 5.6 秒和 4.6 秒才出现，证明接话覆盖的确是云端长尾。

取消协议包含独立的视觉 `skip`，不依赖投机 HTTP 请求是否已经到达服务端。真实正文若已按 index 1 等待，`skip(0)` 会清除未显示的候选末帧并立即放行；若 `skip` 先到，排序门会记住 index 0 已完成，随后到达的正文同样直接通过。这避免快正文偶发卡在候选句序之后。

候选接话的 PCM 与 M3 主回答并行预生成，并用 TTS 模型、实际 voice ID、受支持情绪和完整短句作为严格缓存键。服务发送候选时不再等待 PCM 预热完成；真人投机请求读取同一份正在生成的缓存 Promise，因此不会重复合成或重复收费，却可以同时完成请求建立和动作规划。500 毫秒取消窗结束后若确实需要播放，真人链路直接复用该 PCM，动漫链路复用由 PCM 封装的 WAV；预热失败则自动回退正常实时 TTS。普通用户输入和模型正文不进入这份候选缓存，音色变化会形成不同键，既不保存用户内容，也不会串用旧音色。DINet 返回指标额外包含常驻 worker 的 `queueMs`，用于区分动作切换/前序任务排队与真正神经渲染时间。

当前验证版以 PCM 的 `AudioContext` 绝对时钟为主时钟，每个无声视频分段开始时按实际音频进度校正 `currentTime`，从而避免独立 AAC 解码器切换，同时约束分段漂移。最终 fMP4 版仍要求音视频由同一个编码时间轴产生：每 16,000 个 16 kHz PCM 采样严格对应 25 个视频帧；不足一帧的采样留到下个块继续累计。FFmpeg 输出一次初始化片段，之后按较短 GOP 输出 `moof/mdat` 媒体片段，浏览器只按连续序号追加到同一个 `SourceBuffer`。

连续视频现默认启用，`?continuous=0` 可一键回退原有普通 MP4 分层播放器。页面只有在共享 PCM 已解锁、`MediaSource` 存在且明确支持 `video/mp4; codecs="avc1.64001f"` 时才发送 `fragmentedVideo=true`；能力不足时也会自动回退。音频解锁先立即确认 PCM 通道，再在待机期完成 MediaSource `sourceopen` 与 SourceBuffer 创建，成功后才二次开放 fMP4 协商；每轮正常结束或打断释放旧容器后会立刻预建下一只空容器。创建使用 single-flight Promise 和取消 generation，避免并发创建与迟到旧容器复活。输出使用 `frag_keyframe+empty_moov+default_base_moof`、固定 20 帧 GOP和关闭场景切换关键帧，SPS/PPS 在实测三个分片中一致。浏览器解析每个文件的 MP4 box，首段只追加一次 `ftyp/moov`，随后把各自全部 `moof/mdat` 以 `SourceBuffer.mode="sequence"` 加入同一视频元素；首次 `play()` 由共享 Promise 去重。真实页面主执行环境完成三层验收：直接追加三段得到 2.48 秒连续缓冲、首帧 37 毫秒；正式人物 iframe 联调中三段只启动一次视频，首帧 40 毫秒、相对 PCM 边界迟到 4 毫秒、三次结束事件齐全且无错误；首段开始后中断，随后 1.4 秒没有任何旧播放事件。每个后续 fragment 追加后还会以首段 PCM 起点计算期望视频时间，偏差超过 25 毫秒才轻量追赶，最大漂移写入 `data-video-max-drift-ms`，避免一次网络迟到让整段长回答持续落后。临时同源验收页已删除。

连续 MediaSource 不再在接话说完、正式首句尚未返回时停在最后一帧。若当前音频结束后 320 毫秒仍没有下一片段，iframe 优先淡入本轮仍在后台运行的低幅思考、关心、点头或微笑等待底片；没有可恢复预览时才把普通待机视频对齐到当前源时间。高幅动作和一次性倾听动作不会被保留。MediaSource 和 SourceBuffer 始终保持原样，新片段到达时先恢复解码，在自己的 PCM 边界重新显露同一个视频元素，并为该片段单独发送 `wav2lip-started`，从而让后续句字幕和历史使用真实开始时间。第一轮无预览浏览器验收顺序为：第一段开始 773 毫秒、结束 1091 毫秒、空档回待机 1423 毫秒、第二段恢复 1489 毫秒、完整结束 2148 毫秒。增加等待姿态后再次用真实 fMP4/PCM 强制扣住第二片段，得到第一段结束后 323 毫秒恢复 `thinking`、第二段在 331 毫秒后以 `resumedFromGap=true` 接管，整轮结束清理预览；两轮均无媒体错误，测试页随后删除。

首段窗口现在按播放能力选择，而不是所有客户端固定 800 毫秒。只有已经协商共享 PCM 与连续 fMP4 的链路使用 240 毫秒/6 帧首段，之后立即回到 800 毫秒/20 帧；普通 MP4、未解锁音频或不支持 MediaSource 的兼容路径仍使用 800 毫秒。连续流保留 160 毫秒尾音，因此累计约 400 毫秒 PCM 即可开始首次渲染，比上一版固定少等 80 毫秒。动作等待预览的接管提前量同步使用 240 毫秒，保持源动作帧与口型首段一致。

连续链路只在共享 PCM + fMP4 会话使用 240 毫秒首段和 160 毫秒保留尾音，兼容 MP4 仍保持 800 毫秒首段和 240 毫秒尾音。上一版 320 毫秒页面样本已证明连续音画调度与后续 800 毫秒分片具有余量；本轮只改变首段的 PCM 门槛和对应动作提前量，不改变第二段、共享音频时钟、首帧门控或回退路径。

浏览器首帧门控随后消除了上述鼓掌动作的 36 毫秒迟到。旧逻辑只在音频边界前 32 毫秒调用连续视频 `play()`，但真实首帧解码需 30–63 毫秒；并且解码完成后视频会在隐藏状态继续前进。现在利用 Web Audio 固有的 60 毫秒调度余量立即预解码，拿到首帧后暂停锁定，直到准确音频边界再恢复播放和显露。相同鼓掌素材复测首帧仍需 61 毫秒，但交接迟到从 36 降为 0 毫秒；关心素材首帧 63 毫秒，交接迟到 4 毫秒。视频不会提前偷跑，声音也不会先于嘴形。

开发服务的文件监听也从整个项目目录收窄为 `server.mjs` 与 `src`。旧 `node --watch server.mjs` 会把 `public/dinet-avatar/generated` 中每个新口型片段视为文件变化，导致生成过程中重启 Node、PID 改变并中断 SSE，表现为偶发卡顿或页面闪断。新配置生成两轮共六个 fMP4 后监听 PID 保持不变；正式 `npm start` 本来不使用 watch，不受影响。

正式首句的 MiniMax WebSocket TTS 不再只做空连接预热。服务在发起 M3 请求前创建 TTS 连接并立即完成 `task_start → task_started`，通过 `speech-ready` SSE 把任务 ID 交给页面；首个 `sentence` 到达时只需发送正文与 `task_finish`。早期版本只能等 M3 上游 HTTP 建立后再启动任务，以免长尾期间失效；加入下面的单租约轮换后，任务可以安全地从聊天起点与上游建连、推理完全并行。真实即时消费探针中连接与任务分别提前 2,033/1,993 毫秒完成，`connectionReused=true`、`taskPrimed=true`，首 PCM 230 毫秒、400 毫秒真人口型首段 611 毫秒。若预启动任务仍因网络或供应商超时失效，服务保留一次普通新连接回退，不让回答失败。人物的 `excited/caring/calm/curious` 在任务预启动时映射到供应商支持的 `happy/neutral`，避免因初始人物情绪不是供应商枚举而退成不确定音色。

M3 偶发超过 15 秒的云端长尾时，首句 TTS 预启动任务采用单租约轮换：等待期间每 8 秒创建一个新任务、先把新 ID 通过 `speech-ready` 交给页面，再关闭上一个任务，因此每轮始终最多保留一个可用预热任务。首句进入事件流前立即冻结最新任务，避免浏览器消费时被后台计时器替换；取消、断流或无正文结束则释放任务。该机制不增加语音合成次数，只有轻量 WebSocket/任务握手；页面沿用原有事件协议并始终以最后收到的任务 ID 合成首句。轮换失败会停止租约并清理旧连接，实际首句仍可走普通新连接回退。

行为导演现在按“动作语义”而不只按动作名称判断切换。`happy/nod/thumbs_up/clap/cheer` 属于同一个正向庆祝意图，`thinking/shrug` 属于思考意图，`caring/shy` 属于亲近关怀意图。一轮已经选择鼓掌时，回复里的“你真厉害”不会先改成点赞，下一句的“值得骄傲”也不会再切回鼓掌；主动作完成后自然回到待机。只有语义真正变化，例如庆祝后转入分析，才允许一次思考动作。明确要求的动作仍具有最高优先级。这样保留动作丰富度，同时避免短回答像动作演示一样连续切换同义大动作。

完全中性的日常轮次增加确定性的低幅微动作节奏，而不是随机触发或继续静止：只在服务端没有给出任何语义动作时，四个普通轮次依次使用 `nod → idle → happy → nod`，达到 75% 的轻点头/微笑覆盖并保留 25% 真正安静的呼吸待机。关心、思考、庆祝和用户点名动作不消耗这个节奏，也不会被它覆盖；模型首句若出现更明确的不同语义，仍以首句语义替换微动作。微动作由页面在等待 M3 时立即预热对应真人底片，不把素材切换成本放到首句口型之后。人物容器的行为计划带 `implicitMicroGesture=true`，便于区分语义动作与节奏动作。

中性微动作现在与关心/思考一样进入回答等待期，而不是等人物开口才启动。浏览器在收到 `meta` 后立即选定本轮节奏动作；真人端请求同一个串行 worker 预热素材，接口同时返回受白名单约束的原始动作视频地址，预热完成即静音播放，动漫端直接触发低强度骨骼动作。正式首句仍为同一动作时，以 iframe 实际回报的媒体时间加 240 毫秒首段提前量计算 DINet `frameOffset`；若预热尚未完成、首句已经到达、语义动作发生变化或用户中断，则预览不再启动或立即清理，不能在人物开口后迟到覆盖画面。

动作素材预热只执行最终有意义的选择。服务端继续在 M3 等待期间预热关心、思考、庆祝等已由用户输入明确推断的语义动作，但 `meta.action=idle` 时不再主动切回待机，因为浏览器随后还要根据跨轮节奏选择 `nod / idle / happy`。浏览器把四轮节奏的每一轮都标记为 `cadenceManaged`：低幅轮次预热并播放最终底片，纯待机轮次只预热 idle 而不创建额外预览。实测连续素材切换每次约 135–171 毫秒；删除 `happy → idle → nod` 中间切换可避免约 277 毫秒串行 worker 工作，同时防止动作底片被短暂切回待机。

首句逗号快速分段不再仅按字数判断。流式解析器会等逗号后至少出现两个正文字符，再判断前半句是否能独立朗读；`如果/因为/虽然/听到/看到/能让/把/被` 等从属开头，以及以“的时候、的话、所以、然后、的、也、就、很、需要、可以”等依赖成分结束的分句都会继续等待完整句界。像“我已经把事情处理好了，接下来……”这样的独立分句仍能提前进入 TTS；“哇，能让你特意停下来看，一定……”不会再拆成两次语调和两次口型任务。该门槛只改变首个逗号的抢先策略，句号、问号、感叹号和流结束仍立即释放。

高幅动作的语义来源现限定为用户输入，而不是把“用户 + 人物回复”混在一个字符串里放大。用户说“哇，真的吗”“我成功了”“不知道怎么办”仍分别得到惊讶、鼓掌、耸肩；人物回复中普通的“哇”“恭喜”“完成”“不知道”不能反向让自己突然捂嘴、鼓掌或摊手。单纯“开心、高兴、哈哈”降为微笑，只有成功、搞定、好消息、恭喜、通过、赢得、录取、升职等明确成果才鼓掌；普通“突然想到”“有点意外”不再触发惊讶。回复文本仍可推断点头、微笑、关心、思考等低幅动作。

生活分享的“去采访化”兜底只处理询问分享对象外观、地点、时间、人物等细节的追问，例如“什么样的树呀”“是什么颜色”；不再删除或改写“吃了没”“要不要休息”等照顾性问题。疲惫、烦躁、饥饿和困倦也明确属于关心上下文，即使输入同时包含“今天、下班、回来”等生活分享词，关心语义仍优先。该判断发生在句子进入声音、字幕和口型之前，三条输出始终一致。

生活分享追问的清理也覆盖同一句逗号后的采访尾巴，例如“热茶配傍晚刚刚好，什么茶呀？”保留为“热茶配傍晚刚刚好。”；已有独立回应后的“是什么形状的云？”只删除末问句。天气、景色、声音和舒适感等明确正向分享在 M3 等待期使用“真好。”作为短接话，并把整轮初始状态统一为 `happy/nod`，因此等待底片、接话和正式口型不会在点头与待机间切换。像“我很开心”仍使用微笑，“我不舒服”仍使用关心，不被正向分享规则覆盖。

询问人物自己的爱好、兴趣或周末习惯属于轻松自我表达，不再自动进入持续思考动作。等待期使用“这个嘛。”配合低幅点头，正式回答也保持 `happy/nod`，避免接话前后从待机切到点头；以“我喜欢、我平时、我通常、我经常”开头的逗号分句会等待完整句界，避免“我喜欢在夜里拍星空，”被单独送入一次 TTS。真实复测的 `meta`、接话和两句正式回答均为 `happy/nod`，人物背景可正常融入回答。

轻松的自我偏好问答现在最多朗读两个完整句子。达到上限后立即取消上游剩余生成，以已经下发的句子作为最终回答；这不是全局截断，详细分析、规划和需要补充关键信息的请求不受影响。中文顿号 `、` 只作为列举符号，不再参与首句快速分段；像“几点开始、有多少时间”会作为同一个完整问句进入 TTS 和口型，避免半句单独起一次渲染任务。

首个逗号分句不再只看固定字数。默认仍要求至少 9 个正文字符，并继续阻止条件句、因果句、情绪开场和枚举行程过早朗读；但“睡到自然醒”“先喝一杯水”“去附近走走”这类至少 5 个字符、以明确动作动词开头且能独立成立的建议，可以在两个后续字符已经到达后提前进入 TTS。这样不会重新产生“辛苦了，真的。”式碎片，又能减少建议类回答已有正文后仍等待下一长分句的空档。真实三轮同类请求的首文本到首朗读句间隔为 0–171 毫秒，旧样本为 333 毫秒；完整首句流水线实测首句 1771 毫秒、TTS 首有效 PCM 再用 273 毫秒、首个人物片段在整轮 2292 毫秒产生。

快速逗号策略每轮只允许第一个自然短语抢跑。若 MiniMax 在一个网络块里同时返回多个逗号，解析器取得第一段后立即停止，剩余内容放回缓冲区；后续调用关闭逗号边界，只等句号、问号、感叹号或分号。因此“睡到自然醒，去附近走走，随手买点小吃，心情就会很好。”最终只产生“睡到自然醒，”和剩余完整句两个 TTS，而不是四个碎片。普通建议默认最多三个完整句，详细、全面、分步骤或要求多个方案时不截断；已经给出建议后的“你最近有什么想做的吗？”等泛化尾问会删除，真正用于补齐场合、预算、过敏等关键信息的澄清问题保留。

生活分享的文案兜底也覆盖“整条回复只有追问”的情况：若用户没有提问/求助且不含危机情绪，模型只返回“什么样的树呀？”这类采访式追问时，在任何 TTS 任务建立前改为自然陈述“听起来挺特别的。”；已有实质回应后追加的追问则只删除末句。真正的问题、规划请求以及“你现在安全了吗”之类安全确认保持原样。

回复还会做窄范围的事实落地检查。人物提示明确禁止声称知道当前天气、用户最近行程、工作强度、作息或状态，除非用户消息或用户历史提供了依据；服务端对模型偶发的句首“最近天气挺好的，”“看你这两天节奏也挺紧的，”再做一次确定性清理，只删除该无依据前缀，保留后面的实际建议。检查上下文时只读取用户发言，不把旧助手猜测当成新证据。用户确实说过“最近天气很好”或“最近工作很忙”时，对应描述原样保留。

事实依据按短语而不是单字判断。“热闹、冷静、热门、冷门”不等于用户提供了冷热天气；“事情、工作、安排”单独出现也不等于用户很忙。天气依据要求天气、气温、晴雨、降温等明确名词，或“今天很热、外面冷了”等带时间/地点和状态边界的表达；负荷依据要求“最近很忙、我累了、加班、压力大、工作很多、安排很满、节奏很紧”等强度关系。这样既拦截模型猜测，也不会删除用户已经明确说出的真实状态。

事实清理与流式首句还有独立的空片段约束。模型可能先单独给出超过逗号阈值的“看你这两天工作挺忙，”；该片段清理后为空时，服务端直接跳过，不发送 `sentence`、不冻结首句 TTS 租约、不取消接话，也不占用动作预算，继续等待后面的真实建议。诊断只累计 `filteredSentenceCount`，不会新增日志正文。整轮最终回答仍保留“我在听。”兜底，用于供应商确实没有返回任何可朗读内容的异常情况。

首句 TTS 的 WebSocket/TLS 建连现在也与 M3 等待并行。`/api/chat/stream` 开始调用文本模型时同步建立一个一次性的 MiniMax TTS 连接，并按用户当前语义预先启动只绑定模型、白名单音色和标准化情绪的空任务；浏览器收到第一句后把随机连接标识交回人物流接口，此时才发送实际朗读文本，因此不会提前生成或保存预测文案。连接只能使用一次，15 秒未使用自动关闭，最多保留 16 条；领取时必须再次核对模型、解析后的音色和标准化情绪，任一项与实际首句不一致就关闭预热任务并新建正确连接，不能为了提速使用错误语气。底层流接口还有相同校验，防止其他调用方绕过领取层。真实同配置闭环中连接提前约 1.7 秒完成，`connectionReused=true`、`taskPrimed=true`，TTS 首 PCM 为 212 毫秒、首个 320 毫秒人物片段为 408 毫秒；把实际情绪由预热的 `happy` 改成 `sad` 后稳定回退为 `connectionReused=false`，证明不会串用语气。Speech 2.8 Turbo 与 2.6 Turbo 各三轮 A/B 的首包中位数分别为 456 和 460 毫秒，没有证据支持为速度切换模型，因此继续使用 2.8 Turbo。

模型等待期现在不再只显示静态待机。服务端利用已经用于动作预热的本地语义状态，在 `meta` 中只为 `caring / thinking / happy / nod` 四种低幅动作提供同人物原始底片；真人 iframe 立即静音播放该底片，动漫直接触发现有低幅骨骼姿势，不增加 TTS、DINet 或云端调用。第一句仍使用同一动作时，iframe 回报真实媒体位置，页面按 25 fps 换算 `frameOffset`，再额外预留首段 600 毫秒生成时间，让 DINet 从接近屏幕当前姿势的位置接管；动作不一致或短开场被调度器延后时立即清理预览。鼓掌、欢呼、挥手、惊讶、鞠躬等高幅动作不进入等待预览。真实页面“我今天工作有点累”测试中，关心动作在首句前 2317 毫秒出现，正式口型从第 74 帧接管，事件顺序为 `ready → preview → speech → ended`，没有中间回待机。

慢响应下的接话短句也已并入同一条动作时间轴。服务端等待预热 PCM 完成后，把接话音频的准确毫秒数随 `backchannel` 事件下发；浏览器在准备接话口型时根据等待底片的当前媒体位置和首段生成提前量计算起始帧，随后正式回答以“接话起始帧 + 完整接话音频时长”继续，后续同动作句子再叠加各自已播放时长。动作不匹配时不强行续接。真实页面验证中，等待关心动作之后的接话短句从第 32 帧接管，正式正文第一句约从第 78 帧、第二句从第 123 帧继续；该轮正文首句 1432 毫秒到达，TTS 首音频 224 毫秒、首段视频 567 毫秒，没有任何一次回到动作第 0 帧。

动作保持时间与接话音频时间是两个独立概念。`holdMs` 仍保证点头、关心等姿势不会过快回落，但正式回答的 `frameOffset` 只累加接话流的 `expectedAudioMs/receivedAudioMs`；只有音频元数据尚未到达时才保守使用 400 毫秒首段值。人物容器记录 `data-backchannel-continuation-ms` 供页面验收。裁剪短接话后的一轮真实页面测试中，姿势仍保持 1400 毫秒，但源视频只前进实际 PCM 的 770 毫秒，视频交接迟到为 0 毫秒。

接话内容进一步限制为真正的短反馈，而不是另一句完整回答。关心固定为“我在。”，思考为“我想想。”，普通倾听使用“嗯。”或“听着呢。”，惊喜使用“真的呀？”或“哇。”；除危机安全提醒外，自动测试约束接话正文不超过 5 个汉字。默认音色实测“我在。”约 0.72–0.84 秒，六类代表女声音频范围约 0.72–1.40 秒，原关心接话约 1.82 秒。当前候选约在 200 毫秒产生，正文固定竞争窗为 500 毫秒；约 700 毫秒决策后若口型仍未就绪，竞争边界继续延伸到真实开口。修复前一次慢 TTS 探针使候选延迟到 996 毫秒、首口型到 1247 毫秒；取消等待预热后候选在 536 毫秒到达，首口型在整轮 789 毫秒准备完成。

供应商为短语音固定附带的首尾静音不再占用真人口型队列。接话 PCM 完整生成后按 10 毫秒 RMS 窗口定位有效发声，保留 60 毫秒自然起音、100 毫秒收尾且保证至少 320 毫秒；裁剪后的同一份 PCM 同时送入 Web Audio 与 DINet，因此不会产生口型错位。无有效语音、原本已经紧凑或过短的 PCM 保持原样。默认甜美女声的“这个嘛。”从 1184 毫秒缩短到 690 毫秒，去掉 494 毫秒空白。

正式回答使用流式首静音门，不等待整句结束再裁剪。门只缓存语音开始前的 PCM，按相同 10 毫秒 RMS 窗口检测到发声后保留 60 毫秒自然起音并永久打开；之后的句中停顿、换气和结尾静音全部原样传给 DINet 与 Web Audio。若 1.2 秒内始终没有检测到有效发声则原样放行，避免极轻音色被误吞。正式句实测移除 230 毫秒前导空白，页面 TTS 首有效 PCM 为 237 毫秒、首视频段在整轮 1992 毫秒就绪，音画交接迟到 4 毫秒。

约 700 毫秒的开口决策之后仍可能存在“已提交播放、尚未真正出声”的短窗口。正式正文在此时到达且与接话不同，浏览器会按该接话片段的 `requestId` 精确撤销：取消仍在准备的 DINet 流、移除未显示的视频、停止尚未到达音频边界的 Web Audio source，再立即让正式句进入同一顺序队列。取消不会发送全局清空消息，因此不影响正式回答或同轮其他片段；一旦 iframe 已发出真实 `wav2lip-started`，接话就受保护并完整播放，避免中途截音。相同正文仍认领接话的真实开始/结束生命周期，不重复合成和朗读。

接话验收不再只依据服务端发送事件或前端入队时间。人物容器在 iframe 首帧事件真正到达时记录 `data-backchannel-started-ms`，完整播放后记录 `data-backchannel-completed=true`；每轮开始会清除旧值。由此可以区分“模型很慢但接话已经出现”“接话仍在 DINet 队列”和“候选在开口前被正式正文取消”三种情况。

对需要分析、建议或规划的消息增加了一次严格受限的长尾衔接。正式首句超过 3.2 秒仍未出现时，服务端才发送“这个我再想仔细一点。”的准备事件；浏览器仍执行 500 毫秒可取消窗口，因此最早约 3.7 秒开口。正式句在开口前到达会取消其 TTS 与 DINet 准备，开口后到达则按同一语音队列自然接续。问候、普通分享、“我饿了”等非分析消息不会触发，整轮最多一次，也不发起第二次文本模型请求。页面记录 `data-long-wait-backchannel-ms`，服务端诊断记录 `longWaitBackchannelMs`，便于和正式首句时间核对。

真人接话动作使用可见帧时钟而不只累计语音长度。第一次接话真实开口时记录动作墙钟；接话结束后即使等待 M3 的几秒里只有静音思考预览，时钟仍持续前进。第二次长尾衔接和正式正文取“可见墙钟 / 已接收音频时长”的较大值，再加首片段准备提前量计算源帧，因此不会从第一次接话的旧帧重新抬手。动漫姿势仍由同一保持状态自然延续，不使用真人视频帧偏移。

接话与正式首句还可能是“短反馈 + 同前缀完整句”，例如本机真实记录中的“听着呢。”接“听着呢，什么事？”。若接话已真实开口，播放器现在只合成逗号后的“什么事？”，从而让听感成为一条连续的“听着呢，什么事？”，而字幕、最终文本和聊天历史仍保留模型给出的完整句。裁剪仅接受忽略标点后完全相同且由逗号、分号或顿号继续的前缀；不同措辞、“我在认真听”这类没有分句边界的句子不会被误剪。接话若尚未开口仍走精确取消，不会为了复用前缀而延后正式回答。

连续通话的下一轮监听不再统一固定等待 180 毫秒。共享 Web Audio PCM 路径的播放完成事件以绝对音频时钟为准，可以安全使用较短的恢复窗口；页面在用户实际解锁的 `AudioContext` 上读取 `outputLatency`（不可用时使用 `baseLatency`），按“设备输出延迟 + 40 毫秒防回声余量”计算，并限制在 80–180 毫秒。非 PCM、音频上下文未解锁或旧视频音轨回退仍固定 180 毫秒，避免把人物尾音重新送入语音识别。页面记录 `data-audio-output-latency-ms`、计划的 `data-listen-resume-delay-ms` 以及识别真正 `onstart` 时的 `data-answer-end-to-listening-ms`，可以在实际 Mac 扬声器、耳机或蓝牙设备上区分计划等待与浏览器识别启动开销。自动化点击不属于可信用户手势，无法创建真实 `AudioContext`，因此设备值只在用户实际开始通话后采集，不用测试浏览器空值冒充真机数据。

动作决策现在明确分为三层优先级：危机安全表达最高；带“给我、帮我、请、做、摆、向我”等请求结构的明确动作其次；普通情绪、模型回复语义和连续心情最后。明确动作在服务端 `meta`、每个流式 `sentence` 以及浏览器首句调度中都保持不变，不会被回复里的“很棒”改成点赞，也不会因为“累、烦”改成关心；短开场也不延后明确的害羞、思考或关心动作。14 类动作指令矩阵覆盖鼓掌、欢呼、惊讶、鞠躬、耸肩、交叉、抱胸、害羞、点赞、点头、挥手、微笑、思考和关心。真人链路输入“我很累，给我鼓掌鼓励一下”最终只输出完整句“辛苦了，歇一会儿吧，你已经做得很好了。”，所有事件保持 `clap`。朗读清洗同时删除“啪啪啪”“来，啪啪……”等动作拟声词；快速逗号分段最低正文长度从 6 提到 9 个汉字，最多牺牲同一句内少量首段提前量，避免两三个字的碎语调。

长回答使用双重有界缓冲。Web Audio 最多提前排程约 4 秒，MediaSource 最多提前追加约 4 秒；考虑当前 800 毫秒分片，观测上限约为 4.8 秒。视频播放点后方只保留约 3 秒，`SourceBuffer.remove()` 与 append 共用同一串行队列，不发生 updating 冲突。12 秒/15 分片页面压力测试中，视频最大前向缓冲 4.8 秒、音频 4.78 秒，历史视频累计回收 3.121 秒，单视频启动、15 个结束事件齐全且无错误。人物容器暴露 audio/video ahead、音源数、缓冲起点和累计回收秒数。SSE 仍是 HTTP 单向流，服务端可继续生成至 60 秒上限；未下载 PCM 由 60 秒 TTL、8 MiB 全局内存上限保护，未来若改双向 WebSocket 再把背压传递到 DINet 生成端。

DINet 渲染也加入基于播放确认的窗口，不再把长回答完整算完。新页面协商 `renderBackpressure=true` 后，每个会话最多有 6 个已渲染但未播放确认的 segment；第 7 个在进入 DINet 前等待。iframe 只在对应 PCM 真正播放结束后返回原始 stream ID/sequence，父页面调用本机 `/api/dinet/stream/:id/ack`，播放错误则直接 cancel。生成完成与播放完成是两个状态：最后一段生成后保留最多 60 秒的轻量确认状态，最终 ack 才释放 session 和 PCM；页面消失则超时回收。真实 15 段测试得到 `received=acked=15`、最大未确认 6，前六段 1.188 秒内生成，第七段在首个 ack 后 560 毫秒到达。HTTP SSE 本身仍单向，但独立 ack 请求已经把播放背压传回 DINet 计算入口。

前端需维护少量背压：未播放内容目标保持 300–800 ms，超过上限暂停向 DINet 投递，低于下限才继续追加；不允许为了追赶而乱序播放。用户中断时同时关闭 M3 流、TTS WebSocket、PCM 解码器、DINet 会话和 MediaSource，并递增会话令牌，任何旧分片到达后直接丢弃。

第一阶段的验收基线：

- 正常网络下，从收到首个可朗读文本到首段人物开始播放不超过 2.0 秒；
- 从用户停顿到人物开始播放的中位数目标不超过 3.0 秒，并分别记录 STT/VAD、M3、TTS 首音频、DINet 首帧和浏览器起播时间；
- 连续 30 秒回答的音视频偏差不超过 80 ms；
- 相邻片段没有音爆、重复字、静音缺口、黑帧、人物跳位或嘴形回零；
- 动作在整个回答中保持同一素材时间轴，不能每个分片从动作首帧重新开始；
- 用户打断后 200 ms 内停止旧声音与旧视频，下一轮不会混入旧分片；
- 流式链路失败时可回退当前“整句 WAV + 完整 MP4”实现。

主页语音按钮是通话级开关，不是单句录音按钮。开启后依次循环“聆听 → 根据识别确定性与语义完整度判断停顿端点 → 暂停麦克风 → 生成并播放回答 → 播放队列完全结束后按设备尾音延迟自动续听”。停顿检测由浏览器本地 Web Audio VAD 完成，不再完全依赖浏览器语音识别器较慢的自动收尾。人物回答时不开启语音识别，防止 TTS 被当成用户输入；无语音和临时识别错误会在短延迟后自动恢复。再次点击按钮会结束整个通话，同时停止当前识别、文案请求、语音和动作播放。

用户停顿端点不再固定为 650 毫秒。浏览器 `isFinal=true` 直接提交，不再进入静音阈值分支；中间结果带完整句末标点时使用 420 毫秒，12 字以上完整表达使用 500 毫秒，普通表达使用 560 毫秒，“嗯”等三字以内短词继续保留 650 毫秒，停在“但是、因为、如果、我觉得”等明显承接词上则延长到 700 毫秒。这样 final 路径删除 340–430 毫秒重复等待，临时结果仍不会为了追求数字而截断自然思考停顿。VAD 路径实际采用的阈值与检测到的静音时长继续写入 `data-vad-silence-target-ms` 和 `data-vad-silence-ms`。

性能归因不再把 VAD 达到阈值之后的几十毫秒误当成整个 STT/VAD 阶段。`data-vad-stop-to-submit-ms` 保留提交门内部诊断；跨轮匿名指标使用 `speechEndpointMs = endpointSilenceMs + stopToCommitMs + recognitionCommitToRequestMs`。前一项来自 `SpeechEndpointDetector`，后二项来自 `RecognitionTurnGate` 和页面请求边界，因此既覆盖 340–700 毫秒语义停顿，也不把用户正在说话的时间算成系统延迟。

VAD 能量端点不再只学习“低于 0.025”的前 320 毫秒。旧规则在风扇、空调或增益较高的麦克风上会把稳定底噪永久当成用户仍在说话，本地端点因而无法提交。现在独立 `SpeechEndpointDetector` 会学习较高但稳定的环境声，同时将“可判为静音”的动态阈值封顶为 0.045，避免用户一开口就把语音音量学成新底噪。只有已经存在识别文字时才累计静音，持续语音会立即清零计时。当前学到的底噪与判定阈值记录为 `data-vad-noise-floor` 和 `data-vad-threshold`，便于区分“没有听到静音”和“Web Speech 没有返回文字”。

人物回答期间不常驻开启浏览器语音识别，但复用同一条带 `echoCancellation/noiseSuppression/autoGainControl` 的麦克风流进行本地插话检测。检测从人物真正开口开始；上一轮 final/VAD 一旦决定停止识别，就立即释放逻辑 `recognitionRunning`，不需要等浏览器迟到的 `onend` 才允许插话检测。检测先学习 480 毫秒扬声器残留基线，再要求近场输入高于 `max(0.032, baseline×2.8)` 持续 160 毫秒。低于 160 毫秒的敲击或瞬态噪声会清零保持时钟，不触发打断。命中会递增回答代次并沿已有取消链同时终止文案、语音、口型视频和动作，60 毫秒后进入正式识别；旧回答的异步完成回调因代次不符不能再次恢复聆听。这个半双工加本地打断方案比播放期间直接运行云端识别更不容易自回声，同时使旧音画的停止判定回到 200 毫秒目标内。

浏览器的 `AbortController` 不只停止读取 SSE。服务端把响应 `close` 绑定为一次性客户端取消信号，并向上游 MiniMax 流式 fetch 和正在投机生成的接话 TTS 传播；同时关闭本轮尚未消费的首句 TTS 预连接、清除接话计时器，禁止继续发送句子。正常 `done` 会先解除关闭监听再结束响应，只有这条路径会写入用户结构化记忆和人物情绪连续状态。诊断中的取消轮次保留 `status=cancelled` 与 `cancelledMs`，但没有 `final`，便于区分用户插话与模型失败。

字幕显示与短期聊天历史使用两个不同的真实播放边界，而不是以模型生成完毕为边界。模型句子和口型片段仍可并行超前准备，但真人模式只在 iframe 回报首个 `wav2lip-started`、动漫/普通音频只在音频 `play/onstart` 后显示对应句子；历史则必须等该句最后一个音画片段完整结束才提交。正常播放结束后使用服务商的完整最终文本写入历史；用户插话或连接失败时，页面保留已经开口的当前字幕供用户理解中断位置，模型上下文只保留按顺序完整说完的句子，未播放及只说到一半的内容全部丢弃。若人物尚未开口，页面不会留下空的助手消息，下一轮模型也不会看到一段用户实际没有听过的回答。

真人模式支持独立角色选择。页面保存 `realAvatarCharacter`，并将它同时传给真人 iframe、动作预热、聊天流、分段语音和 DINet 渲染；服务端对角色编号做白名单归一化，并把角色加入视频缓存键。这样切换人物后，待机底片、等待动作、正式说话底片与缓存都来自同一个人物，不会把不同人物的脸或动作混入同一回答。当前默认角色是露米，第二角色小桃使用 `xiaotao_*` 动作命名空间。

DINet 只常驻一套 Audio2BlendShape 与神经渲染模型。每次请求携带角色编号和语义动作，worker 在同一进程内切换对应视频帧、人脸数据、参考特征和网格，避免每种动作或每个人物重复加载一份模型。回答的第一句使用本轮动作，后续句子回到待机，动作与语音同时发生。

MiniMax 短语音在服务进程内保留最多 64 条 LRU 缓存，只以模型、音色、情绪和朗读文本为键，不包含用户身份或聊天历史。相同短句再次出现时直接复用 WAV，并自然命中 DINet 的内容寻址视频缓存；缓存不落盘，服务重启即清空。

### 对话动作调度

主页面通过 `public/conversation-actions.js` 在语义动作与底层素材之间增加对话级调度。每轮先接收服务端根据用户语义推断的主动作，再决定每个朗读分段实际使用的动作：关心、思考等低幅动作遇到不足 6 个字的逗号开场时，首个短语保持待机，把动作留给下一句完整内容，避免人物只在“辛苦了”三个字里匆忙抬手又立即收回。鼓掌、欢呼、鞠躬等强调动作仍在第一句立即出现。

高幅动作共享 3 秒冷却，冷却期间自动降级为微笑、思考或待机；用户明确要求“鼓掌、挥手、鞠躬”等动作时不受冷却影响。进入聆听、结束回答或中断播放时都会清理上一轮调度状态，动漫骨骼姿势同时自然回落。真人和动漫共用同一调度策略，但分别使用预录视频和 VRM 姿势资源。

礼物、送花和“小惊喜”场景使用高兴表情配合关心/感谢姿势：极短的“谢谢你”先自然说完，随后在完整句子中把双手靠近胸前。用户夸人物可爱、漂亮、温柔、贴心或优秀时使用害羞姿势和腮红；人物轻度认可用户时使用轻点头，明确说“你真棒、做得很好、为你骄傲”时使用 `thumbs_up` 夸赞动作。真人的 `thumbs_up` 使用独立的 `bedroom_thumbs_up` 竖大拇指素材，不再回退为点头。

流式 `sentence` 事件现在携带该句独立的 `emotion` 与 `action`，不再只依赖回答开始前的单一 `meta` 状态。调度器允许一轮回答在自然句界处增加一次新的低幅动作，同时禁止连续插入多个姿势。新增 `nod` 语义用于轻度认可和用户明确要求点头：真人映射到 `bedroom_agree_test`，动漫使用 1.2 秒的一次性轻点头骨骼动画，播放后停在自然头位而不循环。

高优先级负面情绪只从用户当前消息判断，不扫描模型回复中对旧对话的复述。模型回答仍可通过“慢慢来、先休息、我陪你”等明确关心表达产生低幅关心动作，但仅仅提到上一轮的“累、压力、难过”不会抢走当前话题已经确定的动作。人物偏好问答在已有实质回答后产生的末尾问句也会被丢弃，避免它为了照顾旧历史又把话题拉回去。

规划动作判断区分“请求规划”和“提到计划”。只有“帮我安排、如何规划、制定一个计划”等请求、疑问或制定语境进入思考；“计划里的事情都做完了”“明天计划去公园”不会仅因出现名词“计划”而误判。完成、做到了、做完了、办完了、搞完了等成就表达优先于规划词，使用庆祝/鼓掌；普通行程陈述保持待机或低幅认可。

问号本身不再等于思考动作。问候使用一次挥手；吃饭了吗、最近忙吗、在干嘛、一起散步或陪我聊天等社交关心/邀请使用轻点头；为什么、怎么办、分析、选择、区别和规划请求才进入思考；天气、时间等普通事实问句保持好奇表情但不强行动作。客户端仍限制挥手等高幅动作只用于首个自然句，后续句回到待机。

“开心、高兴”等词还会区分当前情绪与目标情绪。“我今天很开心”“这个建议让我很开心”仍使用高兴表情；“认真想一下，给我一个让周末开心的建议”“给我一个能让我开心点的主意”属于分析请求，等待预览、接话和首句都使用思考。过去式“我认真想了一下，决定周末去公园”不是请求，不会误触发思考。真实建议链路依次表现为思考预览、“我想想。”、首个思考短语和后续轻点头完整句，语义动作随内容自然收束。

短期浏览器历史在进入模型上下文前也会按成对的“用户问题 → 助手回答”重新清理。这样升级前已经存入 localStorage 的采访式尾问、身份技术话术和设备受限回答不会继续污染新轮次；页面上用户已经看过的旧消息不被篡改，只改变下一次发给模型的上下文。清理后仍执行角色顺序合并和 6 条/1800 字符预算。

长期记忆中的 `open_loop` 只在当前话题与待办正文至少共享一个中文二元词组时召回，不再凭固定层级加分把无关的“明天面试”带入“今天有点累”。含“帮我规划明天怎么安排”或问号的请求不会再被误存为用户未来事项；历史文件中已经存在的“怎么安排/如何规划”伪待办也在召回时兼容过滤。真实关心请求验证 `memories=[]`，M3 首句 1168 毫秒，两句在 1356 毫秒本地完成，回答没有回到旧规划话题。

### 下一阶段：行为导演与连续渲染

后续不再把“增加动作”理解为继续堆关键词，而是增加一个位于对话语义和人物渲染之间的行为导演。它在首个可朗读短语到达时立即生成本轮表演计划，不发起第二次模型请求，因此不增加首句延迟。计划包含主动作、允许的一次微动作、情绪强度、注视方向、头部倾向、动作开始位置和建议保持时长；真人与动漫共享语义时间线，再分别映射到预录底片和 VRM 骨骼。

静音整段动作与自然语义动作已经分离。`bow/surprise` 的无口型完整视频只响应用户明确动作请求；普通致谢使用微笑或点头并正常说话。自然惊讶先在等待正文时播放一次低幅捂嘴反应，正文开口时切换到微笑，从而同时保留惊讶感、正常语音和手掌遮嘴时不叠加口型层三个约束。行为计划中的 `explicit` 是播放策略边界，不再仅凭动作名决定整句是否静音。

日常低幅动作目标覆盖约 60%–75% 的对话轮次，优先使用轻点头、微笑、关心和思考；挥手、鼓掌、欢呼、惊讶等高幅动作只在语义明确或用户直接要求时出现，并继续受 3 秒冷却限制。每个朗读片段最多一个动作，每轮最多一个不同于主动作的次级动作，短开场可以把关心或思考延后到下一段完整内容。行为计划作为可观察数据写入人物容器，便于页面验收和后续接入动作时间线编辑器。

真人素材下一步优先补充同人物、同机位、首尾回中性的低幅底片：呼吸待机、轻点头、微笑保持、轻微歪头倾听、目光移开后返回、双手自然调整、低幅关心和思考回正。当前浏览器已经把 DINet 小分片接入同一 MediaSource 连续视频层，并以 Web Audio PCM 作为整轮共享音频时钟；兼容路径仍保留带音轨 MP4。下一步优化重点是持续采样真实对话的首帧、缓冲余量和长回答漂移，而不是继续增加播放器层。

后续真人动作素材执行统一的强制采集规范：动作原片只能使用无纹理纯色背景或绿幕，最终卧室等场景在后期合成；不再接受湖边、房间等复杂背景原片。幕布颜色必须与头发、服装和饰品形成明显反差，人物含绿色元素时改用蓝幕或其他高反差纯色；人物和背景分别均匀布光，并锁定机位、曝光、白平衡、对焦与快门。入库前除现有尺寸、帧率、人脸和首尾姿态检查外，还必须逐帧验收头发外圈、衣袖、手指缝和运动模糊区域，出现旧背景色边、亮边、黑影、孔洞或背景残片即拒绝安装。这样从源头避免复杂背景污染半透明发丝和快速运动边缘，不能再依靠扩大遮罩或局部补丁长期修复。

LivePortrait 的独立实验已经完成，不进入当前 Mac 的实时聊天链路。官方 PyTorch 2.3 环境会因 `grid_sampler_3d` 缺失而回退 CPU；升级到 PyTorch 2.13 后可原生走 MPS，但 30 帧眼部区域驱动仍需约 25 秒，只有约 1.2 fps。它适合在离线阶段生成或修补眨眼、轻微视线和表情素材，再把产物作为普通动作底片交给现有 DINet；不适合在用户说话后临时生成。实验环境由 `scripts/setup_liveportrait_macos.sh` 隔离安装，只下载并校验约 653 MB 的人像权重，不纳入项目仓库。离线制作统一通过 `scripts/generate_liveportrait_material.sh`，默认区域为 `eyes`、强度为 `0.35`，必须显式提供源素材和驱动素材，避免误把大幅头动应用到现有动作包。

倾听阶段现已纳入同一行为层。浏览器取得第一段有效识别文字后等待 1.4–2.1 秒；若用户仍在讲话，本轮最多触发一次低幅点头。动漫使用 1.2 秒一次性骨骼点头，真人使用同人物 `bedroom_agree_test` 静音底片的前 3.6 秒并关闭循环；抽帧差异确认该时点已完成一次动作并接近回正。识别结束、取消、开始回答或结束通话都会清理尚未触发的计时器和正在显示的真人预览。预览协议带 `purpose=listening`，页面分别记录 scheduled、triggered、started、completed/cancelled，避免与回答等待动作共用状态。

当前主用卧室真人动作包已经盘点：待机、微笑、轻点头、挥手、鼓掌、欢呼、害羞、关心、思考、耸肩、交叉和抱胸共 12 段，均为 `768×1152`、25 fps、222 帧、8.88 秒。同规格使它们适合共享同一渲染时间轴，但此前每个朗读句子都会新建 DINet 会话并从动作第 0 帧开始，连续两句使用关心、思考或微笑时会重复抬手或重复进入表情。

逐段首尾抽帧检查显示，12 段素材首尾 SSIM 均在 0.998 以上，可以安全跨过第 222 帧循环；但一段 8.88 秒素材实际包含两次克制动作，中间会回到自然姿势。行为导演因此把“物理视频循环”与“语义动作周期”分开：底片仍可无缝循环，跨句连续动作最多保持半个素材周期（4.44 秒）。当前正在朗读的完整句不会在中途硬切画面；句子结束后，关心、思考和微笑只有在该周期尚未结束时才继续，高幅动作仍只使用首个自然句，避免长回答里反复挥手或鼓掌。所有传给 DINet 的起始帧先归一化到 `0..221`，等待预览很久也不会累计出无界帧号。

行为导演仍用文本长度估算每个朗读短语的早期时间游标，以便后续句 TTS 能在上一句尚未结束时并行准备；但该估算不再决定真人最终源帧。同一视觉轮次和同一动作进入串行 DINet worker 后，worker 使用上一分片真实 `sourceFrameOffset + frames` 得到下一起始帧，跨句也不会因音色语速与文字估算不同而跳回或跳前。动作变化时在新首帧解码完成后原子切换，不再做整画面交叉淡化；VRM 仍不重复触发同一骨骼姿势。真人播放器在每句末保留 180–360 毫秒的最后一帧，给并行准备的下一句留下接管窗口，整轮真正结束后仍会自动回到待机。高幅挥手、鼓掌、欢呼等不跨句循环，避免大动作持续过久。

真人多句流水线另外使用回答级 `visualTurnId` 和句序号约束动作素材切换。各句 TTS 可以并行准备，但 DINet 渲染按同一回答的句序进入常驻 worker，防止后句先完成 TTS 后抢先把素材切走。相邻句动作不同则在媒体边界原子切换，同动作连续分片继续沿用真实源帧时间线。播放结束和打断都会关闭视觉轮次并释放排序、末帧状态。

普通 `idle` 回答也使用同一回复时间轴：后续句子的 DINet 底片从累计时间对应的源帧继续，不再每遇到标点就从待机第 0 帧重新开始。播放器以服务端实际返回的 `segment.audioMs` 累计最终位置，在最后一段仍播放时保存该位置，并提前把底层待机视频 seek 到镜像循环中的同一姿态，随后才做图层交接。这样同时消除句界的身体复位和回答结束时“说话层/待机层时间点不同”造成的闪动。

## 9. 验收基线

- `npm test` 全部通过；
- `/api/health` 返回当前供应商和模型；
- `/api/dinet/status` 的 `ready` 为 `true`；
- 真人回答结束不闪白、不双声，WAV 不播放 RIFF 元数据；
- 动漫人物切换后首次构图居中，动作期间根节点不横移；
- 人物名字、背景与页面实际保存值一致；
- “带你出去玩 / 下楼”等场景不出现“我在手机里”或技术身份解释。

页面级回归采用不触发云端接口的固定路径：真人初始画面 → 动漫学院日常 → Nike-chan v2 → 左/正/右转向 → 字幕展开。该路径只验证人物完整显示、首次构图居中、转向不移动根节点、字幕不遮掉左栏以及设置仍可用。浏览器自动化不具备真实 Web Speech 与可信麦克风用户手势，因此不得用这条路径宣称 STT、插话或端到端首响已经通过；这些结论只允许来自用户正常通话自动留下的匿名分阶段样本。

性能优化遵循“先归因、再改单变量”的门槛：至少 3 条有效自然会话样本后才报告主瓶颈；每次只针对占比最高且可控的一段调整；调整后同时保留定向测试、完整测试、服务健康状态和同口径前后样本。排名只使用语音端点、本地上下文、上游建连、文本生成、TTS 请求设置/连接/任务/合成、人物请求传输/PCM 缓冲/纯 DINet 首段渲染和浏览器交接等可行动的非累计阶段，不使用“请求到首句”“TTS 请求到首 PCM”或“语音请求到人物首片段”这类跨多个阶段的总时钟。样本不足时不主动制造 MiniMax/TTS 对话，也不重复调 VAD、分片长度或动作阈值。
