## 可以借鉴的部分

LiveTalking 的 Wav2Lip Avatar 预处理位于 `avatars/wav2lip/genavatar.py`。流程是把输入视频拆成逐帧图片，批量检测人脸，平滑检测框，保存裁剪后的人脸图片与 `coords.pkl`。服务端通过 `server/avatar_routes.py` 和 `server/task_manager.py` 把生成过程包装成可查询状态的异步任务。

这些设计适合后续加入本项目：

1. 上传或选择本地视频；
2. 后台执行 DH_live `step0_keypoints` 和网页资源打包；
3. 报告 `pending/running/completed/failed` 状态；
4. 把每个动作登记到统一清单；
5. 在加入运行时之前检查视频、关键点数据和模型包是否完整。

## 不能直接照搬的部分

LiveTalking 的自定义动作配置位于 `data/custom_config.json`，运行逻辑位于 `avatars/base_avatar.py` 和 `avatars/audio_features/base_asr.py`。它用 `audiotype` 把静音、正常说话和自定义动作分开：自定义动作通常绑定自己的音频，播放时优先占用输出；渲染器遇到非正常说话帧时直接使用预制图片，不进行口型推理。

因此原实现适合“不说话时播放动作”，不符合本项目“人物一边做动作一边回答”的目标。直接移植会重新出现动作结束后才说话的问题。

本项目保留现有方式：动作仍是经过 DH_live 预处理的真人视频包，TTS 音频持续进入同一个嘴部推理器，所以动作和口型可以同时发生。只移植 LiveTalking 的配置化和资源管理思想。

## 已落地的改动

`public/dh-live/actions/manifest.json` 现在统一描述：

- 动作对应的资源目录；
- 是否循环；
- 播放完成后返回哪个状态；
- 是否适合被打断；
- 尚未录制动作的降级目标。

浏览器不再依赖硬编码动作目录。比如当前没有真人 `clap` 素材时会降级为 `happy`；以后录制并完成 DH_live 预处理后，只需增加资源目录并修改清单，不需要再改渲染代码。

新增 `scripts/prepare_dh_action.mjs`，把单段真人视频封装成完整动作包。脚本会检查视频尺寸、帧率和时长，调用 DH_live 自动检测人脸与关键点，拒绝存在明显说话的源视频，生成网页资源，检查逐帧数据，并在安装前对比 `idle` 的分辨率、人脸中心和人脸大小。动作登记会原子更新清单，默认拒绝覆盖已有资源。

DH_live 固定版本与 macOS 兼容补丁保存在 `integrations/dh-live/`。端到端验证使用现有 1280×720、25 fps、2.2 秒的微笑素材，重新生成 55 帧动作包；生成视频 SHA-256 与已部署素材一致，逐帧嘴部区域也完全一致，证明新脚本复现了之前的手工流程。

## 下一阶段录制约束

第一轮只录制 `idle`、`nod_smile` 和 `thinking`：

- **所有新录制或生成的真人动作原片必须使用纯色背景或绿幕**，不得把卧室、湖边等复杂最终场景直接拍入动作原片；最终场景统一在后期合成；
- 背景应平整、无纹理、无褶皱、无明显反光，并与头发、服装和饰品保持足够色差；人物含绿色服饰或饰品时改用蓝幕或其他高反差纯色背景；
- 背景与人物分别均匀布光，避免逆光发丝、背景阴影和绿色反光污染皮肤、头发及半透明边缘；
- 同一人物、服装、机位、焦距和光照；锁定曝光、白平衡、对焦和快门，所有动作保持一致；
- 25 fps，人物尺寸和画面中心保持一致；
- 嘴部无遮挡，源视频不说话；
- 每段从同一自然姿势开始，并回到同一姿势；
- 动作幅度小，避免手遮挡嘴和下巴；
- 待机片段可循环，动作片段只播放一次；
- 验收必须逐帧检查头发外圈、花饰、衣袖、手指缝和运动模糊区域，不允许出现旧背景色边、亮边、黑影、孔洞或背景残片；
- 先通过 DH_live 关键点质量检查，再进入网页资源打包。

完成三段闭环后，再增加挥手、轻微惊讶、关心和鼓掌，避免一次录制太多素材却无法无痕切换。
